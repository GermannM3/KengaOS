# COMPAT — запуск чужих приложений (костыль на первое время)

Задача: пока сообщество не написало нативные приложения, дать пользователю
ставить привычные программы. В десктопе — Windows-программы, на мобилке —
APK. Честно: это марафон, разбитый на этапы, где каждый этап полезен сам
по себе.

## Общая база (этап 0) — пакетная система

Без store и пакетов ни Wine, ни APK некуда ставить. **Сделано (v0.7):**

- Формат `.kpkg` v1 — текстовый манифест (name/version/desc/entry),
  лежит в initrd рядом с ядром.
- `kernel/kf_pkg.c` — скан VFS, парс манифестов, реестр, установка.
- Десктоп: окно «Магазин KengaOS» со списком пакетов; установка командой
  `install <буква>` в input-баре; тест в CI (`STORE_TEST=1`).
- Далее: .kpkg v2 = tar/zip с бинарём+иконкой+ресурсами; подпись пакетов;
  репозиторий пакетов по сети (сборка dist-папки в релизе).

## Десктоп: «Wine для KengaOS»

Ставить .exe напрямую — нельзя без трёх слоёв. Порядок работ:

1. **Ring-3 процессы + ELF-загрузчик** (фундамент, в старом kenga-os v0.0.5
   уже был прототип — портируется в единое ядро): изоляция страниц,
   syscalls (SYSCALL/SYSRET), планировщик с вытеснением.
   - Приложение-эталон: нативный `hello.elf`, потом порты простых
     утилит (busybox-стиль) — они дадут приложению-вкус до Wine.
2. **Native SDK**: kenga emit-c умеет собирать freestanding C — то же ядро
   умеет грузить ELF, собранный обычным gcc под наш syscall ABI. Это уже
   «ставить программы» по-настоящему (наши, не Windows).
3. **Win32-подсистема (Wine-стиль)**: PE-загрузчик + реализация подмножества
   win32 API (gdi/user32/kernel32) поверх наших syscalls. Реалистичный
   потолок v1: простые Win32-консольные и окна-утилиты. Полный Wine —
   community-scale.

## Мобилка: «APK и магазины»

1. **Store UI в мобильной оболочке** (тот же kpkg, тач-версия) — контейнер
   появляется сразу.
2. **APK = Android Runtime.** APK — это контейнер с dex-байткодом + нативные
   libso + ресурсы. Чтобы «ставить и запускать», нужен рантайм:
   - реалистично-среднесрочно: портировать **ART из AOSP** на наш aarch64
     kernel API (огромная работа, но AOSP открыт); APK без Google-сервисов
     (F-Droid-класс приложений) — целевой сегмент;
   - костыль-минимум: запуск **отдельных dex** через embedded-рантайм —
     всё равно ART, без него никак. Честно: это самый длинный путь.
3. Промежуточный костыль, который реально работает: **веб-приложения**
   (наш мобильный UI — уже веб-стек в референсе) + kpkg-приложения —
   их «магазин» и отдаём пользователям до ART.
