# KengaOS — СОСТОЯНИЕ НА 188-й КРУГ (сводка; ниже — подробный журнал)

## Проверено и работает (x86_64 и aarch64)

| Подсистема | Что сделано |
|---|---|
| Диски | ATA PIO, AHCI/SATA, NVMe (x86_64), virtio-blk (aarch64) |
| ФС | KengaFS целиком на Kenga: каталоги, удаление, дескрипторы, персистентность |
| ACPI | настоящее выключение S5 + RESET_REG; драйвер EC на Kenga (в QEMU EC отсутствует) |
| Процессы | ring 3, вытеснение таймером, spawn/kill/wait/sleep/exit; таблица слотов переиспользуется |
| Приложения | полный ФС-API; сетевой результат получают сисколлом net (31) — имя файла знает только ядро |
| Сеть | PCI + e1000 + ARP + ICMP + UDP + DNS + TCP + HTTP-клиент с разбором ответа — ВСЁ на Kenga |
| USB | HID (xHCI) в вводе |
| CI | 4 гейта сборки + 18 сетевых проверок на трёх конфигурациях; сборка aarch64 + smoke |

Ключевые команды:
```
bash build/build-x86.sh                                     # все гейты x86
bash scripts/build-a64.sh && bash scripts/run-a64.sh --headless
```
Точка входа с командой ручного прогона и списком «грабель» — в разделе 147-го круга ниже.

## Что осталось

1. Мост C->Kenga к СЕТЕВОМУ коду (состояние драйвера: bar0, кольца RX/TX). Сейчас запросный API полон:
   приложение оставляет заявку, ядро выполняет работу ТОЛЬКО по ней и запускает приложение повторно,
   результат приходит сисколлом net (31). Но приложение может спросить сеть лишь ОДИН раз за загрузку
   (в момент старта), потому что заявка читается в загрузочном гейте. Чтобы спрашивать в любой момент
   и сколько угодно раз, работу должен выполнять обработчик сисколла — а он на C, тогда как стек
   драйвера на Kenga.
   сеть в фоне (приём перестал бы зависеть от точек проверки).
3. Звук, USB mass storage.
4. USB и EC на РЕАЛЬНОМ железе — принципиально требует ноутбука, в QEMU не проверяется.

# Честный чек-лист KengaOS — что увидят компании и пользователи

Дата: 2026-09-05 · Версия: v0.7.2 + UI-оболочки · Проверено по коду:
`kenga-lang/` (v3.13), `kernel/`, `src/` (десктоп + мобилка).

## Видение

ОС нового поколения: системный слой написан на языке Kenga (UI — тоже
постепенно), и система «ткёт» пророков в себя — агенты с памятью и
предсказанием (Prophet) работают как часть ОС, а не как приложение.

## ✅ ЧТО РЕАЛЬНО ЕСТЬ СЕГОДНЯ (проверено, не маркетинг)

### Видит пользователь (ISO на ноутбуке / в QEMU)
- Живой рабочий стол **Aurora**: окна с перекрытием, dock, topbar,
  обои с дрейфующим свечением. Логика десктопа — **на Kenga**
  (`desktop.kenga`, 793 строки, `ui.kenga`, `kmain.kenga`), компилируется
  `emit-c --freestanding` и грузится на голое железо.
- **Терминал** с командами, **чат с агентом** (печатает текст — агент
  отвечает через IPC).
- **4 системных агента** как процессы ОС: logger / agent / model /
  researcher — с IPC, правами (capabilities) и очередями. Видны в
  «AGENT SPACE».
- **Модель-агент ONLINE**: настоящий MLP 2-2-1 в ядре, обучен на XOR,
  инференс через IPC с проверкой прав (`CAP_MODEL_INFER`).
- **Магазин**: 6 пакетов `.kpkg` в initrd, установка из input-бара. **v2**
  (`kenga-app.kpkg`) = текстовый манифест + пустая строка + бинарный
  payload; установка целиком на Kenga: пакет читается из initrd, payload
  пишется в KengaFS `/apps/kenga-app.elf` (`install kenga-app.kpkg`),
  старая форма `install a` по-прежнему идёт в C-реестр. Гейт CI
  `STORE INSTALL OK`.
- **Prophet как системный сервис** (v1): `kernel/kf_prophet.c` — память
  эпизодов + ядро паттернов, surprise (RMSE), k-NN foresee; тикает из
  десктопа (`kd_prophet_tick`), прогноз виден в SYSTEM HEALTH.
- **Пророки оболочки, обучающиеся на ходу** (0.8.1, `Prophet.jsx`):
  ассистенты в «Чате»/«Агентах» выучивают пары «учи: вопрос => ответ»
  (память в localStorage, recall по схожести), предсказывают следующее
  приложение (цепь Маркова по открытиям, точность видна в «Мониторе»),
  surprise на неожиданных переходах. Всё локально, общий код десктопа
  и мобилки.
- **Пайпы в шелле ядра** («bash» v1): `echo text | upper | count` —
  конвейеры команд с фильтрами; boot-самотест + CI-гейт `PIPE OK`.
  Полноценный bash = userspace fork/exec (после ring-3 процессов).
- **KengaFS — персистентная ФС на диске** (`kernel/fs.kenga`, целиком на
  Kenga): superblock, битмап блоков, таблица inode (32), дерево каталогов,
  `mkdir -p`, чтение/запись/удаление; файл `/boots` считает загрузки.
  Десктоп показывает карточку **FILES · KENGA-FS** (inode/блоки + список
  файлов из inode-таблицы) и понимает команды в input-баре: `ls`, `df`,
  `cat <path>`, `touch <path>`, `mkdir <path>`, `rm <path>`,
  `write <path> <text>`. Пишем только на диск с маркером `KENGARWTEST1`
  или уже содержащий KengaFS — чужие диски не трогаются. Персистентность
  проверяется двумя QEMU-ботами на одном образе: `fs:boot=1` →
  `fs:boot=2` (`scripts/test-fs-persistence.sh`).
- **Kenga-приложение в ring 3**: `user/kenga_app.kenga` — исходник на
  **Kenga** (`println`, рекурсивный `fib`) — собирается
  `scripts/build-user.sh`: `emit-c --freestanding` → патч заглушек `println`
  в `int 0x80 write` (`scripts/patch-kenga-user.py`) → clang/`ld.lld` → ELF
  (~3.5 КиБ) → initrd → **KengaFS `/apps/kenga.elf`** → `elf_load` → ring 3,
  возврат по `sys_exit`. Работает на загрузке (гейт `USERAPP OK`) и из
  десктопа командой `run /apps/kenga.elf`. CI проверяет **вывод самой
  программы**: `kenga-app: ring3 OK`, `kenga-app: fib(12) = 144`.
  Попутно найден и исправлен баг `elf_load`: игнорировался `filesz`, и в
  `.bss` уезжал хвост файла (аллокатор Kenga-рантайма сразу получал OOM).
- **xHCI USB**: работает в QEMU на обеих архитектурах (тач-планшет,
  ECAM-скан, слоты, CONFIG_EP); на живом железе не проверен.
- **Две архитектуры одним исходником**: x86_64 ISO + aarch64 (QEMU, CI).
- **Каждый коммит** автотестируется: ядро реально грузится в QEMU на
  обеих архитектурах, включая установку пакета и ring-3 запуск.

### UI-оболочки (прототипы на веб-стеке, общий kernel bridge)

Честно: это React/Vite-прототипы поверх симуляции kernel bridge —
контракт тот же, что у ядра (37 `kd_*`); порт в Kenga/C — по `docs/design/design.md`.

- **Десктоп** (v0.8, без заглушек): окна с перекрытием, dock, лаунчер,
  терминал, **браузер** (`kenga://` + внешние сайты), **монитор**
  (графики CPU/RAM), **настройки** (3 темы + 2 обоев), **файлы** (VFS
  с Kenga-исходниками), **агенты** (чат + XOR-предсказания модель-агента),
  **чат-ассистент**, **о системе**.
- **Мобилка** (v0.8, APK на POCO M4 Pro): boot → lock → home → шторка →
  лаунчер; экранная клавиатура **Ру/En**; браузер; терминал (команды
  на русском и латинице); **звонилка с реальными контактами** (нативный
  мост) и вызовом через системный дозваниватель; **реальные SMS**
  (чтение, ответ через системное приложение); **камера** (getUserMedia,
  снимок+сохранение); файлы, агенты, чат, монитор, настройки, о системе.
- Темы — общие для обеих оболочек: Полярная / Синяя волна / Зелёная волна.
- Браузер честно: рендерит движком хоста (iframe) — оболочка пока живёт
  внутри браузера; в будущей ОС это свой движок / порт (Servo-класс).

### Видит разработчик / компания
- **Язык Kenga v3.13** — полноценный: i64/f64/bool/str/list/**Tensor**/
  **Memory**/structs, if/while/for, imports, события (`on "tick"`),
  FFI-интринсики. Компилятор: `kenga run / emit-c / build`, плюс
  **kenga-lite** (C99-хост без Rust) и bytecode-рантайм. VS Code
  расширение, книга, примеры.
- **Prophet/Memory API в языке** (это и есть «пророки»):
  `memory() / learn / predict / foresee / surprise / remember / recall /
  consolidate / save_mind / load_mind` — локальный инференс с памятью
  паттернов, консолидацией во сне (EWC-lite), сохранением разумов
  (`.km`-файлы, совместимы с Rust-хостом).
- **Тензоры + мультимодальность**: `t_matmul / t_sgd_step / load_ppm /
  load_wav` — входы изображений и звука.
- **Единая поверхность ядра** для desktop и mobile:
  37 `kd_*`-функций (агенты, IPC, память, мышь/тач, uptime) — тот же
  контракт, что декларирует `kernel_bridge.kenga`.

## ⚠️ ЧЕГО ПОКА НЕТ (честно)

| Область | Реальность | Что нужно |
|---|---|---|
| **Kenga-программы пользователей** | ✅ исходник **на Kenga** → ring-3 ELF, **упакован в `.kpkg` v2**, ставится из магазина в KengaFS `/apps`, запускается с диска **как процесс** (своя PML4, свой kernel-стек, сохранённый кадр прерывания: `k_user_spawn_blob` + `k_user_sched_run`), **читает (`sys_cat`) и пишет (`sys_save`) файлы**; записанный файл переживает перезагрузку (`kenga-app prev:` на boot 2) | ⚠️ переключение НЕСКОЛЬКИХ процессов: механизм написан, два процесса реально перемежаются (тики pid 100/101 через yield), но при возобновлении кадр портится (#PF в ring 3, в слотах GPR оказываются регистры ядра). **Исключено замерами:** таймер (маскирование IRQ0 не помогает), переполнение kernel-стека (64 КиБ — то же), общий стек (замер входа: rsp = top−304 у каждого процесса, tops в 64 КиБ друг от друга). Остаётся механика возврата через `k_resume_frame` при switch после выхода процесса. Дальше: `open`/`mmap`, вытеснение. **Разбор бага (11-й круг, дамп таблицы inode):** `fs_mkdir` НЕ виноват — после `mkdir` таблица inode корректна (`/`, boots, system, bootlog.txt, tmp, apps, kenga-app.elf, demo). Виноват `sys_save` из приложения: файл `/apps/state.txt` вообще не создавался, а приложение печатало «saved» безусловно. Гейт `kenga-app wrote:` теперь требует непустое содержимое (раньше проходил и на «(nothing)»). **Оба бага закрыты в 12-м круге одним корневым фиксом:** `isr_syscall` восстанавливал только `rax`, поэтому процесс продолжал работу с регистрами ядра (отсюда и молчаливый `sys_save`, и падение при росте ELF, и порча кадра при переключении). После `POP_GPRS` **два процесса реально перемежаются** (`kenga-app[101]/[100] tick 0,1,2` + `SCHED OK`), файл пишется и читается. **Вытеснение работает (13-й круг):** IRQ0 переключает ring-3 процессы через тот же `k_resume_frame` (`isr_common` возвращается по нему, `k_user_timer_preempt`), прерывание в ядре (cs=0x28) не переключаем. В UART `preempt=0x2`, есть гейт. Приложение умеет создавать каталог и файл в нём (`sys_mkdir` + `sys_save` в новый путь) — проверено чтением из ядра. **Найденный баг рантайма (14-й круг):** `len()` на строке, собранной конкатенацией, возвращает 0 → `sys_save` молча писал 0 байт (литерал сохраняется). В приложении длина задаётся явно. ФС-API приложения закрыт и сквозным образом проверен в CI: `cat` (16), `save` (17), `mkdir` (18), `rm` (19) — положительный гейт на созданный файл и отрицательный на удалённый. Планировщик умеет ждать: `sleep(ms)` (syscall 21) + `uptime_ms()` (22), гейт `kenga-app: sleep ok`; добавлен `up_pick_wait` (idle через `sti; hlt`), иначе выход последнего активного процесса «забывал» спящих. Плюс **коды завершения** (syscall 23): два процесса одного и того же ELF завершаются с разными кодами (`userapp exit pid=0x64 code=0x0` / `pid=0x65 code=0x7`) — доказательство пер-процессного состояния; задел под `wait`. **Приложение запускает приложение** (syscall 24, `spawn`): ELF читается с KengaFS в буфер ядра и становится процессом — в одном прогоне жили три процесса (kenga-app 100/101 + hello 102). Жизненный цикл замкнут: **`wait_status(pid)`** (syscall 25) отдаёт код завершения ребёнка (иначе −1), родитель ждёт опросом через `sleep`. **Блокирующий `wait()` работает** (syscall 26): syscall перезапускается — сохранённый RIP сдвигается на `int 0x80`, а RAX возвращается номер syscall. Этот же механизм нужен для блокирующего чтения. **ЗАКРЫТО (27-й круг):** рост ELF приложения выше ~4.6 КиБ ронял его в ring 3 ещё до первого вывода (`#PF`, `cr2=0`). Причина — ошибка копирования страниц в `elf_load`: для страниц ПОСЛЕ первой источник брался без вычитания `inoff`, то есть данные сдвигались ровно тогда, когда RX-сегмент переходил во вторую страницу (порог между 4224 и 4656 байтами). Фикс — 25-й круг; в 26-м я ошибочно решил, что он «не объясняет баг». Доказательства 27-го круга: (1) побайтовое сравнение — байты ELF, которые видит ядро (файловое смещение 4480), совпали с файлом на хосте, значит чтение из KengaFS было верным и порча происходила именно при загрузке; (2) приложение с паддингом 4816 байт (RX-сегмент заходит во вторую страницу) с фиксом работает полностью — `ring3 OK`, тики, `mkdir`, шесть строк паддинга. Фикс `POP_GPRS` (12-й круг) это НЕ лечит — баг отдельный; воспроизводится на 4656 и 4848 байтах, при 4224 работает. Проверена и исправлена ОДНА ошибка в `elf_load` (страницы после первой копировались со сдвигом на `inoff` — круг 25), но она этот баг НЕ объясняет: на 4.6 КиБ ни один сегмент приложения ещё не пересекает границу страницы. Причина остаётся открытой; `cr2=0` и `rip` в коде приложения. **Замеры 26-го круга:** у рабочего образа (4224 Б) точка входа `0x201df0` лежит внутри RX-сегмента (`0x201190..0x201e12`, одна страница); порог падения — между 4224 и 4656 Б, то есть ровно когда RX-сегмент переходит во ВТОРУЮ страницу (0x202000). Файловые смещения и vaddr сегментов конгруэнтны по модулю 0x1000 (`off=0x190`, `vaddr=0x201190`), поэтому формула копирования страницы k>0 обязана вычитать `inoff` — это и исправлено в 25-м круге. Но падение воспроизвелось и с фиксом, значит у бага есть вторая причина: следующий шаг — собрать приложение ~4700 Б и проверено в 27-м круге и подтвердило фикс. Обходной путь для строк, собранных в рантайме: `k_rt_len` в рантайме приложения (встроенный `len()` на таких строках даёт 0). Дальше: `open`/`mmap`, idle-задача. **Открытый вопрос (29–30 круги):** часть вывода приложения иногда пропадает из UART (`kenga-ap`, нет маркеров дескрипторов), а гейты, которые печатает ядро, проходят. Версия «ядро пишет в 0x3F8 не глядя на готовность передатчика» **проверена и отклонена** — добавление ожидания `LSR.5` привело к зависанию и полной потере вывода, откачено. **Вывод 32-го круга (важно для методики):** проверка `LSR.5` перед записью в UART (31-й круг) — правильная практика для железа, но в QEMU она НЕ устраняет потери: QEMU сообщает `THRE` готовым сразу и всё равно дропает байты при быстрой записи. Это видно по тому, что даже строка `saved /apps/state.txt` приходит обрезанной, а маркеры, стоящие между двумя напечатанными, пропадают целиком. Значит **вывод приложения через UART не годится как основа CI-гейта**: проверять функции приложения надо по артефакту на диске (как `state.txt`: приложение пишет результат в файл, ядро читает его и печатает — это надёжный, kernel-side вывод), а не по строке в UART. **Дескрипторы (`open`/`read`/`close`, syscalls 27–29): API в ядре есть, применение из приложения не работает.** Отсечено экспериментом (33–34 круги): это не UART, не обработчик `write` и не новый статический буфер (`g_fd_buf` заменён на проверенный `uxfer` — результат тот же; падают ВСЕ гейты приложения, включая `spawn` и сбор статуса ребёнка, которые работали до добавления fd-кода). Область сужена до стороны приложения: объявления `@intrinsic` и обёртки `k_sys_open/k_sys_read/k_sys_close` в рантайме. **Уточнение 37–38 кругов (важно):** изоляция `sys_open` выполнена, и симптом оказался точнее, чем «ломает процесс». После `sys_open` следующий `sys_save("/apps/fd.txt", "open ok", 7)` **создал файл из 7 НУЛЕВЫХ байт** — в UART это выглядит как пустое содержимое, но `fs_read` вернул 7. Значит строка-ЛИТЕРАЛ прочиталась как нули: `ux_from_user` смотрит по `user_pml4`, и либо он перестал указывать на PML4 процесса, либо трансляция читает не ту страницу. Проверено `nm`, что переполнения буфера нет (`g_fd_buf` заканчивается за 32 байта до `g_up_stacks`). **Бисект 39-го круга: `sys_open` САМ ПО СЕБЕ ПРОЦЕСС НЕ ЛОМАЕТ.** Если вызвать его ПОСЛЕДНИМ (после всего, что проверяют гейты), то проходят ВСЕ kernel-side гейты, включая коды завершения обоих процессов — то есть open вернулся, и процесс прожил дальше. Упали только два гейта, которые опираются на UART-вывод ПРИЛОЖЕНИЯ (строки чтения bootlog) — их QEMU и потерял. Отсюда два вывода: (1) виновата связка «open, затем следующий syscall, читающий память пользователя» (в 37-м круге после open литерал прочитался как 7 нулей) — смотреть `user_pml4`/`ux_from_user`; (2) **эти два гейта надо перевести на kernel-side доказательство**: они единственные флейки, потому что зависят от вывода приложения, а не от артефакта на диске. Проверять функции приложения только по артефакту на диске — UART-вывод QEMU дропает. **ПРИЧИНА ДЕСКРИПТОРОВ ЛОКАЛИЗОВАНА (45-й круг):** убрал вызов Kenga-ФС из `fd_open`, оставив саму функцию, — и следующий `sys_save` приложения записал ПРАВИЛЬНОЕ содержимое (штатный гейт `kenga-app wrote: kenga-app was here` прошёл). Значит ломает именно **вызов `k_fs_syscall` из `fd_open`**, а не функция, не буфер и не syscall-путь. Рабочая гипотеза: Kenga-сгенерированный код нарушает SysV ABI (затирает callee-saved регистр); вызов напрямую из `k_syscall_handler` это терпит, а из `fd_open` — нет, компилятор держит там живую переменную. Проверка: сохранить/восстановить `rbx, rbp, r12–r15` вокруг вызова `k_fs_syscall` в `fd_open`. **Подтверждено в 47-м круге:** барьеры `__asm__ __volatile__("" ::: "rbx","rbp","r12","r13","r14","r15")` вокруг вызова исправили порчу — с приложением, зовущим `sys_open` перед записью, штатный гейт `kenga-app wrote:` стал проходить (`kenga-app was here` вместо семи нулей). То есть Kenga-сгенерированный код действительно затирает callee-saved. **Что осталось:** с включённым `sys_open` всё ещё падает гейт `sys_cat` (файл `/apps/cat.txt` пишется ДО `sys_open`, так что это отдельный симптом того же класса). **Итог 51-го круга: у проблемы есть ВТОРАЯ составляющая.** С барьерами уже на обоих путях вызова Kenga-ФС включил в приложении `sys_open` — и хотя запись файла (`kenga-app wrote:`) верна, падают `sys_cat` (возвращает не то: приложение пишет `cat BAD`) и блокирующий `wait`. То есть порча callee-saved доказана и исправлена, но недостаточна: похоже, Kenga-код затирает ещё и общее окружение — кандидаты: флаг направления DF, x87/MMX-состояние, либо статический scratch в рантайме Kenga, общий для вложенных вызовов. Симптом «`cat` вернул ошибку ПОСЛЕ того, как `open` прочитал тот же файл» указывает на общее состояние FS-моста между вызовами, а не на регистры. **Итог 53-го круга: буфер окончательно исключён** (чистый тест с уже стоящими барьерами: `fd_open` через проверенный `uxfer` — `sys_cat` всё равно падает). **Закономерность:** гейт `sys_cat` проходит на чистом дереве и падает в КАЖДОМ эксперименте, где меняется приложение (3 из 3). Значит путь `cat` сам уязвим к той же ABI-проблеме: его call-site вызывает Kenga-код, а барьер стоит ПЕРЕД `if`, а не вокруг вызова, поэтому любая правка приложения меняет распределение регистров — и хрупкий путь ломается случайно. **План (делать в этом порядке):** (1) ввести обёртку `k_fs_bridge(...)`, которая СОХРАНЯЕТ и ВОССТАНАВЛИВАЕТ `rbx/rbp/r12–r15` вручную (inline asm вокруг вызова), и перевести на неё ВСЕ call-site `k_fs_syscall`: ветки `cat`, `save`, `mkdir/rm`, `spawn` и `fd_open`; (2) убедиться, что после этого любая правка приложения не роняет `sys_cat`; (3) только затем включать `sys_open` → `sys_read` → `sys_close` и ставить гейт на дескрипторы. **ЗАМЕР 56-го круга (важно):** при добавлении `sys_open` в приложение ядро печатает `kenga-app cat file: cat BAD` — то есть приложение получило от `sys_cat` НОЛЬ (и записало заглушку), а не испорченное содержимое. Значит ломается не данные, а сам вызов: скорее всего `ux_to_user`/`user_v2p` не транслирует буфер приложения (`rt_buf()`), то есть `user_pml4` в этот момент не тот. `sys_cat` при этом идёт ПЕРВЫМ, ДО `sys_open`, так что причина — не «состояние после open», а что-то, меняющееся при изменении самого приложения (раскладка/адрес `rt_buf()`). **РЕШАЮЩИЙ ЗАМЕР 57-го круга:** напечатал в ветке `cat` четыре значения — `user_pml4`, `dst` (адрес буфера приложения), трансляцию `user_v2p(pml4, dst)` и результат моста. Получено: `pml4=0x1149000 dst=0x214030 pa=0x1161030 n=0xffffffffffffffff` (и аналогично для второго процесса, с другим pml4/pa). То есть **трансляция в порядке** (`pa` валиден, `user_pml4` свой у каждого процесса), а **`k_fs_syscall` вернул −1**. Значит ломается сам вызов Kenga-ФС, а не доступ к памяти пользователя: `fs_read` возвращает −1 либо из-за состояния ФС (`st.ok`), либо из-за неверного пути. **ПРИЧИНА НАЙДЕНА (58-й круг): путь ПУСТОЙ.** Замер в ветке `cat`: `CAT path=[] ok=0x1 rw=0x1` — то есть `ux_copy_str` не получила ни одного символа, `fs_lookup("")` не находит файл, `fs_read` возвращает −1, приложение получает ноль и пишет заглушку. Состояние ФС при этом верное (`ok=1`, `rw=1`), а трансляция буфера проверена в 57-м круге и исправна. Значит **ядро невиновно: приложение передаёт пустой указатель на строку пути**. Это объясняет и «3 из 3»: гейт `sys_cat` падал в КАЖДОМ эксперименте, где менялся код приложения. **ПОПРАВКА 59-го круга:** версия «патч-трамплин» НЕВЕРНА — `scripts/patch-kenga-user.py` патчит только заглушки `println_*`, а `sys_cat` идёт через обычную C-обёртку `k_sys_cat` в `kenga_user_rt.c`, ровно как `sys_save`, который при этом работает. **Следующий шаг (одна сборка):** напечатать в ветке `cat` значение `user_v2p(user_pml4, path_uva)` — то есть трансляцию адреса СТРОКИ ПУТИ (в 57-м круге так проверялся буфер назначения, и он транслировался). Если страница литерала не транслируется — виновата раскладка/загрузка `.rodata` приложения (`elf_load`), если транслируется, но байт там ноль — виновата сторона приложения (адрес литерала). **КОРЕНЬ НАЙДЕН (60-й круг):** замер дал `CAT pathuva=0x20300c ppa=0x115000c bytes=0x0 0x0 0x0 0x0` — адрес строки пути транслируется в валидную страницу, но **все байты там нулевые**, и оба процесса передают ОДИН И ТОТ ЖЕ адрес `0x20300c` (константа из ELF). Этот адрес лежит ВНЕ загруженных сегментов: rodata-сегмент кончается на `0x202fff`, RW-сегмент начинается с `0x203c90`, а страницу `0x203000` загружает RW-сегмент — байты ниже его начала остаются нулями. Значит ядро невиновно полностью: приложение ссылается на строку, которой в образе нет. **Следующий шаг:** собрать приложение и посмотреть `llvm-readelf -l` (какие диапазоны покрывают PT_LOAD и где литерал пути), а также проверить, не режет ли `scripts/elf-shrink.py` файл раньше конца данных сегментов. Чинить надо раскладку/упаковку приложения, а не ядро. **ПОДТВЕРЖДЕНО readelf (61-й круг):** `LOAD 3: off=0xe22 vaddr=0x202e22 filesz=0x1de` (rodata, данные ЕСТЬ) и `LOAD 4: off=0x1000 vaddr=0x203000 filesz=0` (RW, данных НЕТ). Строка `bootlog` в файле присутствует (grep=1), то есть лежит в rodata ниже `0x203000`. А приложение передаёт `0x20300c` — адрес внутри RW-сегмента, где по определению нули. **Значит ссылка на литерал и сами байты разъехались: код ссылается на адрес в сегменте без файловых данных.** Это дефект сборки приложения (`scripts/build-user.sh` / раскладка секций линкером), а не ядра и не KengaFS. **Следующий шаг:** добавить в линковку приложения корректный linker script (или `-z separate-code` / явное размещение `.rodata` в одном PT_LOAD с кодом), собрать и проверить, что адрес литерала попадает в диапазон LOAD с filesz>0. **Что уже исключено (62-й круг):** сгенерированный C КОРРЕКТЕН — в `build/user/kenga_app.c` стоит `k_sys_cat("/system/bootlog.txt", k_rt_buf(), 256)`, то есть исходник и emit-c ни при чём. Линковка идёт дефолтным скриптом lld: `ld.lld -flavor gnu -m elf_x86_64 -nostdlib --gc-sections --strip-all -e _start` (своего linker script нет). Значит расхождение «ссылка на адрес ≠ место данных» создаёт **линкер/раскладка**: проверять `--gc-sections`/`--strip-all` и добавить явный linker script, размещающий `.rodata` в одном PT_LOAD с кодом. Также сверить, что делает `elf-shrink.py` с этим образом (`grep -c bootlog` = 1, файл ровно 4096 = max(offset+filesz) по сегментам). **РЕШЕНО (63–64 круги):** линковка приложения переведена на `--no-rosegment` — R и RX теперь в одном PT_LOAD с файловыми данными (было 4 сегмента, стало 2: `LOAD 0 R E filesz=0xf90` код+rodata, `LOAD 1 RW filesz=0` только .bss). После этого **`sys_open` включён в приложении и все гейты зелёные** (cat, dir, rm, spawn, wait, exit-коды) — то есть хрупкость «любая правка приложения ломает sys_cat» устранена как класс, а API дескрипторов разблокирован. **ЗАВЕРШЕНО (65–70 круги):** дескрипторы `open`/`read`/`close` (syscalls 27/28/29) работают из ring-3 приложения: оно открывает `/system/bootlog.txt`, читает порциями по 4 байта до конца, закрывает дескриптор и кладёт итог в `/apps/fd.txt`; ядро читает файл и печатает `kenga-app fd file: read ok 15`. Гейт стоит на всех трёх x86-платформах (pc/AHCI/NVMe) и добавлен вместе с гейтом `sys_cat`. **ФС-API приложения закрыт целиком:** cat (16), save (17), mkdir (18), rm (19), open/read/close (27/28/29) — всё проверяется kernel-side артефактами. **74-й круг:** реализован `sys_kill` (30) — `up_kill(pid, code)` в ядре + `k_sys_kill` в рантайме; помечает процесс завершённым, поэтому код читается через `wait_status`. **Вызывающего из приложения пока нет — реализации без теста в дереве быть не должно:** следующий шаг — детерминированная проверка (родитель порождает ребёнка и убивает его ДО первого запуска, затем `wait_status`; гейт `userapp exit pid=0x67 code=0x89`). **75-й круг: `sys_kill` проверен end-to-end** — приложение порождает ребёнка и убивает его до первого запуска; ядро печатает `userapp exit pid=0x67 code=0x89` (137), гейт проверяет эту строку. В ядре emit-c компилирует ТОЛЬКО `kmain.kenga` (`scripts/build.sh:45`), а остальные модули подключаются его директивами `import "ui.kenga";`, `import "desktop.kenga";`, `import "fs.kenga";` (первые строки kmain.kenga). Значит новый Kenga-драйвер подключается ОДНОЙ строкой `import "kf_ec.kenga";` в kmain.kenga — без правок сборки. Рецепт из 78-го круга относится к user-приложению, а не к ядру. **83-й круг:** проверка через QEMU `-d unimp,guest_errors -D log` дала ПУСТОЙ лог (0 строк) — то есть QEMU не пожаловался ни на одно нераспределённое обращение к портам. ## Сеть: что нужно для колец RX/TX (найдено, 97-й круг)

Для дескрипторных колец e1000 нужна DMA-память и её ФИЗИЧЕСКИЕ адреса:
- `@intrinsic fn mem_palloc() -> i64;` — объявлен в `kernel/kmain.kenga` (стр. 24),
  возвращает HHDM-адрес выделенной страницы (4 КиБ);
- `k_mem_virt_to_phys(int64_t)` в C (`kernel/kf_mem.c:150`, объявление `kf_rt.h:59`) —
  переводит HHDM-адрес в физический; именно физические адреса кладутся в RDBAL/TDBAL;
- на x86 DMA когерентен (то же допущение, что для AHCI: см. `kf_ahci.c:12`);
- дескрипторы e1000 — по 16 байт, массивы должны быть выровнены (страница из palloc подходит);
- QEMU e1000 = Intel 82540EM: регистры RDBAL 0x2800, RDLEN 0x2808, RDH 0x2810, RDT 0x2818,
  RCTL 0x0100; TDBAL 0x3800, TDLEN 0x3808, TDH 0x3810, TDT 0x3818, TCTL 0x0400.

Внимание при реализации: объявления `@intrinsic` в Kenga нельзя дублировать между модулями
без последствий (проверено на `asm_inb`), а инлайн порт- и mmio-интринсиков порождает
локальные переменные — один вызов на функцию. `mem_palloc` объявлен в kmain.kenga, поэтому
код колец безопаснее размещать там же либо проверить видимость из импортируемого модуля.

## Сеть: где именно застряла передача (107-й круг)

- `TDH=1` (дескриптор прочитан устройством) — НЕ означает, что кадр ушёл;
- наш ARP-кадр до сетевого бэкенда НЕ доходит;
- `RDH=0` и статус приёмного дескриптора `st=0` — ответа не могло быть по определению:

## Сеть: окончательная диагностика передачи (109-й круг)

Ключевой факт: **статус дескриптора передачи `txds=0`** — бит DD (Done) не выставлен,
то есть устройство НЕ завершило отправку. Это собственный отчёт контроллера, независимый от
внешнего дампа трафика, и он СОВПАЛ с пустым pcap. Два независимых инструмента говорят одно:
кадр не уходит.

Что проверено и отклонено за круги 104-109 (повторять НЕ надо):
1) сетевой бэкенд — ни при чём (с `-nic user` то же);
2) длина кадра — добит до 60 байт, не помогло;
3) содержимое кадра — собрано hex-литералами, ethertype 0x0806 верен;
4) дескриптор передачи — чтение из кольца: адрес буфера верный (`txd0=18509824`);
5) TCTL — приведён к штатному 0x000400FA (CT/COLD), не помогло;
6) трассировка QEMU `-trace enable=e1000*` — недоступна в этой сборке.

Наблюдение, которое ещё не объяснено: TDH=1 при DD=0 — «голова» кольца сдвинулась, но
завершение передачи не зафиксировано. Это указывает на то, что устройство прочитало
дескриптор, но не смогло выполнить DMA данных кадра.

**Следующая проверка (одна, точная):** убедиться, что физический адрес, который мы отдаём
устройству, действительно указывает на ту же память. AHCI с теми же
`mem_palloc`/`mem_virt_to_phys` работает (в CI проходит `DISK RW OK`), поэтому подозрение
смещается к выравниванию/полям дескриптора e1000. Полезно сверить наш TX-дескриптор
(16 байт) с описанием в даташите: addr(8) | length(2) | cso(1) | cmd(1) | status(1) |
css(1) | special(2) — и проверить, что запись `mm_w16` по смещению +8 не затирает +11.


## Сеть: дескриптор передачи проверен ПОБАЙТНО (110-й круг)

Дамп всех полей дескриптора передачи, прочитанных из кольца (то, что видит устройство):
  txd0=18509824   — адрес буфера, младшие 32 бита
  txd1=0          — адрес буфера, старшие 32 бита
  txd2=184549436  = 0x0B00003C  — length=60 (0x3C), cso=0, cmd=11 (EOP|IFCS|RS)
  txds=0          — status=0, бит DD не выставлен

**Дескриптор сформирован идеально.** Адреса колец (RDBAL/TDBAL), длины (RDLEN/TDLEN=128) и
регистры управления (RCTL=0x04008002, TCTL=0x000400FA) подтверждены обратным чтением.
И всё равно устройство не завершает передачу (DD=0) и кадр не покидает машину (пустой pcap).

Ключевое наблюдение: **все регистровые чтения совпадают с записанным, но datapath не
работает.** Это характерно для состояния, когда устройство принимает записи в регистры, но
функционально не инициализировано — например, если последовательность сброса оставила его в
нерабочем состоянии.

**Следующий тест (одна правка):** убрать вызов `e1000_reset` (или добавить паузу после
сброса, как требует даташит e1000: ~1 мс перед любой инициализацией) и повторить дамп
трафика. Если передача заработает — причина в сбросе; если нет — искать дальше в порядке
инициализации (штатный драйвер читает EEPROM и настраивает несколько регистров, которых у
нас нет).


**111-й круг: версия «виноват сброс» ОПРОВЕРГНУТА.** Отключил `CTRL.RST` полностью —
поведение не изменилось: `PCAP=24` (кадр не уходит) и `txds=0` (DD не выставлен). Значит
последовательность сброса не при чём; эксперимент откачен, сброс на месте.

Отклонённых версий стало семь: бэкенд, длина кадра, содержимое кадра, дескриптор, TCTL,
трассировка (недоступна), сброс.

Что осталось: порядок инициализации устройства. Штатный драйвер e1000 до включения колец

параметры CT/COLD, настраивает `CTRL_EXT`/`TIDV`/`ITR`, иногда использует другой порядок
(RCTL/TCTL до колец). Пока не воспроизведён хотя бы EEPROM-шаг, версия остаётся открытой.

Отклонённых версий стало восемь: бэкенд, длина кадра, содержимое кадра, поля дескриптора,

**Что известно точно (проверено побейтно):** кольца и их адреса, длины, все поля дескриптора
передачи (адрес, длина 60, cmd=0x0B, status), регистры RCTL/TCTL/CTRL — всё совпадает с
записанным. Устройство при этом не завершает передачу (DD=0) и кадр не покидает машину.

**Вывод по методу:** программа-минимум драйвера исчерпана — дальше нужен внешний источник
истины: либо исходники QEMU (`hw/net/e1000.c`), либо дамп инициализации от работающего
драйвера. Перебор гипотез вслепую после восьми отклонённых версий неэффективен.


## Сеть: НАЙДЕНА ВЕРОЯТНАЯ ПРИЧИНА — bus-master не включается (113-й круг)

Догадка: для DMA устройству нужен бит BUS MASTER в PCI-команде (регистр 0x04, бит 2). У AHCI
и NVMe его включает их драйвер, а для e1000 этого не делал никто — и без него устройство
физически не может прочитать ни дескриптор, ни данные кадра. Симптом совпадает идеально:
TDH сдвигается (запись регистров работает), DD не выставляется, кадр никуда не уходит.

Что сделано: добавлены `pci_cfg_write32` (запись конфига через 0xCF8/0xCFC) и
`pci_enable_bus_master` (читает команду, пишет cmd|7, читает обратно). Вызывается до
инициализации e1000.

**Измеренный результат: `pci_cmd=258` = 0x102** — то есть биты 0 (IO) и 2 (BUS MASTER)
ОСТАЛИСЬ НУЛЕВЫМИ, хотя записано 0x109. **Запись в конфиг не сохраняется.** Так как чтение
конфига тем же механизмом работает (все идентификаторы верны), проблема именно в записи
или в том, что устройство/модель не принимает эти биты.

Передача при этом не заработала (`PCAP=24`), но теперь есть конкретный, проверяемый
подозреваемый, а не перебор: если bus-master включить, DMA должен заработать.

**Следующий шаг:** разобраться, почему запись команды не сохраняется. Проверить: (1) не
переписывает ли конфиг кто-то позже (например, общий код инициализации PCI в ядре);
(2) не мешает ли запись двойного слова в 0x04 (она захватывает и STATUS 0x06, а запись
единиц в статус гасит биты RW1C) — попробовать писать только слово (16 бит) в 0x04;
(3) сверить с тем, как включает bus-master драйвер AHCI в этом же дереве.

**134-й круг: повторная отправка DNS НЕ помогает — причина в задержке, а не в потерях.**

Проверено пятью прогонами с повторной отправкой (шестой дескриптор, два одинаковых запроса):
во всех пяти dns_a=-1. Для ARP и ICMP повторная отправка решала проблему, здесь — нет.

Объяснение: ARP и ICMP slirp обрабатывает МГНОВЕННО, а DNS он разрешает через резолвер
ХОСТА — это миллисекунды и больше, иногда секунды. Значит ответ приходит ПОЗЖЕ проверки, и
число отправок тут ни при чём: нужна не надёжность доставки, а ДРУГОЕ ОКНО ПРОВЕРКИ.

Что это означает практически: для DNS не годится шаблон «отправить и подождать в конце
загрузки». Нужен либо отдельный, более поздний этап (например, проверка по событию/через
секунду после загрузки), либо асинхронная модель: запрос отправлен, ответ забирается позже,
когда он придёт. Это уже архитектурный шаг, а не правка константы.

При этом сам DNS ДОКАЗАН: дамп трафика показывает наш запрос (вычисленные длины 57 и 37
совпали с принятыми сетью) и корректный ОТВЕТ с id=0x1234, флагом 0x8180 и двумя A-записями;
разбор ответа в ядре проверен на удачном прогоне (dns_a=7341576 = 8.6.112.0).

Повторная отправка откачена, чтобы не плодить дублирующиеся запросы впустую.


## Сеть: полный стек работает и покрыт девятью проверками (137-й круг)

Итог по сети на Kenga (всё без C, логика на Kenga):
  PCI (перечисление, поиск NIC, BAR0, конфиг) -> bus-master ->
  e1000 (MMIO через HHDM, MAC, сброс, линк SLU, кольца RX/TX с DMA) ->
  ARP (запрос и разбор ответа) -> ICMP echo (пинг, сверка данных) -> UDP -> DNS (разрешение имени).

Гейты в CI (pc, а сетевая часть — на всех трёх x86-конфигурациях):
  cmd_word=7        PCI COMMAND = IO|MEMORY|BUS MASTER (команда пишется СЛОВОМ)
  txds=1            устройство завершило отправку кадра (DD в дескрипторе)
  rxlate=7          кадр принят целиком (DD|EOP)
  rxd2=64           принят ARP-ответ нужной длины
  arpmac=677202     MAC шлюза разрешён и разобран
  cksum_selftest=0  контрольные суммы верны (САМОПРОВЕРКА по свойству суммы)
  ping_rdh=3        эхо-ответ получен
  ping_payload=136  в ответе ВЕРНУЛИСЬ НАШИ байты
  dns_ok=1          ИМЯ РАЗРЕШЕНО

**Главная находка всей сетевой части:** PCI-команду нужно писать СЛОВОМ (16 бит), а не
двойным словом. Запись dword не сохранялась, bus-master не включался, устройство не могло
делать DMA — и это десять кругов выглядело как «непонятное поведение устройства» при
безупречном программном пути (регистры читались обратно верно, дескрипторы были корректны).

**Про задержки (трижды дорого):** ARP и ICMP slirp обрабатывает мгновенно, DNS — через
резолвер ХОСТА. Поэтому для DNS не годится шаблон «повторная отправка»: причина была не в
потерях, а в задержке. Решение — АСИНХРОННОЕ ожидание (опрос кольца внутри функции).
Правило: прежде чем применять знакомое решение, убедиться, что причина та же.

**Про гейты:** гейтить конкретный адрес DNS нельзя — slirp отдаёт две A-записи, и в кольцо
попадает любая. Гейтится ФАКТ (dns_ok=1). Три раза подряд гейт ставился слишком рано (ARP,
ICMP, DNS) — правильный порядок: сначала встроить надёжность, потом гейтить; трёх удачных
прогонов для вывода о детерминированности НЕДОСТАТОЧНО.

**Проверено на 137-й круг:** x86_64 — четыре гейта + девять сетевых зелёные; aarch64 — сборка
без ошибок (BUILD64=0) и SMOKE OK на свежем ядре.


## Сеть: проверки оказались ПРИВЯЗАНЫ К КОНФИГУРАЦИИ (139-й круг)

После устранения таймаут-флака (138-й круг) я повторил выравнивание покрытия — добавил гейты
`ping_payload=136` и `dns_ok=1` на AHCI- и NVMe-smoke. Результат: ТРИ прогона подряд упали с
ОДНОЙ И ТОЙ ЖЕ ошибкой:
  ERROR: ICMP payload mismatch on AHCI config
Одинаковая ошибка во всех прогонах означает, что это НЕ флак, а настоящее различие конфигураций.

Причина: проверки разбора читают ФИКСИРОВАННЫЕ СЛОТЫ приёмного кольца — `arpmac` берёт слот 0,
`ping_type`/`ping_payload` — слот 2 (смещение +32). Это было верно для конфигурации pc, где
порядок кадров сложился так: два ARP-ответа, затем два ICMP-ответа. На q35 порядок иной, и в
слоте 2 оказывается не тот кадр.

Это ТА ЖЕ ошибка, которую я уже исправил для DNS: там разбор ищет кадр ПО ПРИЗНАКУ (порт
источника UDP = 53), а не по номеру слота, и потому работает. Здесь поиск ещё не сделан.

**Правильное исправление (следующий шаг):** проверять не слот, а признак —
- `arpmac`: найти кадр с ethertype 08 06 и opcode 00 02 (ARP-ответ);
- `ping_type`/`ping_payload`: найти кадр с IP proto = 1 (ICMP) и type = 0 (эхо-ответ),
  затем сверить данные на смещении 42 найденного кадра.
Это делает проверки независимыми от конфигурации и порядка кадров, и только после этого их
можно ставить на все три smoke.

Покрытие пока НЕ выровнено: правка откачена (три прогона красные), гейты остаются на pc-smoke,
где они проходят стабильно.

## Найден гейт, который проходил ПО СОВПАДЕНИЮ (141-й круг)

Переведя разбор ARP на поиск по признаку, я получил ошибку на AHCI: `ARP resolution failed`.
Откат вернул зелёное — и это показало важное: на конфигурации q35 слот 0 содержит кадр, у которого
байты 22-25 случайно равны 677202, но который НЕ является ARP-ответом (иначе поиск, требующий
ethertype 0x0806 и opcode 0x0002, его бы нашёл).

**То есть гейт `arpmac=677202` на AHCI- и NVMe-smoke проходил ПО СОВПАДЕНИЮ, а не потому, что ARP
действительно разрешался.** Это ложноположительный гейт — самый опасный вид: он даёт зелёный
сигнал, не подтверждая работу. Обнаружить его удалось только потому, что я заменил разбор на
строгий (проверка ethertype и opcode), и старый критерий перестал совпадать.

**Что это означает для тех кругов:** добавление сетевых гейтов на AHCI/NVMe (круги 120, 138) было
преждевременным. На q35 ARP-ответ не попадает в кольцо надёжно (тайминг иной, чем на pc), и
проверка там держалась на совпадении байтов.

**Правильное решение (следующий шаг):** либо снять сетевые гейты с AHCI/NVMe и оставить их
только на pc (где они подтверждены строгим разбором), либо сначала обеспечить на q35 надёжное
получение ARP (повторная отправка там уже есть — значит дело в чём-то другом, надо смотреть лог
q35 с диагностикой). Второй путь честнее: тогда покрытие можно выровнять по-настоящему.

Строгие функции поиска (`e1000_arp_mac`, `e1000_icmp_payload`) оставлены в дереве — они верны и
именно они вскрыли совпадение. На pc они дают ровно те же значения, что и старый разбор
(arpmac=677202, ping_payload=136).


## Сеть: работает на ВСЕХ конфигурациях; исправлена неверная запись 141-го круга (145-й круг)

**Поправка к разделу 141-го круга.** Там я записал, что гейт `arpmac` на AHCI/NVMe «проходил по
совпадению байтов», и снял его. Это НЕВЕРНО. Настоящая причина была в моём новом коде: условие
поиска кадра `if st == 7` (ожидались флаги DD|EOP) слишком строгое — на конфигурации q35 статус
принятого кадра равен 1 (только бит DD). Поиск отвергал ВАЛИДНЫЕ кадры, а я приписал это старому
гейту и снял корректную проверку.

Исправлено на `if (st & 1) == 1` во всех трёх функциях поиска. После этого все конфигурации дают
одинаково верные значения:
  pc:   arpmac=677202  ping_payload=136  dns_ok=1
  AHCI: arpmac=677202  ping_payload=136  dns_ok=1
  NVMe: arpmac=677202  ping_payload=136  dns_ok=1

Гейты ARP, ICMP и DNS возвращены на AHCI и NVMe — теперь покрытие выровнено ОБОСНОВАННО (по
совпадению значений на трёх конфигурациях), а не по одному удачному прогону, как в 120-м круге.

**Урок (шестой источник ошибок за сессию):** когда новая, более строгая проверка что-то
опровергает, надо СНАЧАЛА убедиться, что она сама верна. Здесь ошибка нового кода была принята за
изъян старого гейта, и верная проверка была снята.

**Проверено:** x86_64 — четыре гейта + девять сетевых на трёх конфигурациях; aarch64 — сборка без
ошибок (BUILD64=0) и SMOKE OK на свежем ядре.

## TCP: РУКОПОЖАТИЕ ЗАВЕРШЕНО И ПОДТВЕРЖДЕНО (153-й круг)

  ack_0000fa02 = 1        — поле ack нашего ACK (00 00 FA 02) присутствует в захвате

  our_ports_30394bbb = 3  — кадры от 12345 к 19387

взаимная согласованность полей обеих сторон.

**Итог: TCP-рукопожатие пройдено полностью и проверено по дампу — SYN, SYN-ACK и наш ACK.**

hex-строку, по которой обычный grep находит последовательности, включая содержащие нулевые байты
(обычный grep по бинарному файлу с \x00 неудобен).


## Сеть: стек доведён до HTTP (155-й круг)

**Работает и проверено (логика целиком на Kenga, без C):**
  PCI (перечисление, NIC, BAR0, конфиг) -> bus-master ->
  e1000 (MMIO через HHDM, MAC, сброс, линк SLU, кольца RX/TX с DMA) ->
  ARP (запрос и разбор ответа) -> ICMP echo (пинг со сверкой данных) ->
  UDP -> DNS (разрешение имени) -> TCP (рукопожатие) -> HTTP (запрос и ОТВЕТ СЕРВЕРА).

Доказательства: девять гейтов на трёх конфигурациях плюс разбор дампов трафика; для HTTP —
поиск конкретных байтов запроса (`GET `) и ответа (`HTTP`) в захвате.

**Находки, которые стоили больше всего времени:**
1. PCI-команду надо писать СЛОВОМ (16 бит): запись двойным словом не сохраняется, bus-master не
   включается, DMA невозможен. Десять кругов это выглядело как «непонятное поведение устройства».
2. Приёмный статус кадра проверять по БИТУ DD (`st & 1`), а не равенством 7: на q35 статус иной.
3. Ответ slirp на DNS приходит с задержкой (резолвер ХОСТА) — нужен отдельный, более длинный
   цикл ожидания, а не повторная отправка.
4. Кольцо передачи было на 8 дескрипторов, а код писал девятый — он выходил за кольцо и
   ИГНОРИРОВАЛСЯ, при зелёных гейтах (проверялись регистры, а не отправка).

**Класс ошибок, повторявшийся семь раз: проверка подтверждала настройку, а не работу.**
Лечится только поиском конкретных данных в артефакте: байты кадра в дампе, ответ сервера, поле
ack в SYN-ACK. Гейты на регистрах и на «функция вернула ноль» этого не ловят.

**Проверено:** x86_64 — четыре гейта + девять сетевых на трёх конфигурациях; aarch64 — сборка без
ошибок (BUILD64=0) и SMOKE OK на свежем ядре.

**Осталось по сети:** разбор HTTP-ответа в ядре (как сделано для DNS) и взятие seq собеседника из
принятого SYN-ACK вместо константы (сейчас 0x0000FA01 зашит).


## TCP: как получить ack из peerseq — вывод, чтобы не путаться (157-й круг)

`e1000_tcp_peer_seq` возвращает СЫРОЙ dword из памяти (little-endian), а seq в TCP — число в СЕТЕВОМ
порядке. Это разные вещи, и на этом легко ошибиться.

Пример из дампа (кадр SYN-ACK, смещение 38):
  байты в памяти: 00 00 FA 01
  как little-endian dword: 0x01FA0000 = 33161216  <- это то, что печатает peerseq
  как сетевое число (b0*2^24 + b1*2^16 + b2*2^8 + b3): 0x0000FA01 = 64001

Нужен ack = сетевое число + 1 = 0x0000FA02 = 64002, и его надо положить обратно в кадр байтами
00 00 FA 02, то есть little-endian dword = 0x02FA0000 = 49938432.

Порядок действий:
1. разложить сырой dword на байты b0..b3 (b0 — младший байт dword, он же ПЕРВЫЙ байт кадра);
2. собрать сетевое число n = b0*16777216 + b1*65536 + b2*256 + b3;
3. n = n + 1 (переносы обрабатываются автоматически);
4. разложить n обратно: n0 = n/16777216, n1 = (n/65536) - n0*256, n2 = (n/256) - (n/65536)*256,
   n3 = n - (n/256)*256;
5. упаковать в память как n3*16777216 + n2*65536 + n1*256 + n0.

Проверка на примере: b0=0, b1=0, b2=250, b3=1 -> n = 250*256 + 1 = 64001 -> n+1 = 64002 ->
n0=0, n1=0, n2=250, n3=2 -> dword = 2*16777216 + 250*65536 + 0 + 0 = 49938432 = 0x02FA0000,
то есть байты 00 00 FA 02. Верно.

Сейчас в коде ACK и GET по-прежнему используют ЗАШИТУЮ константу 0x02FA0000 (как и было в кругах
152-154), а peerseq только печатается. Замена — механическая, но требует этой арифметики, и делать
её надо с проверкой по дампу, а не на глаз.


## Сеть: стек доведён до работающего HTTP-КЛИЕНТА (162-й круг)

**Что работает (логика целиком на Kenga, без C):**

**Семь находок, которые стоили больше всего времени (все — про метод, а не про знания):**
1. PCI-команду писать СЛОВОМ: dword не сохраняется, bus-master не включается, DMA невозможен

4. кольцо передачи было на 8 дескрипторов, код писал девятый — он игнорировался при зелёных гейтах;
5. приёмные дескрипторы не возвращались устройству — кольцо заполнялось, ответы отбрасывались;

## Сетевой API для приложений: отрицательный результат и что из него следует (165-166 круги)

**Что пробовал:** приложение (ring 3) читает /apps/net.txt обычным sys_cat и пересохраняет
прочитанное — попытка отдать сетевые результаты без новых сисколлов, через файл-артефакт.

**Что получилось:** в логе `net app: net BAD` — приложение получает пустой ответ.

**Почему (архитектурная причина):** приложение стартует РАНЬШЕ сетевого блока загрузки. Установлено
ещё в 125-м круге по строкам лога (приложение — 72, сетевой блок — 109) и подтверждено здесь с
другой стороны: файл, записанный ПОСЛЕ работы приложения, оно прочитать не может по определению.

**Вывод о приёме:** файл-артефакт годится, чтобы подтвердить, что сделало ЯДРО, но НЕ для передачи
данных приложению. Это ограничение самого приёма, а не ошибка в коде.

**Два пути к настоящему сетевому API:**
1. Выполнять сетевую работу ДО запуска приложений (перенос блока в загрузке). Просто, но привязывает
   порядок загрузки к сети и не допускает повторных запросов.
2. Сделать сисколл: приложение просит — ядро выполняет — приложение получает ответ. Правильнее:
   не зависит от порядка загрузки, допускает повторы, и это тот же механизм, что уже работает для
   файлов (sys_cat/sys_save) и процессов (spawn/wait).

Гейт на этот факт не поставлен — проверка не могла пройти по построению. Правка в дереве оставлена
как документированный эксперимент: печатает "net BAD" и ничего не ломает.

**Полезный побочный результат:** у Kenga-API записи вид `fs_write(fs, путь, строка)`, причём строку
можно склеивать с числами ("net http=" + nethttp) — форматирование не нужно. Это пригодится для
любых отчётов ядра в файл.


## Сетевой API: точный план переноса (168-й круг)

Установлено по `kmain.kenga`:
  - сетевой блок (печатает `PCI dev0=...`, `dns_ok=`, `http_code=`, `net file:`) начинается
    около строки 399;
  - чтения файлов-артефактов идут ниже, до `net file:` на строке 544;
  - запуск приложения лежит ВЫШЕ сетевого блока (приложение стартует раньше — установлено в 125-м
    круге по логам и подтверждено в 165-м).

**План (один перенос, без сисколла):** переместить сетевой блок ВЫШЕ запуска приложений — сразу
после монтирования ФС и её самопроверки, но ДО `user_spawn_*`. Тогда:
1. ядро выполнит сетевую работу и запишет /apps/net.txt;
2. приложение запустится уже ПОСЛЕ и сможет прочитать файл обычным sys_cat (код в дереве уже есть,
   он сейчас печатает "net BAD");
3. гейт `net app: net http=401` станет осмысленным (сейчас он не мог пройти по построению).

**Риски переноса:** сетевой блок содержит длительные ожидания (DNS — до 20 тыс. итераций опроса,
HTTP — столько же). В начале загрузки они задержат запуск приложений, поэтому после переноса
ОБЯЗАТЕЛЬНО перепроверить, что окно smoke (25 с) по-прежнему покрывает загрузку — иначе снова
получим обрезанный лог и посторонние ошибки гейтов (как в кругах 138 и 160).

**Почему это хуже сисколла:** порядок загрузки становится значимым, повторный запрос из приложения
невозможен, и время загрузки растёт. Но это на порядок дешевле и даёт работающую проверку прямо
сейчас; сисколл (с мостом C<->Kenga для состояния драйвера) остаётся правильной долгосрочной целью.


## Сетевой API: более простой путь вместо переноса блока (173-й круг)

План 168-го круга (перенести сетевой блок ВЫШЕ запуска приложений) требует перестановки ~150 строк
в 500-строчном файле и перепроверки окна smoke. Есть заметно более простой вариант, найденный при
разборе порядка загрузки.

**Идея: запустить приложение ВТОРОЙ раз — уже ПОСЛЕ сетевого блока.**

Порядок в загрузке сейчас: … -> запуск приложения -> планировщик (приложение отрабатывает) ->
сетевой блок -> чтения файлов-артефактов. Приложение не видит /apps/net.txt, потому что сеть
работает позже (круг 165). Но если после сетевого блока добавить ЕЩЁ ОДИН запуск приложения и
прогон планировщика, то второй экземпляр увидит файл — и код, который сейчас печатает "net BAD",
сработает как задумано.

Что нужно:
1. найти точную форму запуска в kmain (интринсики user_spawn_blob / user_spawn_vfs и запуск
   планировщика) — одну строку;
2. вставить после сетевого блока повторный запуск и прогон планировщика;
3. убедиться, что чтения файлов идут ПОСЛЕ этого (они и так ниже по файлу);
4. перепроверить окно smoke: второй прогон приложения добавляет время, а сетевые ожидания уже
   выяснялись как дорогие (круги 138, 160).

Почему это лучше переноса: правка — вставка нескольких строк вместо перестановки большого блока,
порядок существующих шагов не меняется, а значит риск сломать загрузку кратно ниже.

Ограничение то же: это демонстрация доступности данных для приложения, а не API (нет повторных
запросов и зависимости от момента). Настоящий API — сисколл с мостом C<->Kenga.


## НАЙДЕН ДЕФЕКТ: слоты процессов не переиспользуются (177-й круг)

**Где:** `kernel/kf_user.c`, функция `up_register` (строка 648):
```c
static int64_t up_register(uint64_t pml4, uint64_t entry) {
    if (g_up_count >= UP_MAX || !pml4 || !entry) return 0;
    int i = g_up_count++;          /* <-- ТОЛЬКО РАСТЁТ, никогда не уменьшается */
```
**Что это значит:** индекс слота берётся как монотонно растущий счётчик, а не как первый свободный.
Слот завершённого процесса (state = 3) НИКОГДА не освобождается, а `pid = 100 + i` растёт вместе с
ним. После UP_MAX запусков регистрация отказывает: `up_register` возвращает 0, и spawn молча не
удаётся. Именно это в 175-м круге дало `run2 begin pid=0` и два круга неверных объяснений.

`state`: 1 — готов, 2 — ожидание/спит, 3 — завершён. Ноль обозначает свободный слот, но нигде не
выставляется обратно.

**Точное исправление (две части):**
1. в `up_register` искать СВОБОДНЫЙ слот, а не брать следующий:
```c
    int i = -1;
    for (int k = 0; k < UP_MAX; k++) { if (g_up[k].state == 0) { i = k; break; } }
    if (i < 0) return 0;
    if (i + 1 > g_up_count) g_up_count = i + 1;   /* граница для циклов по слотам */
```
2. освобождать слот в момент, когда код завершения ЗАБРАН родителем (в реализации sys_wait), а не
   сразу при выходе: иначе `sys_wait` может прочитать уже переиспользованный слот и вернуть чужой
   код. Это важно — в приложении есть проверка `wait_status == 137` (убитый ребёнок), и преждевременное
   освобождение сломает именно её.

**Почему это дефект ОС, а не помеха эксперименту:** таблица исчерпывается за конечное число
запусков, после чего система не может породить ни одного процесса. Для долгоживущей ОС это отказ
ключевой функции.

**Следствие для текущего состояния:** UP_MAX поднят с 4 до 8 (круг 175), что лишь отложило проблему.
Поднятие числа — не исправление; исправление — переиспользование слотов.


## Уточнение к дефекту слотов: причина точнее, чем казалось (178-й круг)

Читая `up_kill`, `up_child_status`, `up_exit_current` и комментарии рядом, выяснилось, что поведение
БЫЛО ЗАДУМАНО таким:

  /* Статус ребёнка: его код, если он уже завершился, иначе -1 (опрос).
     Записи завершённых процессов живут до конца k_user_sched_run. */

То есть запись завершённого процесса СОЗНАТЕЛЬНО не освобождается сразу — иначе родитель не смог бы
прочитать код через wait_status (в приложении это проверка wait_status == 137 у убитого ребёнка).

**Но запись не освобождается и в конце `k_user_sched_run`, хотя комментарий обещает именно это.**
Вот где настоящая причина: `g_up_count` не сбрасывается при завершении прогона планировщика, поэтому
следующий прогон начинается с уже израсходованной таблицей. В 175-м круге именно это и убило второй
запуск приложения (pid=0).

**Это меняет исправление и делает его МЕНЬШЕ, чем планировалось в 177-м круге.** Не нужно трогать
`up_register` и не нужно освобождать слоты при выходе (это сломало бы wait-статусы). Нужно ровно одно:
в конце `k_user_sched_run` сбросить таблицу — `g_up_count = 0` и обнулить состояния слотов. Прогон
закончился, статусы больше никому не нужны, следующий прогон стартует с чистой таблицей.

**Следствия:**
- UP_MAX 8 (поднятый в 175-м круге лишь как обход) перестаёт быть нужен — хватает исходных 4;
- батчи приложений можно запускать сколько угодно раз подряд, таблица не исчерпывается;
- wait-статусы продолжают работать, потому что сброс происходит ПОСЛЕ прогона, а не в момент выхода.

**Что помешало применить сразу:** попытка прочитать функцию `k_user_sched_run` целиком в этом круге
не дала текста (срез по смещению вернул пустое), а применять правку вслепую в C-коде планировщика
без запаса контекста я не стал — цена ошибки здесь выше, чем выгода от спешки.


## Сброс таблицы процессов: исправление РАБОТАЕТ, но требует парной правки (179-й круг)

Применил предсказанное в 178-м круге исправление — сброс таблицы в конце `k_user_sched_run`
(`for k: g_up[k].state = 0; g_up_count = 0;`) — и ВЕРНУЛ UP_MAX с 8 обратно к 4, чтобы проверить, что
слоты действительно переиспользуются.

**Проверка подтвердила исправление:**
  run2 begin pid=100            — повторный запуск состоялся ПРИ UP_MAX=4, то есть слот 0 был
                                  переиспользован (раньше при 4 слотах spawn возвращал 0);
  net app: net http=401 ...     — приложение по-прежнему получает сетевой результат.

**НО вылезла связанная проблема, и гейт её поймал:** во всех трёх прогонах упало
  ERROR: sys_sleep returned before its deadline

Причина: `up_sleep_current` начинается с защиты «если будить некого — не спим вовсе, чтобы не встать
намертво»:
```c
    if (g_up_count < 2 || g_up_cur < 0 || g_up_cur >= g_up_count) return 0;
```
После сброса таблицы второй прогон приложения состоит из ОДНОГО процесса, `g_up_count == 1`, и защита
срабатывает: sleep возвращается мгновенно. Первый прогон при этом спит нормально.

**Значит правки должны идти ПАРОЙ:** сброс таблицы + пересмотр защиты в сне. Защита писалась против
«встанем намертво», но на самом деле ждать есть кого — таймер, который разбудит (в up_pick_wait стоит
hlt именно до таймерного прерывания). Правильнее опираться на наличие таймера, а не на число
процессов.

**Откатил обе правки**, чтобы не оставить красное дерево: исправление дефекта и обход UP_MAX=8
вернулись к прежнему состоянию. Следующий шаг — сделать обе правки вместе и проверить оба гейта
(и сон, и повторный запуск).

Ценно здесь то, что связанность вскрылась СРАЗУ: гейт на сон существовал и сработал. Без него
исправление выглядело бы полностью успешным, а деградация сна осталась бы незамеченной.

## Таблица процессов: дефект исправлен и подтверждён (180-181 круги)

**Было:** `up_register` брал слот по монотонно растущему счётчику (`int i = g_up_count++`), а записи
завершённых процессов не освобождались никогда. Таблица исчерпывалась за конечное число запусков,
после чего регистрация молча отказывала (`up_register` возвращал 0). В 175-м круге это дало
`run2 begin pid=0`.

**Стало (парная правка, порознь не работает):**
1. сброс таблицы в конце `k_user_sched_run` — состояния в 0, `g_up_count = 0`. Статусы завершённых
   процессов нужны только ВНУТРИ прогона (родитель читает код через wait_status), поэтому wait не
   страдает;
2. в защите сна убрана опора на ЧИСЛО процессов (два места). Разбудить может ТАЙМЕР — `up_pick_wait`
   стоит на hlt именно до таймерного прерывания; со старым условием `g_up_count < 2` одиночный
   процесс не спал вовсе.

**Проверено:** UP_MAX возвращён с 8 к исходным 4 — повторный запуск приложения состоялся (`pid=100`,
слот 0 переиспользован), приложение прочитало сетевой результат, три прогона подряд EXIT=0, все
четыре гейта сборки и 18 сетевых проверок зелёные; aarch64 — сборка без ошибок и SMOKE OK.

**Методический итог этой истории (пять кругов):**
  175 — диагностика показала `pid=0`, то есть МЕХАНИЗМ НЕ СРАБОТАЛ;
  177 — дефект найден чтением кода (растущий счётчик слотов);
  178 — причина уточнена по комментарию рядом: нет сброса МЕЖДУ прогонами (правка стала меньше);
  179 — исправление проверено, вскрыта парная зависимость через существующий гейт сна;
  180 — обе правки вместе, проверка на UP_MAX=4.
Два круга (173-174) ушли на неверную теорию о порядке загрузки, потому что я объяснял РЕЗУЛЬТАТ,
не убедившись, что механизм запускался вообще. Различение «не сработало» и «сработало, но дало не то»
— самый дешёвый диагностический вопрос из всех, что здесь применялись.


## Устойчивость исправления планировщика: пять прогонов (183-й круг)

Исправление таблицы процессов проверено ПЯТЬЮ прогонами подряд, а не тремя:
  run1=0 run2=0 run3=0 run4=0 run5=0   (ALLOK=1)
и в каждом повторный запуск приложения состоялся при UP_MAX=4 (`run2 begin pid=100` — слот 0
переиспользован, а не новый).

Правило «трёх удачных прогонов недостаточно для вывода о надёжности» появилось в этой сессии после
трёх случаев, когда гейт ставился слишком рано. Здесь проверка усилена сознательно: правка касается
ПЛАНИРОВЩИКА, где ошибка проявляется не сразу, а при накоплении процессов.

Итог: дефект закрыт, механизм переиспользования слотов ведёт себя стабильно и предсказуемо.


## Сетевой сисколл: разведка интерфейса FS-моста (184-й круг)

Чтобы сделать `sys_net` (приложение просит — ядро отвечает), не нужно писать работу с диском
заново: в C-части уже есть готовый мост в Kenga-логику ФС. Найденное:

- внешняя функция: `extern int64_t k_fs_syscall(int64_t ino, int64_t bmp, int64_t io, int64_t dat,
  int64_t rw, int64_t ok, ...)` (строка 296); вся логика ФС остаётся в Kenga;
- вызовы моста из C: строки 417-419 (запись?), 448-450 (чтение с maxlen), 463-466, 475-477;
- отдельная ГЛАВНАЯ точка (строка 575-581) — похоже на самостоятельный помощник чтения файла по
  пути; именно её удобнее всего переиспользовать для `sys_net`:
```c
if (!uxfer || !&k_fs_syscall) return -1;
...
int64_t n = k_fs_syscall(ux_ino, ux_bmp, ux_io, ux_dat, ux_rw, ux_ok, ...);
```

**План реализации (следующий шаг, три правки):**
1. в C добавить обработчик нового номера сисколла, который вызывает ту же точку, но с ФИКСИРОВАННЫМ
   путём `/apps/net.txt` — приложению не нужно знать имя файла;
2. объявить интринсик в `user/kenga_app.kenga` и обёртку `k_sys_*` в `user/kenga_user_rt.c`
   (по образцу существующих);
3. в приложении заменить `sys_cat("/apps/net.txt", ...)` на новый вызов и поставить гейт.

**Важно про порядок:** сисколл НЕ решает проблему момента — файл всё равно создаётся сетевым блоком
позже первого запуска приложения. Сейчас её обходит повторный запуск приложения после сети (круги
173-175, закреплён гейтом `net app: net http=401`). Настоящее решение — чтобы ЯДРО выполняло сетевую
работу по запросу приложения; для этого нужен мост C->Kenga уже к СЕТЕВОМУ коду (состояние драйвера:
bar0, кольца), а это существенно больше работы и требует аккуратности с ABI (порча callee-saved,
круг 47).

Разведка сделана чтением, без правок: в C-коде планировщика и моста при исчерпанном контексте менять
вслепую не стал.

## Сетевой сисколл: реализован и подтверждён на обеих платформах (186-187 круги)

**Что сделано:** приложение вызывает `sys_net(buf, len)` (сисколл 31) и получает сетевой результат,
не зная ни имени файла, ни устройства. Путь `/apps/net.txt` знает только ядро.

Три слоя, согласованные по ABI:
  ядро (kf_user.c): `net_status(uva, maxlen)` через мост k_fs_syscall (операция 16 — та же, что у
    cat и fd_open); логика ФС остаётся в Kenga;
  рантайм (kenga_user_rt.c): `k_sys_net(dst, max)` — int 0x80, rax = 31, rdi = буфер, rsi = длина;
  приложение (kenga_app.kenga): `@intrinsic fn sys_net(dst: i64, max: i64)` и вызов вместо
    sys_cat("/apps/net.txt", ...).

**Почему с первого раза:** ABI прочитан, а не угадан — номер в rax, аргументы в rdi/rsi/rdx ровно
соответствуют f[5]/f[4]/f[3], которые читает диспетчер ядра. ABI-барьеры вокруг вызова Kenga-кода
сохранены (иначе затираются callee-saved — урок круга 47).

**Проверено:** x86_64 — три прогона подряд EXIT=0, в логе `net app: net http=401 dns=4534024`;
aarch64 — сборка без ошибок (BUILD64=0) и SMOKE OK.

**Честная граница достигнутого:** сисколл убрал зависимость от ИМЕНИ ФАЙЛА, но НЕ от ПОРЯДКА
ЗАГРУЗКИ. Ядро выкладывает результат после сетевой работы, поэтому приложение запускается второй раз
(круги 173-175). Чтобы приложение могло спросить сеть В ЛЮБОЙ момент, ядру нужно выполнять сетевую
работу по запросу — для этого нужен мост C->Kenga к самому сетевому коду (состояние драйвера: bar0,
кольца RX/TX). Это следующий крупный шаг.


## Сетевой API без моста C->Kenga: запрос от приложения (191-й круг)

Задача «сетевая работа по запросу» казалась требующей моста C->Kenga к драйверу (состояние bar0,
кольца) — это много работы и риск с ABI. Но есть путь проще, и он даёт ЧЕСТНУЮ семантику запроса,
не переписывая драйвер.

**Идея: приложение оставляет ЗАЯВКУ, ядро её исполняет.**

Сейчас порядок такой: приложение отрабатывает -> ядро делает сетевую работу (безусловно) ->
приложение запускается ВТОРОЙ раз и читает результат. Работа выполняется независимо от того, нужна
ли она приложению, — это и есть главное отличие от API.

**Что предлагается:**
1. приложение ПЕРВЫМ действием пишет файл-заявку /apps/net.req (обычным sys_save — механизм есть);
2. ядро после первого прогона ПРОВЕРЯЕТ заявку: если файла нет — сетевую работу не делает вовсе
   (экономия времени загрузки, а сетевые ожидания дороги — круги 138, 160);
3. если заявка есть — ядро выполняет сетевую работу, выкладывает результат и запускает приложение
   повторно; приложение читает результат сисколлом net (уже работает, круг 186);
4. повторный запуск выполняется ТОЛЬКО при наличии заявки.

**Что это даёт:** взаимодействие становится «приложение просит — ядро отвечает», а не «ядро делает
всегда, приложение потом смотрит». Это честная семантика запроса без единой новой FFI-точки: все
механизмы (файлы, сисколл net, повторный запуск) уже существуют и покрыты гейтами.

**Чего это НЕ даёт:** приложение по-прежнему не может спросить сеть В ЛЮБОЙ момент (только одним
запросом за загрузку) и не может запросить что-то иное, кроме фиксированного /apps/net.txt. Полный
API — по-прежнему мост C->Kenga, и он остаётся правильной долгосрочной целью.

**Оценка объёма:** три правки (заявка в приложении, проверка в kmain, перенос сетевой работы под
условие) плюс гейт на обе ветви: «с заявкой — результат есть», «без заявки — сетевой работы нет».
Вторая ветвь проверяется отдельным прогоном, что требует поддержки в тесте.

## Обёртывание сетевой работы условием: замер вложенности (196-й круг)

Попытка 195-го круга (обернуть сетевую работу в `if nreq > 0 { ... }`) упала на компиляции:
`kmain.kenga:707:38: expected '}'`. Причина была неясна — я вставлял скобку по текстовому маркеру.

**Замер (подсчёт баланса фигурных скобок по строкам, от начала сетевого блока):**
  строка 398 (`uart_puts("PCI dev0=")`)  — баланс 0
  ... весь сетевой блок ...

## Мост C->Kenga для сети: разведка и два пути (204-й круг)

**Что найдено (разведка чтением):**
  - Kenga объявляет внешние функции как `@intrinsic fn имя(...)` -> символ C `k_имя`;
  - C объявляет их как `extern int64_t k_имя(...)`;
  - САМЫЙ ПРОСТОЙ существующий мост — `k_vfs_cat(const char* name, char* out, int max)`
    (три аргумента, без хитростей). Более сложный `k_fs_syscall` с шестью аргументами — не образец;
  - вызовы Kenga из C требуют ABI-барьеров (`__asm__ __volatile__("" ::: "rbx","rbp","r12".."r15")`),
    иначе затираются callee-saved (урок круга 47).

## Путь 1 (полный, дорогой): мост к сетевому коду

Чтобы приложение могло спрашивать сеть В ЛЮБОЙ МОМЕНТ и СКОЛЬКО УГОДНО РАЗ:
1. вынести сетевую работу из тела загрузочного гейта в отдельную Kenga-функцию
   `fn net_do(bar0: i64, txring: i64, rxring: i64) -> i64` (возвращает код HTTP);
2. Kenga-сторона сообщает C состояние драйвера: `@intrinsic fn net_state_set(a,b,c)` -> C-глобалы;
3. в обработчике сисколла `net` (C) вызвать `k_net_do(...)` с ABI-барьерами и вернуть результат
   приложению;
4. для aarch64 — правило в scripts/a64-sed.sed и заглушка (как для прочих новых интринсиков).

Сложность: вынос ~150 строк из kmain — РОВНО та операция, на которой я потерял восемь кругов
(круги 195-201). Делать её надо по заведённому порядку: сначала прочитать участок целиком и построить
структурную карту, затем резать по границам блоков, а не по подстрокам.

## Полный цикл запроса: почему правку нельзя делать по частям (206-й круг)

**Замысел:** превратить нынешнюю одноразовую схему в честный цикл «приложение просит — ядро
обслуживает — приложение подтверждает приём»:
1. приложение, прочитав результат сисколлом net, УДАЛЯЕТ файл-заявку (sys_rm — механизм есть, строка
   22 приложения);
2. ядро оборачивает блок повторного запуска в ЦИКЛ с повторным чтением заявки ВНУТРИ: пока заявка
   есть — обслуживает; пропала — выходит (в лог идёт «net req: none»);
3. приложение, если ему нужно ещё, пишет заявку снова — и цикл обслуживает повторно.

Это даёт настоящую повторяемость: не «один запрос за загрузку», а «сколько попросит, столько и
получит», при этом без моста C->Kenga.

**Почему нельзя сделать половину.** Если добавить только удаление заявки в приложении, ядро её не
увидит и НЕ ЗАПУСТИТ приложение повторно — сломаются сразу два гейта (`net file:` и `net app:`),
потому что результат перестанет доходить до приложения. Проверено рассуждением по порядку шагов:
  прогон 1: приложение пишет заявку -> читает результат (его ещё нет) -> УДАЛЯЕТ заявку -> выходит;
  ядро: заявки нет -> повторного запуска нет -> /apps/netapp.txt не обновляется -> гейт красный.
Значит обе правки (удаление заявки И цикл) должны войти ОДНОЙ правкой, а это структурное изменение
в kmain — того же класса, что дал восемь неудач в кругах 195-201.

**Порядок выполнения (по заведённой дисциплине, чтобы не повторить те восемь кругов):**
1. построить структурную карту участка (только строки со скобками) — как в круге 201;
2. выписать переменные блока и их последние использования (аудит) — как в кругах 196 и 199;
3. править ПО ИНДЕКСУ СТРОКИ, а не поиском подстроки (главная ошибка кругов 195-200:
   indexOf("    }") находил первое совпадение в файле и вставка уходила не туда);
4. собрать и проверить оба гейта, затем прогнать несколько раз.

**Текущее состояние:** дерево чистое (HEAD adaeb3d), 93 проверки в сборке, обе платформы зелёные,
правка круга 201 проверена шестью прогонами. План выше — следующий шаг.

  - функционально ничего не теряется: запросный API работает, гейты с обеих сторон проходят,
    результат доходит до приложения (проверено шестью прогонами в круге 205).
Соотношение выгоды и цены здесь явно не в пользу продолжения подбора.

**Что остаётся правильным путём:** мост C->Kenga к сетевому коду (путь 1 из круга 204). Он даёт то же
самое — запросы в любой момент и сколько угодно раз — но требует ВЫНОСА участка в отдельную функцию, а
не обёртывания. Вынос делается иначе: сначала полное чтение участка, затем перенос целиком (создание
новой функции), и только потом удаление старого места. Пока это не сделано с чистым контекстом,
любые правки в этом участке будут давать то же, что девять предыдущих.

Состояние возвращено к зелёному: правка откачена, дерево чистое, все гейты проходят.

## Следующий шаг: вынос сетевого участка в функцию — порядок без подбора (208-й круг)

Линия «обернуть участок условием» закрыта в 207-м круге. Повторять её подбором бессмысленно: девять
попыток, три отката, причина каждой — инструмент правки не понимает структуру (скобки в строковых
литералах и комментариях мой подсчёт баланса не учитывал).

**Правильный путь — ВЫНОС, и он начинается не с правки, а с чтения.** Точный порядок:

1. ПРОЧИТАТЬ участок целиком (kmain.kenga, примерно строки 399-600) и записать его структуру:
   где начинается и заканчивается сетевая работа, какие блоки вложены, какие переменные объявляются.
   Это тот шаг, который я пропустил восемь раз подряд.
2. СОЗДАТЬ новую Kenga-функцию `fn net_do(bar0: i64, txring: i64, rxring: i64) -> i64` и ПЕРЕНЕСТИ
   в неё сетевую работу (без печатей в UART — они остаются вызывающему). Функция возвращает код HTTP.
3. СООБЩИТЬ состояние драйвера в C: `@intrinsic fn net_state_set(a: i64, b: i64, c: i64)` и тонкая

4. ВЫЗВАТЬ из обработчика сисколла `net` (C): `k_net_do(...)` с ABI-барьерами (иначе порча
   callee-saved, урок круга 47).
5. Для aarch64 — правило в scripts/a64-sed.sed и заглушка, если интринсик x86-only.
6. Только ПОСЛЕ этого удалить старое место в kmain (перестановка «создать-перенести-удалить», а не
   «вырезать-вставить»).

**Проверка на каждом шаге:** сборка x86 и aarch64, затем гейты. Ожидаемый первый ощутимый результат —
на шаге 2-4: приложение просит сеть сисколлом и получает ответ В ЛЮБОЙ МОМЕНТ, без повторного запуска
и без файла-заявки.

**Напоминание о цене ошибок в этом участке:** девять кругов на обёртывание. Правки здесь делать
ТОЛЬКО по индексам строк, полученным из прочитанного текста, и никогда — поиском подстроки.

    разбор кода HTTP; возвращает код (или -1); НИЧЕГО не печатает;

  - C: `net_state_set(bar, rx, tx)` (сохранить состояние) и вызов `k_net_do(...)` из обработчика
    сисколла net — с ABI-барьерами;

Ценность: приложение сможет запрашивать сеть сисколлом В ЛЮБОЙ МОМЕНТ и сколько угодно раз — без
повторного запуска и без файла-заявки. Это и есть то, ради чего затевался вынос.


## Мост C->Kenga: проектное решение с защитой от нулевого состояния (212-й круг)

Функция `net_do` создана и компилируется (круг 211). Прежде чем вызывать её из обработчика сисколла,
надо решить ОПАСНЫЙ вопрос: в какой момент состояние драйвера действительно валидно.

**Опасность:** обработчик сисколла net может быть вызван, когда кольца ещё не инициализированы. Если
передать в `net_do` нули (bar=0, rx=0, tx=0), функции драйвера начнут обращаться к памяти по нулевому
адресу — это порча памяти или падение, а не отказ вызова.

**Решение (трёхслойное):**
1. Kenga-сторона сообщает состояние C-стороне сразу после инициализации колец:
   `@intrinsic fn net_state_set(a: i64, b: i64, c: i64) -> i64` -> C сохраняет в глобалы g_net_bar,
   g_net_rx, g_net_tx. Вызов ставится РЯДОМ с инициализацией (то есть внутри сетевого участка).
2. C-сторона в обработчике сисколла net СНАЧАЛА проверяет состояние: если g_net_bar == 0 — состояние
   ещё не выставлялось, значит живой запрос выполнить нельзя, и обработчик отдаёт приложению то, что
   есть (файл /apps/net.txt), как сейчас. НИКАКИХ вызовов драйвера с нулями.
3. Если состояние валидно — вызов `k_net_do(g_net_bar, g_net_tx, g_net_rx)` с ABI-барьерами, и
   приложению возвращается ЖИВОЙ результат.

**Что это даёт по шагам:** первый прогон приложения (когда сетевой участок ещё не отработал) получает
пустой ответ и, как сейчас, пользуется файлом после повторного запуска; ВТОРОЙ прогон получает живой
результат прямо из сисколла. То есть переход происходит постепенно и без периода, когда что-то
сломано.

**Порядок реализации (по тому же принципу, что сработал в 211-м круге — сначала безопасная часть):**
  a) C: глобалы + `k_net_state_set` + проверка состояния в обработчике (пока без вызова net_do —
     поведение не меняется, проверяется сборка);
  b) Kenga: объявление интринсика и вызов `net_state_set(nbar, rva, tva)` рядом с инициализацией колец;
  c) C: включить живой вызов `k_net_do` под проверкой состояния;
  d) сборка, гейты, затем несколько прогонов.

**Состояние на этот круг:** дерево чистое (HEAD e762acc, шаг «создать» закоммичен), обе платформы
зелёные, функция net_do пока не вызывается — это сознательный промежуточный шаг.

## Шаг (c) моста: живой вызов НЕ СРАБОТАЛ, и вот вероятная причина (215-й круг)

Включил живой вызов `k_net_do` из обработчика сисколла net под проверкой состояния. Результат:
  ERROR: network result did not reach the ring-3 app
  net app: net BAD
то есть сисколл вернул приложению отказ, а приложение честно сообщило, что данных нет.

Состояние при этом было ВАЛИДНЫМ: маркер `net state set bar=0xfebc0000` в логе есть (круг 214),
значит защита пропустила вызов. Следовательно, сама функция `net_do` вернула -1 — сетевая работа не
выполнилась.

**Вероятная причина — АДРЕСНОЕ ПРОСТРАНСТВО.** Обработчик сисколла исполняется, когда активны таблицы
страниц ПРИЛОЖЕНИЯ (ring-3 процесс). Сетевому драйверу нужны: MMIO-окно сетевой карты и страницы
колец. Если они отображены только в ЯДРОВЫХ таблицах (что естественно для kernel-only маппинга
BAR0), то обращения драйвера в этом контексте либо дают ошибку страницы, либо читают мусор — и
функция возвращает -1. Косвенное подтверждение: работа с ФАЙЛАМИ через мост k_fs_syscall в том же
обработчике работает (значит HHDM доступен), а работа с ЖЕЛЕЗОМ — нет.

**Точное решение (известный механизм, уже применяемый в этом коде):**
  1. перед вызовом сохранить CR3 приложения и переключиться на ядровый (в kf_user.c уже есть
     `kernel_cr3 = rd_cr3()` и `wr_cr3(kernel_cr3)` — тот же приём используется вокруг user_enter);
  2. выполнить `k_net_do` в ядровом адресном пространстве;
  3. вернуться на CR3 приложения и продолжить обработчик.
То есть живой вызов возможен, но требует явного переключения адресного пространства — как это сделано
для входа в ring 3.

**Проверять надо так же, как здесь:** печатать в маркер результат `k_net_do` ДО возврата приложению.
Тогда будет видно, дело в вызове (код -1) или в доставке (код есть, а до приложения не дошёл). В этом
круге такой печати не было, и пришлось выводить причину косвенно.

**Состояние:** правка откачена, дерево зелёное, все гейты проходят, приложение получает результат как
прежде (через файл). Шаги (a) и (b) моста остаются в силе и закоммичены.

## Шаг (c): попытка диагностики сорвалась на якоре правки (216-й круг)

Замысел диагностики был безопасным и правильным: выполнять живой вызов `k_net_do`, ПЕЧАТАТЬ его
результат маркером и при неудаче ОТКАТЫВАТЬСЯ на файл. Тогда причина была бы видна в логе, а доставка
результата приложению не сломалась бы — то есть диагностика без риска.

Правка не применилась: одна из вставок не нашла якорь (`old_string not found`), программа прервалась,
а рабочая копия kf_user.c могла остаться в промежуточном состоянии. Правильное действие в такой
ситуации — не выяснять, что успело примениться, а СБРОСИТЬ файл к закоммиченному состоянию и
проверить сборку. Сделано именно так:
  git checkout HEAD -- kernel/kf_user.c
  EXIT=0, net state set bar=0xfebc0000, net app: net http=401
то есть шаг (b) на месте, доставка результата работает, дерево чистое.

**Урок про якоря (третий раз за сессию).** Правки по «кажущемуся» тексту строки срываются, потому что
текст в файле отличается от того, что я помню. Рабочий приём, который уже применялся: СНАЧАЛА прочитать
нужную строку инструментом чтения по номеру, затем подставить в правку ИМЕННО прочитанный текст. Так
были сделаны успешные правки кругов 214 и 215; здесь я снова положился на память — и снова сорвалось.

**Гипотеза про адресное пространство остаётся непроверенной.** Она объясняет провал 215-го круга
(`k_net_do` вернул -1 в контексте обработчика), но прямого замера не было. Проверять её надо ровно так,
как задумано выше: печать результата вызова + откат на файл.

**Состояние:** дерево чистое, обе платформы зелёные (x86 проверен сейчас; aarch64 — в круге 214). Мост:
шаги (a) и (b) закоммичены и работают.

## Переключение CR3 НЕ помогло — гипотеза об адресном пространстве ОПРОВЕРГНУТА (219-й круг)

Проверил объяснение из круга 215 (и подтверждённое косвенно в 218): вокруг вызова `k_net_do` добавлено
переключение CR3 на ядровый и обратно — ровно тот же приём, что применяется вокруг `user_enter`
(`rd_cr3()` -> `wr_cr3(kernel_cr3)` -> вызов -> `wr_cr3(saved)`). Возврат к таблицам приложения сделан ДО
`ux_to_user`, потому что буфер приложения существует только в них.

Результат: `net live code=0xffffffffffffffff` — по-прежнему -1. То есть АДРЕСНОЕ ПРОСТРАНСТВО НЕ ЯВЛЯЕТСЯ
причиной: в ядровых таблицах вызов тоже не работает. Гипотеза опровергнута, правка откачена (не даёт
эффекта, а сложность и риск добавляет).

**Что это меняет:** косвенное рассуждение из круга 218 («файлы работают, железо нет, значит маппинг»)
было правдоподобным, но НЕВЕРНЫМ. Прямой замер снова оказался решающим: одна правка — один ответ.

**Что известно точно (замеры, а не рассуждения):**
  - состояние драйвера до C доходит: `net state set bar=0xfebc0000`;
  - вызов `k_net_do` из обработчика возвращает -1 и в таблицах приложения, и в ядровых;
  - откат на файл работает, доставка результата не страдает (`net app: net http=401`).

**Следующий замер (точный, без гипотез):** вызывать из обработчика НЕ весь `net_do`, а по одной фазе,
печатая результат каждой: сначала `e1000_rdh(bar)` (простое чтение регистра), затем `e1000_ping`,
`e1000_dns`, `e1000_tcp_syn` и так далее. Это покажет, ГДЕ именно цепочка обрывается — на чтении MMIO,
на выделении страниц под кадр или на ожидании ответа. Тогда причина станет фактом, а не версией.

**Состояние:** правка откачена, дерево зелёное, все гейты проходят, приложение получает результат как
прежде. Мост: шаги (a) и (b) работают, (c) ждёт точного замера по фазам.

## Замер по фазам: доступ к железу РАБОТАЕТ, причина в отправке (220-й круг)

Серия замеров из обработчика сисколла net (при валидном состоянии драйвера) дала такой ряд:

  1. `net live code=0xffffffffffffffff` — весь net_do возвращает -1;
  2. `net probe rdh=0x0` — чтение RDH вернуло 0. НЕ решающий замер: 0 правдоподобен для индекса
     головы кольца, поэтому вывод сделать нельзя (и я его не сделал);
  3. `net probe rdlen=0x80` — чтение RDLEN вернуло 128, то есть РОВНО то значение, которое мы сами
     выставляли при инициализации кольца. Это РЕШАЮЩИЙ замер.

**Вывод 1:** доступ к MMIO-регистрам драйвера из обработчика сисколла РАБОТАЕТ. Гипотезы «ядро не
видит железо в этом контексте» и «адресное пространство мешает» — ОПРОВЕРГНУТЫ (вторая ещё и правкой с
переключением CR3 в круге 219).

**Вывод 2:** отказ находится в последующих фазах — тех, что работают с ПЕРЕДАЧЕЙ: построение кадра,
выделение страницы под него (`mem_palloc`), запись дескриптора и продвижение TDT. Наиболее вероятно —
ПОВТОРНОЕ ИСПОЛЬЗОВАНИЕ ДЕСКРИПТОРОВ: функции отправки пишут в ФИКСИРОВАННЫЕ слоты (смещения 96/112/128
в кольце) и выставляют ФИКСИРОВАННЫЕ значения TDT (7/8/9). При загрузке так и было, но при повторном
вызове устройство эти дескрипторы уже обработало, и повторная отправка в те же слоты с тем же TDT
ничего не передаёт — отсюда отказ и -1 в результате.

**Следующий замер (по той же логике «по одной фазе»):** добавить пробу, которая вызывает только
`e1000_ping(bar, tx)` и печатает результат. Если он тоже отказ — проверять `mem_palloc` (выделение
страницы под кадр) и состояние TDT (`e1000_tctl`/`e1000_peek(txring + 8)`). Если ping проходит — причина
в TCP-фазе.

**Методическая заметка про сам замер:** первая проба (RDH) была НЕУДАЧНОЙ по построению — я выбрал
регистр, значение которого неизвестно заранее, и получил 0, который можно трактовать двояко. Решающей
стала проба с ЗАРАНЕЕ ИЗВЕСТНЫМ ожидаемым значением (RDLEN=128). Правило: для проверки доступа надо
читать то, что сам записал, а не то, что неизвестно.

**Состояние:** проба откачена, дерево зелёное, все гейты проходят, приложение получает результат.

## ПРИЧИНА ОТКАЗА ЖИВОГО ВЫЗОВА УСТАНОВЛЕНА: тайминг SYN-ACK (221-й круг)

Замер фазы отправки: `net probe ping=0x3` — РОВНО то же значение, что при загрузке. Значит из
обработчика сисколла работают И чтение регистров (круг 220: RDLEN=0x80), И отправка кадров. Обе
гипотезы (адресное пространство, недоступность железа) опровергнуты окончательно, теперь с двух сторон.

Остаётся последняя фаза, и она объясняет всё. `net_do` делает так:
  ping -> DNS -> SYN -> tcp_peer_seq(rx) -> ACK -> GET -> http_wait.
Но SYN-ACK приходит НЕ МГНОВЕННО. В загрузочном гейте между отправкой SYN и чтением seq работало
ПРИЛОЖЕНИЕ (десятки миллисекунд), и за это время ответ успевал прийти. В `net_do`, вызванном из
сисколла, эти шаги идут ВПЛОТНУЮ: `tcp_peer_seq` читает кольцо сразу после отправки SYN, получает -1,
ACK и GET строятся с неверным seq, ответа на HTTP нет, `http_wait` истекает — и функция возвращает -1.

Это НЕ ошибка доступа и НЕ ошибка обвязки: это СКРЫТАЯ ЗАВИСИМОСТЬ ОТ ВРЕМЕНИ, которая в загрузке была
незаметна, потому что её случайно закрывало время работы приложения. Классический случай, когда
«работает» держится на побочном эффекте.

**Исправление (точное и маленькое):** в `net_do` между отправкой SYN и чтением `tcp_peer_seq` вставить
ОЖИДАНИЕ ответа — опрос кольца, пока seq не станет >= 0, с ограниченным числом итераций (как сделано
для DNS и HTTP). То есть повторить приём, который уже применялся дважды: асинхронное ожидание вместо
надежды на задержку.

**Как проверять:** после правки маркер `net live code=` должен показать 0x191 (401), а не -1. Если
снова -1 — следующим замером проверять, доходит ли SYN-ACK вообще (`tcp_peer_seq` отдельной пробой,
как делалось с RDLEN и ping).

**Состояние:** проба откачена, дерево зелёное, все гейты проходят, приложение получает результат через
файл (откат работает). Мост: шаги (a)(b) готовы, причина отказа шага (c) установлена.

## Ожидание SYN-ACK не помогло: объяснение опровергнуто, идём по фазам дальше (222-й круг)

Проверил объяснение круга 221 (net_do читает seq собеседника раньше, чем приходит SYN-ACK). Для этого:
  - добавлена `tcp_peer_wait(rx)` — опрос кольца, пока seq не станет >= 0 (до 200 тыс. итераций);
  - в `net_do` чтение seq заменено на это ожидание.

Результат: `net live code=0xffffffffffffffff` — по-прежнему -1. То есть ТАЙМИНГ SYN-ACK не является
причиной общего отказа (во всяком случае, не единственной). Правка откачена: она не достигла цели, а
дерево должно оставаться минимальным.

**Что уже установлено замерами (не рассуждениями):**
  - состояние драйвера до C доходит: `net state set bar=0xfebc0000`;
  - чтение регистров из обработчика работает: `net probe rdlen=0x80` (совпало с выставлявшимся 128);
  - отправка из обработчика работает: `net probe ping=0x3` (то же значение, что при загрузке);
  - весь net_do возвращает -1 — и с ожиданием SYN-ACK, и без него.

**Логика дальнейшего сужения.** `net_do` возвращает -1, если отрицателен любой из результатов:
ping, DNS или код HTTP. Ping проверен — работает (0x3). Значит остаются ДВЕ фазы: DNS и HTTP-обмен.
Следующая проба — `e1000_dns(bar, tx, rx)` отдельно, с печатью результата. Если он отрицательный —
причина в DNS-фазе (и, вероятно, в том же классе: ответ резолвера не успевает или приходит в другое
место кольца). Если положительный — остаётся HTTP-обмен, и тогда проверять по шагам TCP.

**Наблюдение про метод:** серия проб (RDLEN -> ping -> далее) сужает область быстро и без гипотез.
Две пробы отсекли два больших класса причин (доступ к железу и адресное пространство), третья —
тайминг SYN-ACK. Каждая проба стоит один круг и даёт ФАКТ вместо версии. Так и надо было с самого
начала: не рассуждать о причинах, а измерять фазы по одной.

**Состояние:** правка откачена, дерево зелёное, все гейты проходят, приложение получает результат

## Сужение дошло до HTTP-фазы: ping, DNS и регистры работают (223-й круг)

Ряд проб из обработчика сисколла net (все с печатью результата):
  `net probe rdlen=0x80`    — чтение регистров РАБОТАЕТ (совпало с выставленным 128);
  `net probe ping=0x3`      — ОТПРАВКА работает (то же значение, что при загрузке);
  `net probe dns=0x6452f08` — DNS РАБОТАЕТ (вернулся адрес A-записи, 0x6452F08);
  `net live code=0xffffffffffffffff` — весь net_do по-прежнему -1.

**Вывод: из четырёх фаз три работают (регистры, отправка, DNS). Отказ находится в ОДНОЙ оставшейся —
HTTP-обмене (TCP: SYN -> seq -> ACK -> GET -> ожидание ответа).**

**Наиболее вероятная причина (версия, требующая замера, а не рассуждения):** повторное использование
ПАРАМЕТРОВ СОЕДИНЕНИЯ. Функции TCP собраны с зашитыми портом источника (12345) и начальным seq
(0x11223344) — а при загрузке соединение с этими же параметрами уже было установлено и завершено. Новый
SYN с тем же портом и тем же seq хост-сервер может счесть ПОВТОРОМ старого сегмента и не отвечать;
тогда seq собеседника не появится, ACK и GET строятся неверно, ответа нет, ожидание истекает — и
net_do возвращает -1. Это согласуется с тем, что при загрузке (первое соединение) всё работает.

**Следующие пробы (по той же схеме, по одной фазе):**
  1. `e1000_tcp_syn` отдельно — ушёл ли SYN (в загрузке он давал 60/успех);
  2. `e1000_tcp_peer_seq` с ожиданием — пришёл ли SYN-ACK; если НЕТ, версия про повтор параметров
     подтверждается, и лечится это СМЕНОЙ порта/seq на каждый запрос, а не ожиданием;
  3. если SYN-ACK приходит — проверять `e1000_tcp_get` и `http_wait`.

**Что дал этот круг по существу:** область поиска сужена с «мост не работает» до «одна из четырёх фаз»,
причём три проверены положительно. Осталась одна, и есть конкретная проверяемая версия причины.

**Состояние:** проба откачена, дерево зелёное, все гейты проходят, приложение получает результат

## Найден ФЛАК: гейт http_code=401 иногда падает (224-й круг)

После отката диагностических проб проверка сборки упала с `ERROR: HTTP response status was not parsed`.
Прогон сразу после неё — и ещё два (всего три) — зелёные: `r1=0 r2=0 r3=0`, `http_code=401` на месте.
Значит гейт ФЛУКТУИРУЕТ.

**Почему это ожидаемо, и почему стало видно именно сейчас.** Вся серия проб (круги 218-224) показала, что
HTTP-фаза держится на тайминге первого соединения: SYN уходит, SYN-ACK приходит не всегда одинаково
быстро, а разбор кода состояния требует, чтобы ответ успел попасть в кольцо до опроса. Если хост-сервер
(локальный GUI) отвечает медленнее обычного, `http_wait` истекает и гейт падает.

**Что с этим делать (записано как задача, не как догадка):**
  1. САМОЕ ПРАВИЛЬНОЕ — устранить причину: параметры соединения сейчас зашиты (порт 12345, seq
     0x11223344), из-за чего при повторных запросах SYN игнорируется как повтор (это доказано в этом же
     круге). Смена порта/seq на каждый запрос сделает поведение воспроизводимым, а не зависящим от того,
     первое это соединение или нет.
  2. Пока причина не устранена — либо увеличить окно ожидания ответа в `http_wait` (с замером времени
     загрузки: оно уже было источником проблем в кругах 138 и 160), либо признать гейт вероятностным и
     перезапускать его при падении. Второе хуже: гейт, который иногда падает, перестаёт быть сигналом.

**Важно про мою реакцию.** Увидев падение, я не стал объявлять регрессию и не полез править код: сначала
проверил ПОВТОРЯЕМОСТЬ (три прогона). Именно так и надо поступать с любым одиночным падением — в этой
сессии уже был случай (круг 141), когда поспешный вывод из одного наблюдения привёл к снятию ВЕРНОГО гейта.

**Состояние:** дерево чистое, гейты зелёные (три прогона подряд), причина отказа живого вызова
установлена и записана (повтор параметров соединения).

## Исправление повтора параметров: соль должна быть ОБЩЕЙ (225-й круг)

Причина отказа установлена замером (круг 224): зашитые порт источника (12345) и начальный seq
(0x11223344) делают повторный SYN похожим на повтор старого сегмента, и сервер не отвечает. Лечение —
делать параметры соединения РАЗНЫМИ на каждый запрос.

**Первое, что приходит в голову, и почему это НЕ работает.** Взять «соль» из адреса выделенного кадра
(`mem_palloc()` возвращает разные страницы) и вывести из неё порт и seq прямо внутри каждой TCP-функции.
Просто и без изменения сигнатур — но НЕВЕРНО: `mem_palloc` вызывается в КАЖДОЙ из трёх функций
(SYN, ACK, GET), поэтому «соль» у них окажется РАЗНОЙ, порты разойдутся, и рукопожатие не соберётся.

**Правильный проект:** соль вычисляется ОДИН раз на запрос и передаётся во все три функции:
  1. `net_do` получает дополнительный параметр `salt`;
  2. внутри `net_do` он передаётся в `e1000_tcp_syn(bar, tx, salt)`, `e1000_tcp_ack(bar, tx, peer, salt)`,
     `e1000_tcp_get(bar, tx, peer, salt)`;
  3. в каждой из них: порт источника = 12345 + (salt % 1000), начальный seq для SYN = salt (для ACK и GET
     seq уже производный от принятого SYN-ACK, менять его не нужно — важен только ПОРТ, чтобы сегменты
     одного соединения были узнаваемы);
  4. запись порта в кадр — в СЕТЕВОМ порядке: значение `mm_w16` = (порт % 256) * 256 + (порт / 256);
  5. источник соли — C-сторона: счётчик вызовов в `net_live` (0, 1, 2, ...) либо младшие биты времени
     работы. Счётчик проще и детерминирован.

**Откуда берётся соль в загрузочном гейте.** Там `net_do` вызывается впервые, поэтому достаточно передать
любое фиксированное значение (например, 0) — первое соединение всегда уникально. Менять надо только
живой путь.

**Как проверять:** маркер `net live code=` должен стать `0x191` (401) вместо -1, а проба `net probe peer=`
должна давать значение, а не -1. Если peer появляется, а код всё ещё -1 — сужать внутри HTTP-фазы
(GET и ожидание ответа).

**Заодно это снимет флак гейта `http_code=401`** (круг 224): сейчас он держится на том, что первое
соединение уникально, и падает, когда хост отвечает медленнее.

**Почему это не сделано в этом круге:** правка затрагивает три функции TCP и добавляет параметр в
`net_do`, то есть четыре связанные правки в участке, где каждая ошибка стоит круга. Проект записан
целиком, включая ловушку с «солью из адреса кадра», чтобы следующая попытка не повторила её.


## Соль из времени: правка не прошла компиляцию (226-й круг)

Реализовал элегантный вариант исправления повтора параметров: соль берётся из времени работы
(`time_uptime_ms() / 5000`). Идея была в том, что внутри ОДНОГО запроса все три функции (SYN, ACK, GET)
вычисляют одно и то же значение (запрос длится миллисекунды), а между РАЗНЫМИ запросами значения
различаются (они секунды друг от друга) — то есть порт совпадает там, где нужно, и отличается там, где
нужно, БЕЗ изменения сигнатур.

Правка применена механически: объявление интринсика, затем в трёх функциях замена зашитого порта
(в двух местах найдено по 3 вхождения) и зашитых seq (1 и 2 вхождения). Замены применились.

Сборка упала. Точную причину я НЕ зафиксировал (в grep не попала строка ошибки) — и это моя ошибка
в организации проверки: перед откатом надо было прочитать причину, а не только факт падения.

**Наиболее вероятная причина (по опыту этого кода): Kenga требует объявлять переменные В НАЧАЛЕ функции.**
Я вставил `let salt` и `let sport` в середину тел, где уже есть операторы. Если так, правка должна быть
перестроена: объявления — первой строкой функции, присваивания — на месте.

**Что остаётся в силе:** причина отказа установлена замером (повтор порта/seq), и проект исправления
записан целиком (круг 225), включая ловушку с mem_palloc. Осталось уточнить форму реализации под
требования языка.

**Урок про откат.** Я откатил правку, не выяснив причину: сработала привычка «вернуть зелёное». Это
правильно как рефлекс, но НЕПОЛНО: причину надо фиксировать ДО отката, иначе следующий круг тратится на
повторение той же ошибки. Впредь: сначала прочитать ошибку компилятора и записать её, затем откатывать.

**Состояние:** правка откачена, дерево зелёное, все гейты проходят.

`build/uart.log` после прогонов, часть которых УПАЛА (там был `r2=1`), и видел ОСТАТКИ логов предыдущих
запусков — то есть значения `0x191` были не результатом этих прогонов, а артефактом чтения не того файла.

**Как надо было измерять:** каждый прогон должен был сохранять свой лог отдельно (копией), а не полагаться
на общий `uart.log`, который переписывается и может остаться от предыдущего запуска при падении сборки.
Это тот же класс ошибок, что «устаревший ELF» (круг 94) и «обрезанный лог» (круг 138): ИНСТРУМЕНТ
ИЗМЕРЕНИЯ не проверили прежде, чем делать вывод.

**Что это меняет по существу:** живой вызов отказывает УСТОЙЧИВО. Значит:
  - серия проб (круги 218-224) была НЕ напрасной: регистры, отправка и DNS действительно работают (их
    значения невозможно получить из чужого лога — они уникальны для состояния драйвера);
  - отказ находится в четвёртой фазе — TCP/HTTP;
  - версия «повтор параметров соединения» НЕ проверена: проба `net probe peer=` давала -1, но её тоже надо
    перепроверить с раздельными логами, прежде чем строить на ней исправление.

**Следующий шаг (с исправленным измерением):**
  1. каждый прогон сохраняет СВОЙ лог (cp uart.log build/run-N.log) перед следующим;
  2. проба TCP (syn + ожидание peer) повторяется на нескольких прогонах;
  3. только после этого делается вывод о фазе и причине.

**Урок (третий раз за серию, в третий раз в новой форме):** прежде чем объяснять результат, надо
убедиться, что САМ РЕЗУЛЬТАТ получен корректно — что файл тот, что прогон тот, что сборка прошла.

## Чистое измерение фазы TCP: SYN уходит, ответа нет, воспроизводимо (229-й круг)

Замер сделан НОВЫМ инструментом (`scripts/measure.sh`, раздельные логи прогонов, круг 228). Результат
двух прогонов:
```
run1: probe syn=0x3c | probe peer=0xffffffffffffffff | net live code=0xffffffffffffffff
run2: probe syn=0x3c | probe peer=0xffffffffffffffff | net live code=0xffffffffffffffff
```
**Отказ ВОСПРОИЗВОДИМ** (2 из 2), и локализован точно:
  - SYN из обработчика УХОДИТ (функция вернула 0x3c — длину кадра, как при загрузке);
  - SYN-ACK НЕ ПРИХОДИТ даже за 200 тыс. опросов кольца;
  - следовательно, живой вызов падает именно на этом шаге.

Это первый замер в серии, которому можно доверять: логи раздельные, прогонов несколько, значения
совпали. Все прежние выводы строились на чтении общего лога и потому были ненадёжны.

## Важное уточнение: что именно доказывает `probe syn=0x3c`

`0x3c` — это ВОЗВРАЩАЕМОЕ ЗНАЧЕНИЕ функции отправки (длина кадра), а НЕ подтверждение, что кадр покинул
устройство. То есть возможны ДВА разных диагноза, и текущий замер их не различает:
  (а) кадр ушёл, но сервер не ответил — тогда причина в параметрах соединения (порт/seq), как
      предполагалось в круге 224;
  (б) кадр НЕ ушёл — тогда причина в передаче (дескриптор, TDT), и приём тут ни при чём.

## Решающая проба (различает (а) и (б) одним числом)

После отправки SYN прочитать СТАТУС передающего дескриптора — бит DD (смещение 12 в дескрипторе), как
это уже делается при загрузке в гейте `txds=1`:
  - DD=1 -> кадр ушёл, значит сервер не ответил => версия (а), лечится сменой порта/seq на каждый запрос;
  - DD=0 -> кадр НЕ ушёл => версия (б), лечится разбором передачи (повторное использование слота
    дескриптора и значения TDT: функции отправки пишут в ФИКСИРОВАННЫЕ слоты 96/112/128 и выставляют
    ФИКСИРОВАННЫЙ TDT, а при загрузке эти слоты уже были использованы).

Практически: добавить в пробу чтение `e1000_peek(txring + 96 + 12)` (статус первого использованного слота
отправки) и напечатать его рядом с `probe syn=`. Одна проба — один ответ, как это уже сработало с RDLEN
(круг 220) и ping (круг 221).

**Состояние:** проба откачена, дерево зелёное. Инструмент замера с раздельными логами в дереве

## РЕШАЮЩИЙ ЗАМЕР: кадр УХОДИТ, сервер МОЛЧИТ — причина в параметрах соединения (231-й круг)

Проба выполнена ИСПРАВЛЕННЫМ инструментом (`scripts/measure.sh`, который теперь отвергает недостоверные
логи и печатает статус сборки). Оба прогона — OK, значения совпали:
```
run1 OK: probe syn=0x3c  probe txdd=0x1  probe peer=0xffffffffffffffff  net live code=0xffffffffffffffff
run2 OK: probe syn=0x3c  probe txdd=0x1  probe peer=0xffffffffffffffff  net live code=0xffffffffffffffff
```

**Читается однозначно:**
  `probe syn=0x3c` — функция отправки SYN отработала;
  `probe txdd=0x1` — БИТ DD УСТАНОВЛЕН, то есть устройство кадр ОБРАБОТАЛО и он УШЁЛ в сеть;
  `probe peer=-1` — ответа на этот SYN НЕ ПРИШЛО (200 тыс. опросов кольца);
  `net live code=-1` — итог живого вызова.

**Вывод: кадр отправляется успешно, а сервер на него не отвечает.** Это ровно вариант (а), отмеченный в
круге 229, и он совпадает с версией круга 224: параметры соединения (порт источника 12345 и начальный
seq 0x11223344) ЗАШИТЫ, и при загрузке с этими же параметрами соединение уже было установлено и завершено.
Новый SYN с теми же портом и seq сервер считает повтором старого сегмента и игнорирует.

**Почему это теперь доказано, а не предположено.** Раньше версия опиралась на косвенные доводы. Сейчас
есть прямой замер: кадр ушёл (DD=1) — значит причина НЕ в передаче, НЕ в доступе и НЕ в тайминге;
остаётся то, что сервер не желает отвечать на такой SYN. Плюс замер воспроизводим (2 из 2) и сделан
инструментом, который сам проверяет достоверность лога.

**Исправление (проект из круга 225, теперь подтверждённый):** делать параметры соединения РАЗНЫМИ на
каждый запрос — соль вычисляется ОДИН раз и передаётся в `tcp_syn`, `tcp_ack`, `tcp_get` (одна соль на все
три, иначе порты разойдутся — ловушка из круга 225). Вариант с солью из `time_uptime_ms() / 5000`, который
не скомпилировался в круге 226, остаётся рабочим по идее, но требует аккуратной реализации (вероятная
причина отказа — объявления переменных в середине функции).

**Что установлено за серию проб (все с чистым воспроизводимым замером):**
  регистры — РАБОТАЮТ; отправка — РАБОТАЕТ (и кадр реально уходит: DD=1); DNS — РАБОТАЕТ;
  приём SYN-ACK — НЕ ПРИХОДИТ из-за параметров соединения.

**Состояние:** проба откачена, дерево зелёное, все гейты проходят

## Соль: правка ПРИМЕНИЛАСЬ ЧИСТО, но СЛОМАЛА загрузочный TCP (236-й круг)

Пятая попытка сделана по всем правилам, выведенным за серию:
  - способ — по прочитанным строкам, без регулярок;
  - перед правкой ПРОВЕРЕНА УНИКАЛЬНОСТЬ каждого якоря (pseudo=3 -> сознательный replace_all;
    заголовок e1000_arp_mac=1; port2==port3 -> replace_all; три строки seq уникальны);
  - после правки прочитан файл обратно: строк 925->942, соль в трёх функциях, порт в трёх, интрисик на
    месте, БАЛАНС СКОБОК 0 (структура цела — впервые за пять попыток!).

Итог по структуре — безупречно. Итог по существу — РЕГРЕССИЯ: три прогона из трёх дали
  `ERROR: HTTP response status was not parsed`
то есть загрузочный HTTP-обмен перестал работать. До правки он давал `http_code=401` стабильно.

**Что это значит.** Причина отказа живого вызова (параметры соединения) была установлена ЗАМЕРОМ верно, но
моя реализация соли ломает то, что работало. Значит в реализации есть ошибка, и её надо искать, а не
подгонять: загрузочный TCP — самый проверенный путь во всей системе (гейты по нему стоят с круга 154), и
если он сломался, то изменилось что-то существенное, а не «просто значение».

**Гипотезы для следующей попытки (в порядке дешевизны проверки):**
  1. источник соли: `time_uptime_ms() / 5000` на момент загрузки может давать НОЛЬ, и тогда порт остаётся
     12345, а seq становится 4660 вместо 0x11223344 — надо проверить, что при этом вообще отправляется;
  2. момент вычисления соли: SYN, ACK и GET вызываются с интервалом в миллисекунды, но граница деления на
     5000 может попасть между ними, и тогда у ACK/GET будет ДРУГОЙ порт — рукопожатие не соберётся;
  3. арифметика seq: `salt * 65536 + 4660` — при больших значениях времени число может выйти за пределы,
     ожидаемые полем, и сервер отбросит сегмент.
Проверять надо по одной, замером (печатать salt, sport и значение seq в кадре), а не рассуждением.

**Что в этой попытке было правильно и что сохранить:** способ правки (по строкам, с проверкой
уникальности и чтением обратно) сработал — структура не пострадала. Проблема оказалась в СОДЕРЖАНИИ
правки, а не в её выполнении. Это прогресс: раньше отказ был в инструменте, теперь — в понимании.

**Состояние:** правка откачена, дерево зелёное (X86=0), загрузочный TCP снова работает

## Соль: арифметика проверена ВРУЧНУЮ и оказалась верной (237-й круг)

Проверил вычисления соли без правок в коде — просто посчитал:
```
порт 12345 -> dword 0x3930 -> байты 30 39    (в точности как зашитое значение 0x3930)
порт 12346 -> dword 0x3a30 -> байты 30 3a
порт 13344 -> dword 0x2034 -> байты 34 20    (сетевой порядок соблюдён)
seq: salt*65536+4660 и salt*65536+4661 различаются ровно на 1 при любом salt (0, 1, 20, 200, 5000)
```
**Обе арифметические гипотезы исключены:**
  - формула порта даёт ровно те же байты, что зашитое значение (значит, при salt=0 поведение
    тождественно прежнему, и «сломанный порядок байт» отпадает);
  - SYN и ACK различаются ровно на 1 — seq корректен.

**Что это даёт.** Отпадают самые вероятные объяснения регрессии круга 236. Остаются:
  1. `time_uptime_ms()` в контексте kf_pci.kenga возвращает не то, что ожидается (например, значение,
     отличное от времени загрузки, или 0 — тогда seq=0x1234 вместо 0x11223344, что само по себе
     допустимо, но меняет поведение);
  2. что-то в САМОЙ ВСТАВКЕ, а не в значениях: `@intrinsic fn time_uptime_ms` был добавлен ПЕРЕД функцией
     `e1000_arp_mac` (в середину файла), а `let salt`/`let sport` — сразу после `let pseudo` во всех трёх
     функциях через replace_all;
  3. разделитель 5000 мс: если граница попадает МЕЖДУ вызовами SYN и ACK, порты разойдутся — но при
     загрузке вызовы идут в микросекундах друг от друга, поэтому маловероятно.

**Как проверять дальше (по одной, замером):** печатать изнутри функции значения `salt` и `sport` — тогда
сразу видно, что именно подставляется. Для этого надо убедиться, что в kf_pci.kenga доступна печать
(интринсики там уже используются: mmio_read, mem_palloc, kf_get_hhdm — значит механизм есть).

**Методическая ценность круга:** проверка арифметики ЗАДАЧЕЙ, а не сборкой, заняла один вызов и исключила
две гипотезы. Это дешевле любого прогона и должно применяться раньше — до правок, а не после трёх неудач.

**Состояние:** дерево зелёное, загрузочный TCP работает (после отката), обе платформы собираются.

    kf_pci.kenga или местом вставки объявления и вычислений, а НЕ самим фактом изменения порта.

Это ровно то разделение, которое следовало сделать ДО пятой попытки: один прогон с чистым изменением
одного параметра отсекает целый класс причин. Стоимость — один круг, тогда как слепое повторение соли
дало бы то же падение и не добавило понимания.

**Следующий шаг (узкий и проверяемый):** в загрузочном пути напечатать значение, которое возвращает
`time_uptime_ms()` из kf_pci.kenga. Если оно ноль или мусор — причина найдена; если нормальное время —
значит дело в самом вычислении `salt`/`sport` (например, в порядке объявлений или в области видимости).

**Почему правка откачена:** она не улучшает систему — порт остаётся постоянным, поэтому живой вызов
по-прежнему сталкивается с соединением загрузки. Ценность была в ИЗМЕРЕНИИ, а не в изменении.

**Состояние:** дерево зелёное, загрузочный TCP работает, обе платформы собираются.

## Соль, попытка 6: причина НЕ в месте объявления, а в ВЫЗОВЕ интринсика внутри функций TCP (240-й круг)

Шестая попытка сделана со всеми выясненными условиями:
  - `@intrinsic fn time_uptime_ms` объявлен В НАЧАЛЕ файла (гипотеза круга 239);
  - уникальность всех якорей проверена ДО правки (first=1, pseudo=3 -> сознательный replace_all, port1=1,
    port2=2, port3=2, seq=1/1/1);
  - после правки прочитан файл обратно: соль в трёх функциях, порт в трёх, интринсик в начале,
    баланс скобок 0;
  - проверка обеих платформ новым скриптом: aarch64 — сборка OK и SMOKE OK.

**Результат по x86 — та же регрессия:** `network result was not written to the FS` и `did not reach the
ring-3 app`, то есть загрузочный HTTP снова не отработал. Значит ГИПОТЕЗА КРУГА 239 ОПРОВЕРГНУТА: место
объявления интринсика ни при чём.

**Что остаётся единственным отличием от успешного теста круга 238** (там я поменял ТОЛЬКО значение порта, и
всё прошло): вызов `time_uptime_ms()` ВНУТРИ функций отправки. Круг 238 не вызывал ничего — только другое
число. Здесь в трёх функциях появился вызов интринсика.

**Наиболее вероятная причина — та самая, что записана в истории этого кода (круг 47): сгенерированный
Kenga-код нарушает SysV ABI и затирает callee-saved регистры (rbx, rbp, r12-r15).** Если вызвать интринсик
посреди функции, значения, которые компилятор держит в этих регистрах (адрес кадра `buf`, адрес `pa`, `pseudo`),
могут быть испорчены — и кадр собирается с мусором. Внешне это выглядит как «сервер не отвечает», хотя
раньше те же самые кадры отправлялись успешно.

**Отсюда правильное решение (оно же было в проекте круга 225, и теперь ясно, ПОЧЕМУ оно такое):** соль
должна ВЫЧИСЛЯТЬСЯ СНАРУЖИ и передаваться В ФУНКЦИИ ПАРАМЕТРОМ. Тогда внутри горячих функций не будет ни
одного вызова интринсика, и порча регистров исключена по построению.

Порядок работ:
  1. добавить параметр `salt: i64` в `e1000_tcp_syn`, `e1000_tcp_ack`, `e1000_tcp_get`;
  2. в местах вызова (загрузочный гейт и `net_do`) вычислять соль ОДИН раз и передавать её;
  3. проверить обе платформы и загрузочный HTTP.

**Полезный побочный результат круга:** новый скрипт `check-both.sh` сразу показал, что aarch64 цел, — то
есть проверка обеих платформ работает и после правки, которая ломает x86.

**Состояние:** правка откачена, дерево зелёное, загрузочный TCP снова работает

## План правки «соль параметром» — точные якоря (241-й круг)

Причина, по которой соль внутри функций не годится, установлена в круге 240: вызов интринсика посреди
горячей функции портит callee-saved регистры (rbx, rbp, r12-r15) — та самая особенность сгенерированного
Kenga-кода, что известна с круга 47. Поэтому соль вычисляется СНАРУЖИ и передаётся параметром: тогда внутри
функций TCP не будет ни одного вызова интринсика.

**Полный список правок (15 операций, все по точному тексту строк):**

```
fn e1000_tcp_ack(bar0: i64, txring: i64, peer: i64)          + , salt: i64
fn e1000_tcp_get(bar0: i64, txring: i64, peer: i64)          + , salt: i64
```
ПОРТ (3 строки, в каждой из трёх функций):

```
mm_w16(buf + 34, 0x3930);   ->   mm_w16(buf + 34, (sport - (sport / 256) * 256) * 256 + sport / 256);
```
SEQ (3 строки):
```
mm_w32(buf + 38, 0x44332211);  ->  mm_w32(buf + 38, salt * 65536 + 4660);   (SYN)
mm_w32(buf + 38, 0x45332211);  ->  mm_w32(buf + 38, salt * 65536 + 4661);   (ACK, GET)
```

ВЫЗОВЫ в kernel/kmain.kenga (6 строк):

```kenga
    let sport: i64 = 12345 + (salt - (salt / 1000) * 1000);
```

  - загрузка использует порт 12345 (как сейчас), работает;

**Порядок и проверки:** править kf_pci и kmain ОДНОЙ правкой (иначе сборка не свяжется: сигнатуры и
вызовы должны меняться вместе); перед правкой проверить уникальность всех 15 якорей; после — прочитать

## РЕШАЮЩИЙ ЗАМЕР: ожидание не при чём — ответ не приходит НИКОГДА (243-й круг)

Замер поставлен так, чтобы полностью исключить ожидание внутри обработчика:
  - на ПЕРВОМ вызове сисколла отправляем SYN и СРАЗУ возвращаемся (никакого опроса);
  - на ВТОРОМ вызове (приложение просит результат ещё раз) проверяем, появился ли SYN-ACK.
Результат:
```
probe1 syn=0x3c                  <- SYN отправлен на первом вызове
probe2 peer=0xffffffffffffffff   <- на следующем вызове ответа ВСЁ ЕЩЁ НЕТ
net app: net http=401 ...        <- приложение результат получает (через откат на файл)
```

**Вывод: гипотеза «мешает ожидание внутри обработчика» ОПРОВЕРГНУТА.** Ответ не приходит вообще, сколько бы
времени ни прошло между вызовами.

**Это сводит картину к одной формулировке:** из обработчика сисколла кадры УХОДЯТ (DD=1, проверено в круге
231), но НИ ОДИН ответ не возвращается; при этом те же самые функции, вызванные в загрузочном гейте,
работают (загрузочный HTTP даёт 401). Разница только в контексте вызова.

**Важное уточнение, которое я обязан сделать про прошлые выводы.** В круге 221 проба `ping` из обработчика
вернула 0x3, и я счёл это доказательством, что «отправка работает». Но 0x3 — это ВОЗВРАЩАЕМОЕ ЗНАЧЕНИЕ
функции (комбинация счётчиков кольца), а НЕ подтверждение, что пришёл ответ. То есть ICMP из обработчика
тоже НЕ проверялся на получение ответа. Возможно, картина общая: из обработчика не возвращается НИЧЕГО.

**Следующий замер (тот же приём, что сработал сейчас):** отправить из обработчика ICMP-echo на первом
вызове, а на втором — проверить, есть ли в кольце кадр с типом 0 (echo reply). Если и его нет, значит
проблема общая для всех протоколов и лежит в том, КАК выглядит исходящий кадр (например, контрольная сумма
или MAC собираются с испорченными значениями — та самая порча callee-saved, круг 47), а не в приёме.

Если же ICMP-ответ придёт, а SYN-ACK нет — разница в TCP-части, и искать надо в конкретных полях сегмента.

**Состояние:** диагностика откачена, дерево зелёное

## НАЙДЕН ВЕРОЯТНЫЙ ВИНОВНИК: e1000_rx_return обрывает приём (244-й круг)

Замер:
```
icmp1 sent=0x3     <- ICMP отправлен ИЗ ОБРАБОТЧИКА
icmp2 reply=-1     <- echo-reply НЕ ПРИШЁЛ
```
При этом в ЗАГРУЗКЕ тот же ping получает ответ — гейты `ping_rdh=3` и `ping_payload=136` проходят,
причём последний сверяет ВЕРНУВШИЕСЯ данные. То есть приём в принципе работает.

**Значит совпадает не «плохой кадр», а МОМЕНТ: всё, что отправляется и принимается ДО определённой точки
загрузки, работает; всё после — нет.** А между ними стоит единственная операция, меняющая состояние приёма:
`e1000_rx_return` (добавлена в круге 160, чтобы «кольцо не заполнялось навсегда»). Она обнуляет байты
статуса всех восьми дескрипторов и ставит `RDT = RDH - 1`.

**Гипотеза, объясняющая ВСЮ картину:** после `e1000_rx_return` кольцо приёма перестаёт принимать кадры.
Тогда:
  - загрузочные проверки (ARP, ping, DNS, HTTP) идут ДО неё и проходят — они и составляют все сетевые гейты;
  - живой вызов из обработчика идёт ПОСЛЕ и не получает ответов ни на SYN, ни на ICMP — ровно то, что мы
    видим в замерах;
  - и это же объясняет, почему «ничего не приходит», хотя кадры уходят (DD=1) и почему загрузка работает.

**Почему это правдоподобно технически.** `rx_return` ставит RDT на один дескриптор ПОЗАДИ RDH. Если в момент
вызова RDH равен нулю (а после обработки всех кадров это так и есть), RDT становится 7 — то есть устройству
объявляются доступными дескрипторы 0..7, включая те, чьи адреса буферов уже отданы. Любое расхождение здесь
приводит к тому, что устройство пишет не туда или не пишет вовсе, а программная часть продолжает опрашивать
байты статуса, которые остаются нулями — что и выглядит как «ответ не пришёл».

**Решающий тест (простой и однозначный):** убрать вызов `e1000_rx_return` из сетевого участка загрузки и
повторить замер ICMP. Ожидания:
  - если ответ придёт — виновник найден, и лечить надо не соль и не тайминги, а ПРАВИЛЬНОЕ продвижение RDT
    (например, возвращать только дескрипторы, которые действительно обработаны, и не трогать статусы);
  - если не придёт — гипотеза отпадает, и остаётся версия «исходящие кадры из обработчика испорчены».

**Почему я не сделал этот тест сразу.** Он требует изменить сам механизм приёма — тот, на котором держатся
девять сетевых гейтов. Делать это при исчерпанном контексте, не проверив сначала гипотезу чтением кода
`e1000_rx_return` и `e1000_rx_enable`, я не стал: цена ошибки здесь — красное дерево и потеря работающего
приёма, а не потеря круга.

**Что важно в этом круге:** впервые появилось объяснение, которое согласуется СО ВСЕМИ замерами
одновременно (кадры уходят, ответов нет, загрузка работает, обработчик — нет, ни TCP, ни ICMP), и которое
проверяется ОДНИМ изменением. Предыдущие версии объясняли лишь часть фактов.

**Состояние:** диагностика откачена, дерево зелёное.

## Чтение e1000_rx_return: гипотеза круга 244 ОСЛАБЛА, но не отпала (245-й круг)

Прочитал `e1000_rx_return` (строка 860) и `e1000_rx_enable` (строка 194). Вот что делает первая:
```kenga
fn e1000_rx_return(bar0: i64, rxring: i64) -> i64 {
    let i: i64 = 0;
    while i < 8 { mm_w8(rxring + i * 16 + 12, 0); i = i + 1; }   /* обнуляем байты статуса */
    let rdh: i64 = mm_r32(bar0 + kf_get_hhdm() + 10256);
    let rdt: i64 = rdh - 1;
    if rdt < 0 { rdt = 7; }
    mm_w32(bar0 + kf_get_hhdm() + 10264, rdt);                  /* RDT позади RDH */
    return rdt;
}
```

**Почему это выглядит КОРРЕКТНО.** `RDT = RDH - 1` — общепринятый приём: устройству объявляются свободными
все дескрипторы, кроме одного (тот самый «зазор», чтобы не путать пустое кольцо с полным). Кольцо приёма
описано на 8 дескрипторов с восемью буферами по 2048 байт — это согласовано. Обнуление байтов статуса —
тоже обычная практика: признак «программное обеспечение забрало кадр».

**То есть с ходу дефекта не видно.** Гипотеза круга 244 («rx_return обрывает приём») объясняла все замеры,
но чтение кода её НЕ подтверждает: операция выглядит правильной. Возможно, она и не виновата.

**Что при этом остаётся верным и ценным из круга 244:** совпадение по ВРЕМЕНИ. Всё, что проверяется до
этой операции, работает (девять сетевых гейтов); всё, что после, — не получает ответов. Это факт, и он
требует объяснения независимо от того, виноват ли конкретно `rx_return`.

**Как проверять дальше — два независимых способа, оба дешёвые:**
  1. ЗАМЕР СОСТОЯНИЯ вместо догадок: напечатать `RDH` и `RDT` ДО и ПОСЛЕ `rx_return`, а также `RDH` в
     момент живого вызова. Если после возврата RDT/RDH стоят так, что кольцо считается полным, — это и есть
     причина, и она будет видна числом, а не рассуждением.
  2. Тест «без возврата»: временно убрать вызов `rx_return` и повторить замер ICMP. Если ответ появится —
     виновник найден; если нет — гипотеза отклонена.
Способ 1 предпочтительнее: он не трогает работающий механизм и сразу даёт числа.

**Методическая заметка.** Круг 244 дал объяснение, которое понравилось мне своей полнотой, — и я почти
принял его за вывод. Чтение кода показало, что операция корректна, то есть полнота объяснения ещё не
означает его правоты. Это третий раз за серию, когда стройная версия рассыпалась при первой же проверке
(«ложный гейт», «адресное пространство», теперь «rx_return»).

**Состояние:** дерево зелёное, ничего не менялось — только чтение.

## Числа кольца приёма: найдена АНОМАЛИЯ в чтении RDH (246-й круг)

Собрал состояния кольца из уже имеющегося лога (правок не требовалось):
```
rdlen=128     длина кольца — 128 байт = 8 дескрипторов                    (верно)
rdh=0         RDH сразу после включения приёма                             (верно)
rdh=15107     RDH в следующей проверке — НЕВОЗМОЖНОЕ значение!             (аномалия)
rdh2=1        RDH позже                                                   (верно)
rdh=3         RDH после пинга                                             (верно)
rx_ret=5      RDT, выставленный e1000_rx_return                           (следствие)
http_code=401 загрузочный HTTP отработал
```

**Что здесь важно.** `RDH` — индекс головы кольца приёма, допустимы значения 0..7 (кольцо на 8 дескрипторов).
Значение 15107 = 0x3B03 в этот диапазон не попадает НИКАК. То есть функция чтения RDH хотя бы один раз
вернула мусор.

**Почему это существенно для нашей задачи.** `e1000_rx_return` вычисляет `RDT = RDH - 1`. Если RDH хоть раз
прочитан как мусор, то RDT выставляется в бессмысленное значение (15106), устройство получает указатель за
пределы кольца и ПЕРЕСТАЁТ писать принятые кадры. Дальше всё сходится с замерами: кадры уходят (DD=1),
ответов нет ни на TCP, ни на ICMP, а всё, что проверялось ДО этого места, работает.

**Оговорка, которую обязан сделать.** В этом конкретном прогоне `rx_ret=5`, то есть в момент вызова
`rx_return` значение RDH было 6 (6-1=5) — правдоподобное. Значит аномальное чтение 15107 произошло в ДРУГОЙ
момент, и напрямую связать его с поломкой приёма пока нельзя. Но сам факт, что RDH может вернуть мусор,
делает версию проверяемой и опасной: любое чтение мусора в этом месте ломает приём необратимо.

**Следующий замер (точный, по одному числу):** печатать RDH непосредственно ПЕРЕД вычислением RDT внутри
`e1000_rx_return` и RDH при каждом последующем обращении (в живом вызове). Тогда будет видно:
  - стабильно ли RDH лежит в 0..7 после возврата;
  - не выходит ли он за диапазон в момент живого вызова;
  - совпадает ли это с прекращением приёма.

**Заодно устранить причину аномалии:** проверить, не читается ли RDH слишком рано (до того как устройство
завершит инициализацию) — тогда достаточно перенести чтение позже, и это безопасная правка.

**Методическая ценность:** аномалия найдена ЧТЕНИЕМ УЖЕ СОБРАННЫХ чисел, без единого прогона. Это второй
случай за серию (после ручной проверки арифметики в круге 237), когда самое дешёвое действие дало самый
конкретный результат.

**Состояние:** дерево зелёное, изменений не вносилось.

## ОПРОВЕРГНУТО: приём ПОСЛЕ возврата дескрипторов работает (249-й круг)

Тест: посл�� `e1000_rx_return` отправить ещё один ICMP-пинг и посмотреть, сдвинется ли индекс головы кольца.
```

rx_ret=5      RDT, выставленный возвратом дескрипторов
ping2=7       второй пинг ПОСЛЕ возврата
rdh3=7        RDH ВЫРОС с 5 до 7 -> приняты ДВА кадра
```

**Кольцо приёма живо после возврата.** Ответ на второй пинг пришёл и был записан устройством. Значит гипотеза
круга 248 («приём умирает после rx_return, потому что кольцо заполнено») ОПРОВЕРГНУТА.

**Что это меняет и что оставляет.** Все версии, связанные с состоянием КОЛЬЦА, теперь отсечены замером:
  - доступ к железу — работает (RDLEN=0x80, круги 220, 231);
  - приём после возврата — работает (этот круг);
  - передача — работает (DD=1, круг 231).
Остаётся ровно одно различие между работающим и неработающим случаем: КОНТЕКСТ ВЫЗОВА. Из загрузочного
гейта всё работает; из обработчика сисколла — ничего не возвращается, хотя кадры уходят.

**Единственная непроверенная версия, которая это объясняет: исходящие кадры из обработчика ИСПОРЧЕНЫ.**
Они покидают устройство (DD=1), но сервер их молча отбрасывает — поэтому нет ни SYN-ACK, ни echo-reply.
Наиболее вероятный механизм — тот, что известен в этом коде с круга 47: сгенерированный Kenga-код
нарушает SysV ABI и затирает callee-saved регистры при вызове из C. Барьеры стоят вокруг ВНЕШНЕГО вызова
(`k_net_do`), но внутри `net_do`, где идёт сборка кадра, значения (адрес буфера, смещения полей) могут
портиться — и тогда кадр уходит с неверной контрольной суммой или адресами, а сервер его игнорирует.

**Как проверить (замер, а не рассуждение):** напечатать из обработчика СОДЕРЖИМОЕ первых байтов
собранного кадра и его контрольную сумму — MAC назначения, ethertype, IP-адреса. Если хоть одно поле
отличается от того, что печатается при сборке в загрузке, версия подтверждается, и лечить надо не сеть, а
передачу данных между C и Kenga.

**Итог по серии (круги 218-249):** шесть версий отсечены замером (адресное пространство, недоступность
железа, тайминг SYN-ACK, параметры соединения, ожидание в обработчике, смерть кольца после возврата).
Осталась одна — и она проверяема печатью полей кадра.

**Состояние:** диагностика откачена, дерево зелёное

сути, и делает нынешний механизм с заявкой и повторным запуском).

## Проверка «позднего ответа»: кириллица попала в код (253-й круг)

Правка (одна печать после второго прогона приложения — решающая проверка гипотезы о продвижении
эмуляции) не скомпилировалась:
```
error at D:/KengaOS/kernel/kmain.kenga:581:8: unexpected character 'с'
```
Символ 'с' — КИРИЛЛИЧЕСКИЙ. Значит многострочный комментарий перед вставленной печатью оказался закрыт
раньше, чем закончился текст, и русские буквы попали в позицию КОДА, а не комментария. Компилятор указал
точную строку и столбец — это и позволило понять причину сразу, без догадок.

**Правило, которое стоит соблюдать в этом коде:** комментарии в Kenga-файлах писать КОРОТКО и следить за
тем, чтобы ни `*/`, ни неожиданное завершение не оставляли текст за пределами комментария. Длинные
многострочные пояснения на русском — самый частый источник таких ошибок, потому что границу комментария
легко потерять глазом.

**Что было готово к проверке.** Гипотеза о том, что из обработчика кадры не доходят до эмуляции сети, а
не «теряются» где-то ещё, проверяется ОДНОЙ печатью: сразу после второго прогона приложения (то есть после
работы обработчика сисколла) посмотреть, не появился ли в кольце echo-reply — функция `e1000_icmp_payload`
ищет именно его и при загрузке возвращает 136 (сумма данных нашего узора).

## ОТВЕТ НА ПОСЛЕДНИЙ ВОПРОС: кадры из обработчика не доходят до сети вообще (255-й круг)

Различающий замер (вставка в СТРОКУ КОДА, окружение проверено чтением ДО сборки — урок круга 254 учтён):
```
late_icmp=-1        <- echo-reply НЕ появился и ПОСЛЕ возврата обработчика
net app: net http=401 ...   <- приложение результат получает (через откат на файл)
```

Смысл: мы отправили ICMP-пинг ИЗ ОБРАБОТЧИКА, а проверили кольцо уже ПОСЛЕ того, как гость вернулся в
основной цикл и загрузка продолжилась. Ответа нет. Значит версия «эмуляция не успевает продвинуться внутри
обработчика, но кадры доходят с задержкой» — ОПРОВЕРГНУТА: при задержке ответ бы появился позже, а его нет.

**Восьмая опровергнутая версия за серию.** Итог:
  1. адресное пространство — нет;
  2. недоступность железа — нет (регистры читаются);
  3. тайминг SYN-ACK — нет;
  4. параметры соединения — нет;
  5. ожидание внутри обработчика — нет;
  6. смерть кольца после возврата — нет (RDH растёт);
  7. испорченные кадры — нет (MAC верный, 0xa5552);
  8. задержка из-за эмуляции — нет (ответа нет и позже).

**Что остаётся.** Кадры уходят (DD=1), поля кадра начинаются верно, кольцо живо — но сеть на них не
отвечает и НИКОГДА. Единственное, что я проверял НЕ ПОЛНОСТЬЮ, — СОДЕРЖИМОЕ КАДРА: я смотрел только его
первые четыре байта (MAC назначения). Остальные поля — IP-адреса источника и назначения (смещения 26 и 30),
контрольная сумма (24), а для ICMP ещё и сумма данных — не проверялись. Если в кадре, собранном ИЗ
ОБРАБОТЧИКА, испорчен, например, адрес источника, сетевой стек хоста молча отбросит кадр — и ответа не
будет ни сразу, ни позже. Это ровно согласуется со всеми восемью замерами.

**Следующий замер (последний по этой линии):** напечатать из обработчика поля кадра по смещениям:
  26 — адрес источника (ожидается 0x0F02000A, то есть 10.0.2.15),
  30 — адрес назначения (ожидается 0x0202000A, то есть 10.0.2.2),
  24 — контрольная сумма IP.
Достаточно ОДНОГО несовпадения, чтобы версия подтвердилась и объяснила всё.

**Почему это стоит проверить именно так.** Первые четыре байта кадра (MAC) оказались верными — значит
сборка кадра ЧАСТИЧНО работает, и порча, если она есть, касается конкретных полей, а не всего кадра. При
этом известно, что вызов Kenga-кода из C может затирать callee-saved регистры (круг 47): если это
происходит В СЕРЕДИНЕ сборки, первые поля (уже записанные) останутся верными, а последующие — испортятся.
Именно такая картина и наблюдалась бы.

**Состояние:** диагностика откачена, дерево зелёное.

## ACPI под UEFI: попытка и точная причина неудачи (258-й круг)

Цель: заставить ACPI работать под UEFI (в BIOS он находится: ACPI READY pm1a=0x604, под UEFI — ACPI NONE).

Причина установлена чтением кода: ac_find_rsdp() в kernel/kf_acpi.c ищет только в legacy-области
0xE0000..0xFFFFF, которой под UEFI нет.

Сделано: добавлен limine_rsdp_request в kernel/start.S (по образцу остальных запросов) и ветка в
ac_find_rsdp, которая берёт адрес у загрузчика. ID запроса сначала был взят по памяти и оказался неверным
(0x27637845accd8e1c вместо 0x27637845accdcf3c) — исправлено по заголовку limine.h. Структуры проверены там
же: response лежит в поле [5], адрес RSDP — по смещению +8 в ответе.

**После исправления ID Limine ответил (поле [5] стало ненулевым), но revision запроса остался 0 — то есть
запрос так и не подтверждён.** Прочитанные значения оказались нечитаемыми: адрес не выровнен на 16,
revision ответа равен нулю.

**Найденная причина:** в x86_64-файле kernel/start.S базовая ревизия Limine объявлена как 0, тогда как в
aarch64-версии (kernel/aarch64/start64.S) — 6. При старой базовой ревизии Limine игнорирует более новые
запросы, поэтому RSDP-запрос не обрабатывается.

**Проверенная попытка исправления:** поднял базовую ревизию до 6 (как в aarch64). Результат — СЛОМАЛСЯ BIOS:
в логе пропали ранние маркеры (INTR READY, INT3, SHELL READY), то есть загрузка под BIOS перестала проходить
в прежнем виде. Правка откачена полностью, состояние возвращено к зелёному: BIOS=0, ACPI READY pm1a=0x604,
дерево чистое.

**Что делать в следующий раз (по шагам, чтобы не потерять круги):**
1. поднимать базовую ревизию не сразу до 6, а последовательно (4, затем 5): возможно, ломается именно
   конкретное значение, а не сам факт повышения;
2. смотреть, что Limine печатает в САМОМ НАЧАЛЕ загрузки при повышенной ревизии — его диагностика
   объясняет отказ лучше, чем последствия в ядре;
3. учесть, что при базовой ревизии 0 работают только старые запросы (framebuffer, memmap, hhdm, module) —
   именно поэтому под BIOS всё работает, а RSDP не появляется;
4. альтернатива, не требующая Limine: под UEFI адрес RSDP есть в EFI System Table, но после выхода из
   boot services он недоступен — значит путь через загрузчик остаётся основным.

**Состояние:** правки откачены, BIOS зелёный, ACPI под UEFI по-прежнему не работает (как и до попытки).

### Продолжение: базовая ревизия Limine — 4 и 6 ломают BIOS (259-й круг)

Проверено последовательно:
  база 4 + RSDP-запрос -> BIOS НЕ грузится (пропадают ранние маркеры: INTR READY, INT3, SHELL READY),
    а поле revision запроса остаётся 0x0 и под BIOS, и под UEFI;
  база 6 + RSDP-запрос -> то же самое (проверено ранее).

То есть: при базовой ревизии 0 Limine игнорирует новые запросы; при 4 и 6 загрузка под BIOS ломается.
Это значит, что дело не в конкретном значении, а в том, что kernel/start.S не соответствует более новому
протоколу Limine: загрузчик либо отказывается работать, либо передаёт управление иначе, чем ожидает наш
ассемблерный вход.

**Правильный путь (следующая задача, отдельная и более крупная):** привести kernel/start.S в соответствие
протоколу Limine для более новой базовой ревизии — то есть разобраться, что именно загрузчик делает иначе
(проверить его вывод в самом начале загрузки, сверить точку входа и передаваемые регистры). Только после
этого RSDP-запрос станет возможен, и ACPI заработает под UEFI.

**Обходной путь, не требующий Limine:** под UEFI таблицы ACPI находятся в памяти, которую прошивка
описывает в EFI System Table; после выхода из boot services прямой доступ к ней теряется, но адрес RSDP
можно получить иначе — например, поиском сигнатуры RSD PTR в диапазонах, которые Limine отдаёт в карте
памяти (memmap-запрос работает и при базе 0). Это менее надёжно, чем запрос к загрузчику, но не требует
менять протокол.

**Состояние:** правки откачены, BIOS зелёный (ACPI READY pm1a=0x604), дерево чистое.
