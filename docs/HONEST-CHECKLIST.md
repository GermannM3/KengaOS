# Честный чек-лист KengaOS — что увидят компании и пользователи

Дата: 2026-09-05 · Версия: v0.7.2 + UI-оболочки · Проверено по коду:
`kenga-lang/` (v3.13), `kernel/`, `src/` (десктоп + мобилка).

## Видение

ОС нового поколения: системный слой написан на языке Kenga (UI — тоже
постепенно), и система «ткёт» пророков в себя — агенты с памятью и
предсказанием (Prophet) работают как часть ОС, а не как приложение.

## ✅ ЧТО РЕАЛЬНО ЕСТЬ СЕГОДНЯ (проверено, не маркетинг)

### Видит пользователь (ISO на ноутбуке / в QEMU)
- Живой рабочий стол **Aurora**: окна с перекрытием, dock, topbar,
  обои с дрейфующим свечением. Логика десктопа — **на Kenga**
  (`desktop.kenga`, 793 строки, `ui.kenga`, `kmain.kenga`), компилируется
  `emit-c --freestanding` и грузится на голое железо.
- **Терминал** с командами, **чат с агентом** (печатает текст — агент
  отвечает через IPC).
- **4 системных агента** как процессы ОС: logger / agent / model /
  researcher — с IPC, правами (capabilities) и очередями. Видны в
  «AGENT SPACE».
- **Модель-агент ONLINE**: настоящий MLP 2-2-1 в ядре, обучен на XOR,
  инференс через IPC с проверкой прав (`CAP_MODEL_INFER`).
- **Магазин**: 6 пакетов `.kpkg` в initrd, установка из input-бара. **v2**
  (`kenga-app.kpkg`) = текстовый манифест + пустая строка + бинарный
  payload; установка целиком на Kenga: пакет читается из initrd, payload
  пишется в KengaFS `/apps/kenga-app.elf` (`install kenga-app.kpkg`),
  старая форма `install a` по-прежнему идёт в C-реестр. Гейт CI
  `STORE INSTALL OK`.
- **Prophet как системный сервис** (v1): `kernel/kf_prophet.c` — память
  эпизодов + ядро паттернов, surprise (RMSE), k-NN foresee; тикает из
  десктопа (`kd_prophet_tick`), прогноз виден в SYSTEM HEALTH.
- **Пророки оболочки, обучающиеся на ходу** (0.8.1, `Prophet.jsx`):
  ассистенты в «Чате»/«Агентах» выучивают пары «учи: вопрос => ответ»
  (память в localStorage, recall по схожести), предсказывают следующее
  приложение (цепь Маркова по открытиям, точность видна в «Мониторе»),
  surprise на неожиданных переходах. Всё локально, общий код десктопа
  и мобилки.
- **Пайпы в шелле ядра** («bash» v1): `echo text | upper | count` —
  конвейеры команд с фильтрами; boot-самотест + CI-гейт `PIPE OK`.
  Полноценный bash = userspace fork/exec (после ring-3 процессов).
- **KengaFS — персистентная ФС на диске** (`kernel/fs.kenga`, целиком на
  Kenga): superblock, битмап блоков, таблица inode (32), дерево каталогов,
  `mkdir -p`, чтение/запись/удаление; файл `/boots` считает загрузки.
  Десктоп показывает карточку **FILES · KENGA-FS** (inode/блоки + список
  файлов из inode-таблицы) и понимает команды в input-баре: `ls`, `df`,
  `cat <path>`, `touch <path>`, `mkdir <path>`, `rm <path>`,
  `write <path> <text>`. Пишем только на диск с маркером `KENGARWTEST1`
  или уже содержащий KengaFS — чужие диски не трогаются. Персистентность
  проверяется двумя QEMU-ботами на одном образе: `fs:boot=1` →
  `fs:boot=2` (`scripts/test-fs-persistence.sh`).
- **Kenga-приложение в ring 3**: `user/kenga_app.kenga` — исходник на
  **Kenga** (`println`, рекурсивный `fib`) — собирается
  `scripts/build-user.sh`: `emit-c --freestanding` → патч заглушек `println`
  в `int 0x80 write` (`scripts/patch-kenga-user.py`) → clang/`ld.lld` → ELF
  (~3.5 КиБ) → initrd → **KengaFS `/apps/kenga.elf`** → `elf_load` → ring 3,
  возврат по `sys_exit`. Работает на загрузке (гейт `USERAPP OK`) и из
  десктопа командой `run /apps/kenga.elf`. CI проверяет **вывод самой
  программы**: `kenga-app: ring3 OK`, `kenga-app: fib(12) = 144`.
  Попутно найден и исправлен баг `elf_load`: игнорировался `filesz`, и в
  `.bss` уезжал хвост файла (аллокатор Kenga-рантайма сразу получал OOM).
- **xHCI USB**: работает в QEMU на обеих архитектурах (тач-планшет,
  ECAM-скан, слоты, CONFIG_EP); на живом железе не проверен.
- **Две архитектуры одним исходником**: x86_64 ISO + aarch64 (QEMU, CI).
- **Каждый коммит** автотестируется: ядро реально грузится в QEMU на
  обеих архитектурах, включая установку пакета и ring-3 запуск.

### UI-оболочки (прототипы на веб-стеке, общий kernel bridge)

Честно: это React/Vite-прототипы поверх симуляции kernel bridge —
контракт тот же, что у ядра (37 `kd_*`); порт в Kenga/C — по `docs/design/design.md`.

- **Десктоп** (v0.8, без заглушек): окна с перекрытием, dock, лаунчер,
  терминал, **браузер** (`kenga://` + внешние сайты), **монитор**
  (графики CPU/RAM), **настройки** (3 темы + 2 обоев), **файлы** (VFS
  с Kenga-исходниками), **агенты** (чат + XOR-предсказания модель-агента),
  **чат-ассистент**, **о системе**.
- **Мобилка** (v0.8, APK на POCO M4 Pro): boot → lock → home → шторка →
  лаунчер; экранная клавиатура **Ру/En**; браузер; терминал (команды
  на русском и латинице); **звонилка с реальными контактами** (нативный
  мост) и вызовом через системный дозваниватель; **реальные SMS**
  (чтение, ответ через системное приложение); **камера** (getUserMedia,
  снимок+сохранение); файлы, агенты, чат, монитор, настройки, о системе.
- Темы — общие для обеих оболочек: Полярная / Синяя волна / Зелёная волна.
- Браузер честно: рендерит движком хоста (iframe) — оболочка пока живёт
  внутри браузера; в будущей ОС это свой движок / порт (Servo-класс).

### Видит разработчик / компания
- **Язык Kenga v3.13** — полноценный: i64/f64/bool/str/list/**Tensor**/
  **Memory**/structs, if/while/for, imports, события (`on "tick"`),
  FFI-интринсики. Компилятор: `kenga run / emit-c / build`, плюс
  **kenga-lite** (C99-хост без Rust) и bytecode-рантайм. VS Code
  расширение, книга, примеры.
- **Prophet/Memory API в языке** (это и есть «пророки»):
  `memory() / learn / predict / foresee / surprise / remember / recall /
  consolidate / save_mind / load_mind` — локальный инференс с памятью
  паттернов, консолидацией во сне (EWC-lite), сохранением разумов
  (`.km`-файлы, совместимы с Rust-хостом).
- **Тензоры + мультимодальность**: `t_matmul / t_sgd_step / load_ppm /
  load_wav` — входы изображений и звука.
- **Единая поверхность ядра** для desktop и mobile:
  37 `kd_*`-функций (агенты, IPC, память, мышь/тач, uptime) — тот же
  контракт, что декларирует `kernel_bridge.kenga`.

## ⚠️ ЧЕГО ПОКА НЕТ (честно)

| Область | Реальность | Что нужно |
|---|---|---|
| **Kenga-программы пользователей** | ✅ исходник **на Kenga** → ring-3 ELF, **упакован в `.kpkg` v2**, ставится из магазина в KengaFS `/apps`, запускается с диска **как процесс** (своя PML4, свой kernel-стек, сохранённый кадр прерывания: `k_user_spawn_blob` + `k_user_sched_run`), **читает (`sys_cat`) и пишет (`sys_save`) файлы**; записанный файл переживает перезагрузку (`kenga-app prev:` на boot 2) | ⚠️ переключение НЕСКОЛЬКИХ процессов: механизм написан, два процесса реально перемежаются (тики pid 100/101 через yield), но при возобновлении кадр портится (#PF в ring 3, в слотах GPR оказываются регистры ядра). **Исключено замерами:** таймер (маскирование IRQ0 не помогает), переполнение kernel-стека (64 КиБ — то же), общий стек (замер входа: rsp = top−304 у каждого процесса, tops в 64 КиБ друг от друга). Остаётся механика возврата через `k_resume_frame` при switch после выхода процесса. Дальше: `open`/`mmap`, вытеснение. **Разбор бага (11-й круг, дамп таблицы inode):** `fs_mkdir` НЕ виноват — после `mkdir` таблица inode корректна (`/`, boots, system, bootlog.txt, tmp, apps, kenga-app.elf, demo). Виноват `sys_save` из приложения: файл `/apps/state.txt` вообще не создавался, а приложение печатало «saved» безусловно. Гейт `kenga-app wrote:` теперь требует непустое содержимое (раньше проходил и на «(nothing)»). **Оба бага закрыты в 12-м круге одним корневым фиксом:** `isr_syscall` восстанавливал только `rax`, поэтому процесс продолжал работу с регистрами ядра (отсюда и молчаливый `sys_save`, и падение при росте ELF, и порча кадра при переключении). После `POP_GPRS` **два процесса реально перемежаются** (`kenga-app[101]/[100] tick 0,1,2` + `SCHED OK`), файл пишется и читается. **Вытеснение работает (13-й круг):** IRQ0 переключает ring-3 процессы через тот же `k_resume_frame` (`isr_common` возвращается по нему, `k_user_timer_preempt`), прерывание в ядре (cs=0x28) не переключаем. В UART `preempt=0x2`, есть гейт. Приложение умеет создавать каталог и файл в нём (`sys_mkdir` + `sys_save` в новый путь) — проверено чтением из ядра. **Найденный баг рантайма (14-й круг):** `len()` на строке, собранной конкатенацией, возвращает 0 → `sys_save` молча писал 0 байт (литерал сохраняется). В приложении длина задаётся явно. ФС-API приложения закрыт и сквозным образом проверен в CI: `cat` (16), `save` (17), `mkdir` (18), `rm` (19) — положительный гейт на созданный файл и отрицательный на удалённый. Планировщик умеет ждать: `sleep(ms)` (syscall 21) + `uptime_ms()` (22), гейт `kenga-app: sleep ok`; добавлен `up_pick_wait` (idle через `sti; hlt`), иначе выход последнего активного процесса «забывал» спящих. Плюс **коды завершения** (syscall 23): два процесса одного и того же ELF завершаются с разными кодами (`userapp exit pid=0x64 code=0x0` / `pid=0x65 code=0x7`) — доказательство пер-процессного состояния; задел под `wait`. **Приложение запускает приложение** (syscall 24, `spawn`): ELF читается с KengaFS в буфер ядра и становится процессом — в одном прогоне жили три процесса (kenga-app 100/101 + hello 102). Жизненный цикл замкнут: **`wait_status(pid)`** (syscall 25) отдаёт код завершения ребёнка (иначе −1), родитель ждёт опросом через `sleep`. **Блокирующий `wait()` работает** (syscall 26): syscall перезапускается — сохранённый RIP сдвигается на `int 0x80`, а RAX возвращается номер syscall. Этот же механизм нужен для блокирующего чтения. **ЗАКРЫТО (27-й круг):** рост ELF приложения выше ~4.6 КиБ ронял его в ring 3 ещё до первого вывода (`#PF`, `cr2=0`). Причина — ошибка копирования страниц в `elf_load`: для страниц ПОСЛЕ первой источник брался без вычитания `inoff`, то есть данные сдвигались ровно тогда, когда RX-сегмент переходил во вторую страницу (порог между 4224 и 4656 байтами). Фикс — 25-й круг; в 26-м я ошибочно решил, что он «не объясняет баг». Доказательства 27-го круга: (1) побайтовое сравнение — байты ELF, которые видит ядро (файловое смещение 4480), совпали с файлом на хосте, значит чтение из KengaFS было верным и порча происходила именно при загрузке; (2) приложение с паддингом 4816 байт (RX-сегмент заходит во вторую страницу) с фиксом работает полностью — `ring3 OK`, тики, `mkdir`, шесть строк паддинга. Фикс `POP_GPRS` (12-й круг) это НЕ лечит — баг отдельный; воспроизводится на 4656 и 4848 байтах, при 4224 работает. Проверена и исправлена ОДНА ошибка в `elf_load` (страницы после первой копировались со сдвигом на `inoff` — круг 25), но она этот баг НЕ объясняет: на 4.6 КиБ ни один сегмент приложения ещё не пересекает границу страницы. Причина остаётся открытой; `cr2=0` и `rip` в коде приложения. **Замеры 26-го круга:** у рабочего образа (4224 Б) точка входа `0x201df0` лежит внутри RX-сегмента (`0x201190..0x201e12`, одна страница); порог падения — между 4224 и 4656 Б, то есть ровно когда RX-сегмент переходит во ВТОРУЮ страницу (0x202000). Файловые смещения и vaddr сегментов конгруэнтны по модулю 0x1000 (`off=0x190`, `vaddr=0x201190`), поэтому формула копирования страницы k>0 обязана вычитать `inoff` — это и исправлено в 25-м круге. Но падение воспроизвелось и с фиксом, значит у бага есть вторая причина: следующий шаг — собрать приложение ~4700 Б и проверено в 27-м круге и подтвердило фикс. Обходной путь для строк, собранных в рантайме: `k_rt_len` в рантайме приложения (встроенный `len()` на таких строках даёт 0). Дальше: `open`/`mmap`, idle-задача. **Открытый вопрос (29–30 круги):** часть вывода приложения иногда пропадает из UART (`kenga-ap`, нет маркеров дескрипторов), а гейты, которые печатает ядро, проходят. Версия «ядро пишет в 0x3F8 не глядя на готовность передатчика» **проверена и отклонена** — добавление ожидания `LSR.5` привело к зависанию и полной потере вывода, откачено. **Вывод 32-го круга (важно для методики):** проверка `LSR.5` перед записью в UART (31-й круг) — правильная практика для железа, но в QEMU она НЕ устраняет потери: QEMU сообщает `THRE` готовым сразу и всё равно дропает байты при быстрой записи. Это видно по тому, что даже строка `saved /apps/state.txt` приходит обрезанной, а маркеры, стоящие между двумя напечатанными, пропадают целиком. Значит **вывод приложения через UART не годится как основа CI-гейта**: проверять функции приложения надо по артефакту на диске (как `state.txt`: приложение пишет результат в файл, ядро читает его и печатает — это надёжный, kernel-side вывод), а не по строке в UART. **Дескрипторы (`open`/`read`/`close`, syscalls 27–29): API в ядре есть, применение из приложения не работает.** Отсечено экспериментом (33–34 круги): это не UART, не обработчик `write` и не новый статический буфер (`g_fd_buf` заменён на проверенный `uxfer` — результат тот же; падают ВСЕ гейты приложения, включая `spawn` и сбор статуса ребёнка, которые работали до добавления fd-кода). Область сужена до стороны приложения: объявления `@intrinsic` и обёртки `k_sys_open/k_sys_read/k_sys_close` в рантайме. **Уточнение 37–38 кругов (важно):** изоляция `sys_open` выполнена, и симптом оказался точнее, чем «ломает процесс». После `sys_open` следующий `sys_save("/apps/fd.txt", "open ok", 7)` **создал файл из 7 НУЛЕВЫХ байт** — в UART это выглядит как пустое содержимое, но `fs_read` вернул 7. Значит строка-ЛИТЕРАЛ прочиталась как нули: `ux_from_user` смотрит по `user_pml4`, и либо он перестал указывать на PML4 процесса, либо трансляция читает не ту страницу. Проверено `nm`, что переполнения буфера нет (`g_fd_buf` заканчивается за 32 байта до `g_up_stacks`). **Бисект 39-го круга: `sys_open` САМ ПО СЕБЕ ПРОЦЕСС НЕ ЛОМАЕТ.** Если вызвать его ПОСЛЕДНИМ (после всего, что проверяют гейты), то проходят ВСЕ kernel-side гейты, включая коды завершения обоих процессов — то есть open вернулся, и процесс прожил дальше. Упали только два гейта, которые опираются на UART-вывод ПРИЛОЖЕНИЯ (строки чтения bootlog) — их QEMU и потерял. Отсюда два вывода: (1) виновата связка «open, затем следующий syscall, читающий память пользователя» (в 37-м круге после open литерал прочитался как 7 нулей) — смотреть `user_pml4`/`ux_from_user`; (2) **эти два гейта надо перевести на kernel-side доказательство**: они единственные флейки, потому что зависят от вывода приложения, а не от артефакта на диске. Проверять функции приложения только по артефакту на диске — UART-вывод QEMU дропает. **ПРИЧИНА ДЕСКРИПТОРОВ ЛОКАЛИЗОВАНА (45-й круг):** убрал вызов Kenga-ФС из `fd_open`, оставив саму функцию, — и следующий `sys_save` приложения записал ПРАВИЛЬНОЕ содержимое (штатный гейт `kenga-app wrote: kenga-app was here` прошёл). Значит ломает именно **вызов `k_fs_syscall` из `fd_open`**, а не функция, не буфер и не syscall-путь. Рабочая гипотеза: Kenga-сгенерированный код нарушает SysV ABI (затирает callee-saved регистр); вызов напрямую из `k_syscall_handler` это терпит, а из `fd_open` — нет, компилятор держит там живую переменную. Проверка: сохранить/восстановить `rbx, rbp, r12–r15` вокруг вызова `k_fs_syscall` в `fd_open`. **Подтверждено в 47-м круге:** барьеры `__asm__ __volatile__("" ::: "rbx","rbp","r12","r13","r14","r15")` вокруг вызова исправили порчу — с приложением, зовущим `sys_open` перед записью, штатный гейт `kenga-app wrote:` стал проходить (`kenga-app was here` вместо семи нулей). То есть Kenga-сгенерированный код действительно затирает callee-saved. **Что осталось:** с включённым `sys_open` всё ещё падает гейт `sys_cat` (файл `/apps/cat.txt` пишется ДО `sys_open`, так что это отдельный симптом того же класса). **Итог 51-го круга: у проблемы есть ВТОРАЯ составляющая.** С барьерами уже на обоих путях вызова Kenga-ФС включил в приложении `sys_open` — и хотя запись файла (`kenga-app wrote:`) верна, падают `sys_cat` (возвращает не то: приложение пишет `cat BAD`) и блокирующий `wait`. То есть порча callee-saved доказана и исправлена, но недостаточна: похоже, Kenga-код затирает ещё и общее окружение — кандидаты: флаг направления DF, x87/MMX-состояние, либо статический scratch в рантайме Kenga, общий для вложенных вызовов. Симптом «`cat` вернул ошибку ПОСЛЕ того, как `open` прочитал тот же файл» указывает на общее состояние FS-моста между вызовами, а не на регистры. **Итог 53-го круга: буфер окончательно исключён** (чистый тест с уже стоящими барьерами: `fd_open` через проверенный `uxfer` — `sys_cat` всё равно падает). **Закономерность:** гейт `sys_cat` проходит на чистом дереве и падает в КАЖДОМ эксперименте, где меняется приложение (3 из 3). Значит путь `cat` сам уязвим к той же ABI-проблеме: его call-site вызывает Kenga-код, а барьер стоит ПЕРЕД `if`, а не вокруг вызова, поэтому любая правка приложения меняет распределение регистров — и хрупкий путь ломается случайно. **План (делать в этом порядке):** (1) ввести обёртку `k_fs_bridge(...)`, которая СОХРАНЯЕТ и ВОССТАНАВЛИВАЕТ `rbx/rbp/r12–r15` вручную (inline asm вокруг вызова), и перевести на неё ВСЕ call-site `k_fs_syscall`: ветки `cat`, `save`, `mkdir/rm`, `spawn` и `fd_open`; (2) убедиться, что после этого любая правка приложения не роняет `sys_cat`; (3) только затем включать `sys_open` → `sys_read` → `sys_close` и ставить гейт на дескрипторы. **ЗАМЕР 56-го круга (важно):** при добавлении `sys_open` в приложение ядро печатает `kenga-app cat file: cat BAD` — то есть приложение получило от `sys_cat` НОЛЬ (и записало заглушку), а не испорченное содержимое. Значит ломается не данные, а сам вызов: скорее всего `ux_to_user`/`user_v2p` не транслирует буфер приложения (`rt_buf()`), то есть `user_pml4` в этот момент не тот. `sys_cat` при этом идёт ПЕРВЫМ, ДО `sys_open`, так что причина — не «состояние после open», а что-то, меняющееся при изменении самого приложения (раскладка/адрес `rt_buf()`). **РЕШАЮЩИЙ ЗАМЕР 57-го круга:** напечатал в ветке `cat` четыре значения — `user_pml4`, `dst` (адрес буфера приложения), трансляцию `user_v2p(pml4, dst)` и результат моста. Получено: `pml4=0x1149000 dst=0x214030 pa=0x1161030 n=0xffffffffffffffff` (и аналогично для второго процесса, с другим pml4/pa). То есть **трансляция в порядке** (`pa` валиден, `user_pml4` свой у каждого процесса), а **`k_fs_syscall` вернул −1**. Значит ломается сам вызов Kenga-ФС, а не доступ к памяти пользователя: `fs_read` возвращает −1 либо из-за состояния ФС (`st.ok`), либо из-за неверного пути. **ПРИЧИНА НАЙДЕНА (58-й круг): путь ПУСТОЙ.** Замер в ветке `cat`: `CAT path=[] ok=0x1 rw=0x1` — то есть `ux_copy_str` не получила ни одного символа, `fs_lookup("")` не находит файл, `fs_read` возвращает −1, приложение получает ноль и пишет заглушку. Состояние ФС при этом верное (`ok=1`, `rw=1`), а трансляция буфера проверена в 57-м круге и исправна. Значит **ядро невиновно: приложение передаёт пустой указатель на строку пути**. Это объясняет и «3 из 3»: гейт `sys_cat` падал в КАЖДОМ эксперименте, где менялся код приложения. **ПОПРАВКА 59-го круга:** версия «патч-трамплин» НЕВЕРНА — `scripts/patch-kenga-user.py` патчит только заглушки `println_*`, а `sys_cat` идёт через обычную C-обёртку `k_sys_cat` в `kenga_user_rt.c`, ровно как `sys_save`, который при этом работает. **Следующий шаг (одна сборка):** напечатать в ветке `cat` значение `user_v2p(user_pml4, path_uva)` — то есть трансляцию адреса СТРОКИ ПУТИ (в 57-м круге так проверялся буфер назначения, и он транслировался). Если страница литерала не транслируется — виновата раскладка/загрузка `.rodata` приложения (`elf_load`), если транслируется, но байт там ноль — виновата сторона приложения (адрес литерала). **КОРЕНЬ НАЙДЕН (60-й круг):** замер дал `CAT pathuva=0x20300c ppa=0x115000c bytes=0x0 0x0 0x0 0x0` — адрес строки пути транслируется в валидную страницу, но **все байты там нулевые**, и оба процесса передают ОДИН И ТОТ ЖЕ адрес `0x20300c` (константа из ELF). Этот адрес лежит ВНЕ загруженных сегментов: rodata-сегмент кончается на `0x202fff`, RW-сегмент начинается с `0x203c90`, а страницу `0x203000` загружает RW-сегмент — байты ниже его начала остаются нулями. Значит ядро невиновно полностью: приложение ссылается на строку, которой в образе нет. **Следующий шаг:** собрать приложение и посмотреть `llvm-readelf -l` (какие диапазоны покрывают PT_LOAD и где литерал пути), а также проверить, не режет ли `scripts/elf-shrink.py` файл раньше конца данных сегментов. Чинить надо раскладку/упаковку приложения, а не ядро. **ПОДТВЕРЖДЕНО readelf (61-й круг):** `LOAD 3: off=0xe22 vaddr=0x202e22 filesz=0x1de` (rodata, данные ЕСТЬ) и `LOAD 4: off=0x1000 vaddr=0x203000 filesz=0` (RW, данных НЕТ). Строка `bootlog` в файле присутствует (grep=1), то есть лежит в rodata ниже `0x203000`. А приложение передаёт `0x20300c` — адрес внутри RW-сегмента, где по определению нули. **Значит ссылка на литерал и сами байты разъехались: код ссылается на адрес в сегменте без файловых данных.** Это дефект сборки приложения (`scripts/build-user.sh` / раскладка секций линкером), а не ядра и не KengaFS. **Следующий шаг:** добавить в линковку приложения корректный linker script (или `-z separate-code` / явное размещение `.rodata` в одном PT_LOAD с кодом), собрать и проверить, что адрес литерала попадает в диапазон LOAD с filesz>0. **Что уже исключено (62-й круг):** сгенерированный C КОРРЕКТЕН — в `build/user/kenga_app.c` стоит `k_sys_cat("/system/bootlog.txt", k_rt_buf(), 256)`, то есть исходник и emit-c ни при чём. Линковка идёт дефолтным скриптом lld: `ld.lld -flavor gnu -m elf_x86_64 -nostdlib --gc-sections --strip-all -e _start` (своего linker script нет). Значит расхождение «ссылка на адрес ≠ место данных» создаёт **линкер/раскладка**: проверять `--gc-sections`/`--strip-all` и добавить явный linker script, размещающий `.rodata` в одном PT_LOAD с кодом. Также сверить, что делает `elf-shrink.py` с этим образом (`grep -c bootlog` = 1, файл ровно 4096 = max(offset+filesz) по сегментам). **РЕШЕНО (63–64 круги):** линковка приложения переведена на `--no-rosegment` — R и RX теперь в одном PT_LOAD с файловыми данными (было 4 сегмента, стало 2: `LOAD 0 R E filesz=0xf90` код+rodata, `LOAD 1 RW filesz=0` только .bss). - BAR0 = 0xFEBC0000, доступ к MMIO через HHDM (`kf_get_hhdm`);
- MAC прочитан и совпал с эталоном QEMU: `52:54:00:12:34:56`;
- сброс `CTRL.RST` (бит самосбрасывается — значит запись доходит до железа) и `STATUS` с битом Link Up.

**Три вывода про процесс проверки (важнее кода, стоили больше всего времени):**
1. Вывод приложения через UART в QEMU теряется — гейты обязаны читать только артефакты, которые
   создаёт и читает само ядро. Ложные гейты этого типа давали неверные выводы в кругах 28–37.
2. `scripts/run-a64.sh` брал СУЩЕСТВУЮЩИЙ ELF, поэтому упавшая сборка aarch64 шесть кругов
   выглядела успехом (круги 87–93). Закрыто: проверка свежести ELF перед упаковкой образа
   (проверено и на успешном пути, и на устаревшем ядре — срабатывает).
3. Нельзя утверждать «платформа не затронута» по рассуждению. Общий `kmain.kenga` собирается
   для обеих платформ, поэтому x86-only код обязан иметь aarch64-путь: правило в
   `scripts/a64-sed.sed` + заглушка в `kernel/aarch64/hw_a64.c`. Без этого сборка ARM падает.

**Ограничения emit-c, найденные на практике:**
- каждый инлайн порт- или mmio-интринсика порождает ЛОКАЛЬНУЮ переменную (`_k_port_in`),
  поэтому два вызова в одной области видимости дают `redefinition`; лечится обёрткой
  «один интринсик на функцию»;
- `fn` — зарезервированное слово Kenga (имя параметра недопустимо).

**Исправление собственной ошибки в отчётах:** USB-HID (xHCI: мышь/планшет) давно реализован и
встроен в `kf_mouse.c`; строка «USB ❌» была ошибочной. Не закрыты USB mass storage и железо.

**Проверено на конец сессии:** x86_64 — четыре гейта зелёные; aarch64 — сборка без ошибок и
SMOKE OK на свежем ядре.


## Сеть: что нужно для колец RX/TX (найдено, 97-й круг)

Для дескрипторных колец e1000 нужна DMA-память и её ФИЗИЧЕСКИЕ адреса:
- `@intrinsic fn mem_palloc() -> i64;` — объявлен в `kernel/kmain.kenga` (стр. 24),
  возвращает HHDM-адрес выделенной страницы (4 КиБ);
- `k_mem_virt_to_phys(int64_t)` в C (`kernel/kf_mem.c:150`, объявление `kf_rt.h:59`) —
  переводит HHDM-адрес в физический; именно физические адреса кладутся в RDBAL/TDBAL;
- на x86 DMA когерентен (то же допущение, что для AHCI: см. `kf_ahci.c:12`);
- дескрипторы e1000 — по 16 байт, массивы должны быть выровнены (страница из palloc подходит);
- QEMU e1000 = Intel 82540EM: регистры RDBAL 0x2800, RDLEN 0x2808, RDH 0x2810, RDT 0x2818,
  RCTL 0x0100; TDBAL 0x3800, TDLEN 0x3808, TDH 0x3810, TDT 0x3818, TCTL 0x0400.

Внимание при реализации: объявления `@intrinsic` в Kenga нельзя дублировать между модулями
без последствий (проверено на `asm_inb`), а инлайн порт- и mmio-интринсиков порождает
локальные переменные — один вызов на функцию. `mem_palloc` объявлен в kmain.kenga, поэтому
код колец безопаснее размещать там же либо проверить видимость из импортируемого модуля.
