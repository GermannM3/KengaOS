# Честный чек-лист KengaOS — что увидят компании и пользователи

Дата: 2026-09-05 · Версия: v0.7.2 + UI-оболочки · Проверено по коду:
`kenga-lang/` (v3.13), `kernel/`, `src/` (десктоп + мобилка).

## Видение

ОС нового поколения: системный слой написан на языке Kenga (UI — тоже
постепенно), и система «ткёт» пророков в себя — агенты с памятью и
предсказанием (Prophet) работают как часть ОС, а не как приложение.

## ✅ ЧТО РЕАЛЬНО ЕСТЬ СЕГОДНЯ (проверено, не маркетинг)

### Видит пользователь (ISO на ноутбуке / в QEMU)
- Живой рабочий стол **Aurora**: окна с перекрытием, dock, topbar,
  обои с дрейфующим свечением. Логика десктопа — **на Kenga**
  (`desktop.kenga`, 793 строки, `ui.kenga`, `kmain.kenga`), компилируется
  `emit-c --freestanding` и грузится на голое железо.
- **Терминал** с командами, **чат с агентом** (печатает текст — агент
  отвечает через IPC).
- **4 системных агента** как процессы ОС: logger / agent / model /
  researcher — с IPC, правами (capabilities) и очередями. Видны в
  «AGENT SPACE».
- **Модель-агент ONLINE**: настоящий MLP 2-2-1 в ядре, обучен на XOR,
  инференс через IPC с проверкой прав (`CAP_MODEL_INFER`).
- **Магазин**: 6 пакетов `.kpkg` в initrd, установка из input-бара. **v2**
  (`kenga-app.kpkg`) = текстовый манифест + пустая строка + бинарный
  payload; установка целиком на Kenga: пакет читается из initrd, payload
  пишется в KengaFS `/apps/kenga-app.elf` (`install kenga-app.kpkg`),
  старая форма `install a` по-прежнему идёт в C-реестр. Гейт CI
  `STORE INSTALL OK`.
- **Prophet как системный сервис** (v1): `kernel/kf_prophet.c` — память
  эпизодов + ядро паттернов, surprise (RMSE), k-NN foresee; тикает из
  десктопа (`kd_prophet_tick`), прогноз виден в SYSTEM HEALTH.
- **Пророки оболочки, обучающиеся на ходу** (0.8.1, `Prophet.jsx`):
  ассистенты в «Чате»/«Агентах» выучивают пары «учи: вопрос => ответ»
  (память в localStorage, recall по схожести), предсказывают следующее
  приложение (цепь Маркова по открытиям, точность видна в «Мониторе»),
  surprise на неожиданных переходах. Всё локально, общий код десктопа
  и мобилки.
- **Пайпы в шелле ядра** («bash» v1): `echo text | upper | count` —
  конвейеры команд с фильтрами; boot-самотест + CI-гейт `PIPE OK`.
  Полноценный bash = userspace fork/exec (после ring-3 процессов).
- **KengaFS — персистентная ФС на диске** (`kernel/fs.kenga`, целиком на
  Kenga): superblock, битмап блоков, таблица inode (32), дерево каталогов,
  `mkdir -p`, чтение/запись/удаление; файл `/boots` считает загрузки.
  Десктоп показывает карточку **FILES · KENGA-FS** (inode/блоки + список
  файлов из inode-таблицы) и понимает команды в input-баре: `ls`, `df`,
  `cat <path>`, `touch <path>`, `mkdir <path>`, `rm <path>`,
  `write <path> <text>`. Пишем только на диск с маркером `KENGARWTEST1`
  или уже содержащий KengaFS — чужие диски не трогаются. Персистентность
  проверяется двумя QEMU-ботами на одном образе: `fs:boot=1` →
  `fs:boot=2` (`scripts/test-fs-persistence.sh`).
- **Kenga-приложение в ring 3**: `user/kenga_app.kenga` — исходник на
  **Kenga** (`println`, рекурсивный `fib`) — собирается
  `scripts/build-user.sh`: `emit-c --freestanding` → патч заглушек `println`
  в `int 0x80 write` (`scripts/patch-kenga-user.py`) → clang/`ld.lld` → ELF
  (~3.5 КиБ) → initrd → **KengaFS `/apps/kenga.elf`** → `elf_load` → ring 3,
  возврат по `sys_exit`. Работает на загрузке (гейт `USERAPP OK`) и из
  десктопа командой `run /apps/kenga.elf`. CI проверяет **вывод самой
  программы**: `kenga-app: ring3 OK`, `kenga-app: fib(12) = 144`.
  Попутно найден и исправлен баг `elf_load`: игнорировался `filesz`, и в
  `.bss` уезжал хвост файла (аллокатор Kenga-рантайма сразу получал OOM).
- **xHCI USB**: работает в QEMU на обеих архитектурах (тач-планшет,
  ECAM-скан, слоты, CONFIG_EP); на живом железе не проверен.
- **Две архитектуры одним исходником**: x86_64 ISO + aarch64 (QEMU, CI).
- **Каждый коммит** автотестируется: ядро реально грузится в QEMU на
  обеих архитектурах, включая установку пакета и ring-3 запуск.

### UI-оболочки (прототипы на веб-стеке, общий kernel bridge)

Честно: это React/Vite-прототипы поверх симуляции kernel bridge —
контракт тот же, что у ядра (37 `kd_*`); порт в Kenga/C — по `docs/design/design.md`.

- **Десктоп** (v0.8, без заглушек): окна с перекрытием, dock, лаунчер,
  терминал, **браузер** (`kenga://` + внешние сайты), **монитор**
  (графики CPU/RAM), **настройки** (3 темы + 2 обоев), **файлы** (VFS
  с Kenga-исходниками), **агенты** (чат + XOR-предсказания модель-агента),
  **чат-ассистент**, **о системе**.
- **Мобилка** (v0.8, APK на POCO M4 Pro): boot → lock → home → шторка →
  лаунчер; экранная клавиатура **Ру/En**; браузер; терминал (команды
  на русском и латинице); **звонилка с реальными контактами** (нативный
  мост) и вызовом через системный дозваниватель; **реальные SMS**
  (чтение, ответ через системное приложение); **камера** (getUserMedia,
  снимок+сохранение); файлы, агенты, чат, монитор, настройки, о системе.
- Темы — общие для обеих оболочек: Полярная / Синяя волна / Зелёная волна.
- Браузер честно: рендерит движком хоста (iframe) — оболочка пока живёт
  внутри браузера; в будущей ОС это свой движок / порт (Servo-класс).

### Видит разработчик / компания
- **Язык Kenga v3.13** — полноценный: i64/f64/bool/str/list/**Tensor**/
  **Memory**/structs, if/while/for, imports, события (`on "tick"`),
  FFI-интринсики. Компилятор: `kenga run / emit-c / build`, плюс
  **kenga-lite** (C99-хост без Rust) и bytecode-рантайм. VS Code
  расширение, книга, примеры.
- **Prophet/Memory API в языке** (это и есть «пророки»):
  `memory() / learn / predict / foresee / surprise / remember / recall /
  consolidate / save_mind / load_mind` — локальный инференс с памятью
  паттернов, консолидацией во сне (EWC-lite), сохранением разумов
  (`.km`-файлы, совместимы с Rust-хостом).
- **Тензоры + мультимодальность**: `t_matmul / t_sgd_step / load_ppm /
  load_wav` — входы изображений и звука.
- **Единая поверхность ядра** для desktop и mobile:
  37 `kd_*`-функций (агенты, IPC, память, мышь/тач, uptime) — тот же
  контракт, что декларирует `kernel_bridge.kenga`.

Дальше: `open`/`mmap`, вытеснение. **Разбор бага (11-й круг, дамп таблицы inode):** `fs_mkdir` НЕ виноват — после `mkdir` таблица inode корректна (`/`, boots, system, bootlog.txt, tmp, apps, kenga-app.elf, demo). Виноват `sys_save` из приложения: файл `/apps/state.txt` вообще не создавался, а приложение печатало «saved» безусловно. Гейт `kenga-app wrote:` теперь требует непустое содержимое (раньше проходил и на «(nothing)»). **Оба бага закрыты в 12-м круге одним корневым фиксом:** `isr_syscall` восстанавливал только `rax`, поэтому процесс продолжал работу с регистрами ядра (отсюда и молчаливый `sys_save`, и падение при росте ELF, и порча кадра при переключении). После `POP_GPRS` **два процесса реально перемежаются** (`kenga-app[101]/[100] tick 0,1,2` + `SCHED OK`), файл пишется и читается. **Вытеснение работает (13-й круг):** IRQ0 переключает ring-3 процессы через тот же `k_resume_frame` (`isr_common` возвращается по нему, `k_user_timer_preempt`), прерывание в ядре (cs=0x28) не переключаем. В UART `preempt=0x2`, есть гейт. Приложение умеет создавать каталог и файл в нём (`sys_mkdir` + `sys_save` в новый путь) — проверено чтением из ядра. **Найденный баг рантайма (14-й круг):** `len()` на строке, собранной конкатенацией, возвращает 0 → `sys_save` молча писал 0 байт (литерал сохраняется). В приложении длина задаётся явно. ФС-API приложения закрыт и сквозным образом проверен в CI: `cat` (16), `save` (17), `mkdir` (18), `rm` (19) — положительный гейт на созданный файл и отрицательный на удалённый. Планировщик умеет ждать: `sleep(ms)` (syscall 21) + `uptime_ms()` (22), гейт `kenga-app: sleep ok`; добавлен `up_pick_wait` (idle через `sti; hlt`), иначе выход последнего активного процесса «забывал» спящих. Плюс **коды завершения** (syscall 23): два процесса одного и того же ELF завершаются с разными кодами (`userapp exit pid=0x64 code=0x0` / `pid=0x65 code=0x7`) — доказательство пер-процессного состояния; задел под `wait`. **Приложение запускает приложение** (syscall 24, `spawn`): ELF читается с KengaFS в буфер ядра и становится процессом — в одном прогоне жили три процесса (kenga-app 100/101 + hello 102). Жизненный цикл замкнут: **`wait_status(pid)`** (syscall 25) отдаёт код завершения ребёнка (иначе −1), родитель ждёт опросом через `sleep`. **Блокирующий `wait()` работает** (syscall 26): syscall перезапускается — сохранённый RIP сдвигается на `int 0x80`, а RAX возвращается номер syscall. Этот же механизм нужен для блокирующего чтения. **ЗАКРЫТО (27-й круг):** рост ELF приложения выше ~4.6 КиБ ронял его в ring 3 ещё до первого вывода (`#PF`, `cr2=0`). Причина — ошибка копирования страниц в `elf_load`: для страниц ПОСЛЕ первой источник брался без вычитания `inoff`, то есть данные сдвигались ровно тогда, когда RX-сегмент переходил во вторую страницу (порог между 4224 и 4656 байтами). Фикс — 25-й круг; в 26-м я ошибочно решил, что он «не объясняет баг». Доказательства 27-го круга: (1) побайтовое сравнение — байты ELF, которые видит ядро (файловое смещение 4480), совпали с файлом на хосте, значит чтение из KengaFS было верным и порча происходила именно при загрузке; (2) приложение с паддингом 4816 байт (RX-сегмент заходит во вторую страницу) с фиксом работает полностью — `ring3 OK`, тики, `mkdir`, шесть строк паддинга. Фикс `POP_GPRS` (12-й круг) это НЕ лечит — баг отдельный; воспроизводится на 4656 и 4848 байтах, при 4224 работает. Проверена и исправлена ОДНА ошибка в `elf_load` (страницы после первой копировались со сдвигом на `inoff` — круг 25), но она этот баг НЕ объясняет: на 4.6 КиБ ни один сегмент приложения ещё не пересекает границу страницы. Причина остаётся открытой; `cr2=0` и `rip` в коде приложения. **Замеры 26-го круга:** у рабочего образа (4224 Б) точка входа `0x201df0` лежит внутри RX-сегмента (`0x201190..0x201e12`, одна страница); порог падения — между 4224 и 4656 Б, то есть ровно когда RX-сегмент переходит во ВТОРУЮ страницу (0x202000). Файловые смещения и vaddr сегментов конгруэнтны по модулю 0x1000 (`off=0x190`, `vaddr=0x201190`), поэтому формула копирования страницы k>0 обязана вычитать `inoff` — это и исправлено в 25-м круге. Но падение воспроизвелось и с фиксом, значит у бага есть вторая причина: следующий шаг — собрать приложение ~4700 Б и проверено в 27-м круге и подтвердило фикс. Обходной путь для строк, собранных в рантайме: `k_rt_len` в рантайме приложения (встроенный `len()` на таких строках даёт 0). Дальше: `open`/`mmap`, idle-задача. **Открытый вопрос (29–30 круги):** часть вывода приложения иногда пропадает из UART (`kenga-ap`, нет маркеров дескрипторов), а гейты, которые печатает ядро, проходят. Версия «ядро пишет в 0x3F8 не глядя на готовность передатчика» **проверена и отклонена** — добавление ожидания `LSR.5` привело к зависанию и полной потере вывода, откачено. **Вывод 32-го круга (важно для методики):** проверка `LSR.5` перед записью в UART (31-й круг) — правильная практика для железа, но в QEMU она НЕ устраняет потери: QEMU сообщает `THRE` готовым сразу и всё равно дропает байты при быстрой записи. Это видно по тому, что даже строка `saved /apps/state.txt` приходит обрезанной, а маркеры, стоящие между двумя напечатанными, пропадают целиком. Значит **вывод приложения через UART не годится как основа CI-гейта**: проверять функции приложения надо по артефакту на диске (как `state.txt`: приложение пишет результат в файл, ядро читает его и печатает — это надёжный, kernel-side вывод), а не по строке в UART. **Дескрипторы (`open`/`read`/`close`, syscalls 27–29): API в ядре есть, применение из приложения не работает.** Отсечено экспериментом (33–34 круги): это не UART, не обработчик `write` и не новый статический буфер (`g_fd_buf` заменён на проверенный `uxfer` — результат тот же; падают ВСЕ гейты приложения, включая `spawn` и сбор статуса ребёнка, которые работали до добавления fd-кода). Область сужена до стороны приложения: объявления `@intrinsic` и обёртки `k_sys_open/k_sys_read/k_sys_close` в рантайме. Следующий шаг: оставить в приложении ТОЛЬКО `sys_open` (файловый гейт) и смотреть, выживет ли процесс; затем добавить `read`, затем `close`. Проверять функции приложения только по артефакту на диске — UART-вывод QEMU дропает |

   ~~AHCI~~ (сделано: `kf_ahci.c`, гейт `AHCI READY` на `-M q35`) → NVMe → ACPI → Wi-Fi.
4. **Телефон**: adb (беспроводное сопряжение) → mtkclient →
   `fastboot boot` из RAM → чек-лист железа (`docs/PHONE-TRACK.md`).

> правами, инференс в ядре, магазин пакетов, ring-3 приложения,
