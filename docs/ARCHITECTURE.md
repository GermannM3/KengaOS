# Архитектура KengaOS

Этот документ описывает, **почему** KengaOS устроена именно так.
Для **как** — смотри исходники и README.

---

## 1. Философия

### 1.1. Kenga-нативная ОС

KengaOS — это не «ещё один unix-like». Это ОС, в которой агентная модель,
living memory и событийный цикл Kenga являются **системными примитивами**, а
не библиотечной надстройкой. Цель: язык Kenga не должен «обходить» ОС —
он должен говорить с ней на родном языке.

В практике v0.0.x это означает: ядро — обычное классическое монолитное
ядро на C. Это **бутстрап**. Постепенно C-модули заменяются на Kenga-модули
через `lower_c` (генератор C из Kenga), и ядро «прорастает» Kenga-кодом.

### 1.2. Русский — язык первого класса

Большинство ОС начинаются с английского и потом получают локализацию как
опцию. KengaOS начинает с русского. Это не национализм — это прагматизм:
сообщество вокруг Kenga русскоязычное, документация русскоязычная, и
касающиеся ядра концепции («намерения», «память», «агенты») формулируются
естественнее на русском.

Интерфейс переключается в runtime через `lang ru`/`lang en`. Добавить
третий язык — 50 строк кода в `i18n.c`.

### 1.3. Bare-metal-first

KengaOS загружается на голом железе, не использует BIOS-сервисы после
загрузчика. Загрузчик — Limine (UEFI или BIOS legacy), который уже
настроил длинный режим, пейджинг, и передал нам готовое адресное
пространство. KengaOS не делает ничего, что мог бы делать загрузчик.

## 3. Процесс загрузки

```
1.  Limine (UEFI или BIOS)
       │
       │  Настраивает: long mode, paging, framebuffer, memmap
       │  Загружает: kernel.elf по адресу 0xFFFFFFFF80000000
       │  Передаёт: rdi = указатель на boot_info
       ▼
2.  entry.S: _kentry
       │
       │  Очищает BSS, выравнивает стек, вызывает kmain
       ▼
3.  kmain():
       │
       ├─ uart_init(COM1)              ← отладочный вывод доступен
       ├─ i18n_set_lang(LANG_RU)       ← русский по умолчанию
       ├─ fb_init(framebuffer)         ← графический вывод
       ├─ detect_memory()              ← читаем memmap от Limine
       ├─ boot_banner()                ← ASCII-логотип
       ├─ boot_log()                   ← выводим версии/память
       ├─ gdt_init()                   ← GDT + TSS
       ├─ idt_init()                   ← IDT + PIC remap
       ├─ pit_init(1000)               ← таймер
       ├─ kbd_init()                   ← клавиатура
       └─ shell_run()                  ← REPL
```

## 4. i18n — как это работает

### 4.1. Принцип

В коде **никогда** не пишутся строки напрямую. Только ID:

```c
// ПЛОХО:
fb_puts("KengaOS загружается...\r\n");

// ХОРОШО:
kprintf(i18n_str(STR_BOOT_STARTING));
```

`i18n_str(STR_BOOT_STARTING)` возвращает указатель на UTF-8 строку
в таблице текущего языка. Переключение языка меняет указатель таблицы —
мгновенно, без перевыделения памяти.

### 4.2. Расширение

Чтобы добавить язык (например, испанский):

1. В `i18n.h` добавить `LANG_ES = 2` в `kenga_lang_t`.
2. В `i18n.c` написать `strings_es[STR_COUNT]` с переводами.
3. Добавить `strings_es` в `lang_tables[]`.
4. Добавить `"Español"` в `lang_self_names[]`.
5. В `i18n_parse_lang_code` добавить `if (code[0]=='e' && code[1]=='s'...)`.

Всё. В shell можно писать `lang es`.

### 4.3. UTF-8

Все строки — UTF-8. Framebuffer умеет декодировать многобайтные
последовательности (см. `fb_putc` в `fb.c`). Шрифт 8x16 поддерживает
латиницу + кириллицу (диапазоны U+0020..U+007F и U+0410..U+044F).

UART выводит UTF-8 байт-за-байтом. Большинство современных терминалов
соберут последовательность корректно. (QEMU `-serial stdio` — точно.)

## 5. Связь с Kenga-lang

### 5.1. Стратегия миграции

Kenga уже умеет генерировать C через `lower_c`. Но в текущей версии
генератор тянет CRT-зависимости (`stdio.h`, `string.h`). Чтобы Kenga-код
мог жить в ядре, нужно:

1. **`--freestanding` флаг** для `lower_c` — выкидывает CRT includes,
   заменяет на минимальные `memcpy`/`memset` инлайнами.
2. **`mmio_read<T>(addr)` / `mmio_write<T>(addr, val)`** — встроенные
   функции, эмитящие `*(volatile T*)addr`. Для драйверов.
3. **`asm!(arch, code)`** — встроенный ассемблер. Минимально: один
   строковый литерал + optional операнды.
4. **`atomic_load/store/cas/fence`** — атомарные операции.

Когда это есть, можно переписывать модули:

| Модуль C         | Аналог на Kenga                 | Когда |
|------------------|---------------------------------|-------|
| `kernel/lib/libc.c` | `stdlib.kenga`               | v0.1  |
| `kernel/i18n/i18n.c` | `i18n.kenga`                 | v0.1  |
| `kernel/drivers/fb.c` | `drivers/fb.kenga`          | v0.2  |
| `kernel/drivers/kbd.c` | `drivers/kbd.kenga`         | v0.2  |
| `kernel/kmain.c` | `kmain.kenga`                   | v0.3  |
| `arch/x86_64/*.S` | Kenga + `asm!`                 | v0.3  |

### 5.2. Kenga-нативные концепции в ядре

Когда язык станет freestanding, в ядро переедут не только C-модули,
но и Kenga-нативные концепции:

- **`emit/pump` события** → замена классическим IPC (pipes, signals).
  Процессы-агенты общаются событиями. Это уже работает в Kenga 3.13.
- **`ttl` / `sweep`** → кэш-страницы памяти. Ядро само выгружает
  холодные данные. (Внимание: kernel memory домен — без ttl, agent
  memory домен — с ttl.)
- **`memory()` + `learn()`** → предиктивный планировщик. Ядро учится
  на поведении процессов и подсказывает CFS-слою, кому дать больше CPU.
- **Birth-цикл** → self-healing. Если системный агент падает, recovery
  kernel пересобирает его из исходников.

Это план на v0.4–v0.6. См. [`docs/ROADMAP.md`](ROADMAP.md).

## 6. Что НЕ делает KengaOS v0.0.1

- ❌ Не поддерживает реальные жёсткие диски (только загрузка из ISO).
- ❌ Не имеет файловой системы.
- ❌ Не имеет сети.
- ❌ Не имеет планировщика процессов (одна нить = shell).
- ❌ Не использует GPU (только software-рендеринг в framebuffer).
- ❌ Не имеет power management (suspend/resume).
- ❌ Не поддерживает USB.

Всё это — планы. См. ROADMAP.

## 7. Безопасность

В v0.0.x ядро работает в ring 0, без защиты памяти между процессами
(потому что процессов пока нет). Это **бутстрап**. Когда появится
planner и user-mode (ring 3), будет внедрена capability-модель:

- Каждый агент при spawn получает capability-токены.
- Ядро проверяет capability на каждом системном вызове.
- Никаких ACL — только capabilities (как в seL4/Capsicum).
