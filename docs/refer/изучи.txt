🔍 Фазовый разбор
Phase 0 — Подготовка языка
✅ Сильные стороны: lower_c уже генерирует C99. Freestanding-режим — это в основном задача удаления зависимостей, а не добавления.

⚠️ Риски и конкретные правки:

Freestanding lower_c — нужно убедиться, что emit не тянет stdio.h, stdlib.h, string.h. Сейчас в kenga_lite.c явно есть CRT includes. Решение: флаг --freestanding в lower_c, который подменяет rt_types.kenga на rt_types_freestanding.kenga (свои memcpy/memset/memcmp на указателях, без printf).
Inline asm! — не делайте универсальный синтаксис. Сделайте минимально узкий:
text

asm!("x86_64", "cli");              // one-liner
asm!("x86_64", "mov $0, %0", out "=r"(x));   // с операндами
Парсинг — простой строковый литерал + optional список операндов. Этого хватит для GDT/IDT/IRQ/context switch. Не пытайтесь повторить LLVM-style asm constraints.
Raw pointers / MMIO — синтаксис *(u32*)0x12345 = 0xFF; опасен тем, что компилятор может закэшировать запись. Лучше типобезопасная встроенка:
text

mmio_write<u32>(0xFD000000, 0xFF);
let v = mmio_read<u32>(0xFD000000);
Она эмитит volatile C-указатель под капотом — и аудит безопаснее, и intent очевиден.
Атомарики — добавьте минимальный набор: atomic_load, atomic_store, atomic_cas, atomic_fence. Эмитятся в __atomic_* GCC builtins или _Atomic C11. Не нужно своего backend.
Phase 1 — Bare-Metal
✅ Limine — правильный выбор (UEFI, stivale2, стабильный протокол). Не пишите свой загрузчик — это ловушка времени.

⚠️ Что пропущено в роадмапе:

UART раньше framebuffer. Framebuffer — классный demo, но для отладки ядра UART в 100× полезнее. Первая цель — не пиксель на экране, а символ в /dev/ttyS0 (QEMU: -serial stdio).
Serial→printf для Kenga. Сделайте kprintf поверх UART — это 50 строк на C, но без него ядро не отлаживается.
GDT/IDT раньше IRQ. В роадмапе IRQ упомянут вскользь, но без IDT вы не получите ни таймер, ни клавиатуру, ни page fault handler. Это ~300 строк на C+asm, но критично.
🎯 Предлагаемая переформулировка Phase 1:

Limine config + kmain.kenga вызывает uart_init() и печатает "KengaOS v0.1"
GDT + IDT на asm! (только load, без сложных handlers)
Timer IRQ + планировщик «круговой» (без предиктов — это Phase 2)
Framebuffer как бонус, не как цель
Page allocator (buddy или bitmap — не обязательно сложный)
Phase 2 — Микроядро
✅ Сильнейшая часть дизайна: события emit/pump уже в языке. IPC-through-events — это естественное продолжение, а не новая абстракция.

⚠️ Серьёзные риски:

«Живой Memory Manager с ttl/sweep для страниц» — концептуально красиво, но операционно опасно. Что произойдёт, если sweep выгрузит страницу с контекстом прерывания? Или со стеком обработчика IRQ?
Решение: разделите memory domains:
Kernel domain — никаких ttl/sweep, классический buddy allocator
Agent domain — тут живёт ttl/sweep, но страницы помечены как agent-owned и swap'аются только когда процесс в user-mode
Hard floor: ядро никогда не sweep'ит то, что не помечено agentOwned=true
Предиктивный планировщик на world-model — если ML-модель, которая решает, кому дать CPU, сама зависнет, у вас повиснет вся система.
Решение: двухуровневый планировщик:
CFS-like базовый слой (round-robin с приоритетами) — всегда работает
Predictive hint layer — world-model подсказывает «дай процессу X на 10мс больше», но базовый слой может проигнорировать подсказку
Watchdog: если predict-агент не отвечает 100мс — fallback на чистый CFS
Policy Engine — нужен capability-based дизайн, не ACL. Каждый агент при появлении получает токены: «может читать /dev/uart», «может выделять до 16 МБ», «может порождать дочерних агентов». Все запросы к ядру содержат токен.
Фаза 3 — Mobile
⚠️ Основные недоработки:

Сеть — для мобильных ОС это приоритет №1. Драйвер WiFi/Ethernet + стек TCP/IP (рекомендую портировать lwIP — 50 КБ, C, MIT). Без сети мобильная ОС — просто игрушка.
Управление питанием — критически важно для мобильных устройств. Режим ожидания/активации, масштабирование частоты, подсветка. Это много кода.
Ввод — драйвер сенсорного экрана (I2C/HID), мультитач.
Файловая система — для начала хотя бы FAT32 в режиме только для чтения, а потом ext2/btrfs.
⚠️ «Голос как основной способ ввода» — пересмотрите подход. Постоянно включенный микрофон — это приватность, экономия заряда батареи, снижение задержки, запасной вариант в шумной обстановке. Сделайте голос равноправным каналом, а не основным. Клавиатура на экране должна быть доступна всегда за <100 мс.

⚠️ WASM-песочницы — это хорошо, но сам по себе WASM не дает доступа к GPU/сети/файловой системе. Вам нужен WASI-уровень, и ваши события должны быть хост-функциями — иначе WASM-приложения не смогут полноценно взаимодействовать с ядром.

Фаза 4 — десктоп
⚠️ Композитор — это 6–12 месяцев работы одного человека. Не пишите свой GUI-тулкут. Серьезно рассмотрите следующие варианты:

Slint (Rust, но имеет C API) — можно звать через FFI
lvgl — C, для embedded, отлично подходит
IMGUI-стиль — проще всего для start'а
⚠️ FFI — половина уже есть через lower_c. Нужно добавить обратное направление: возможность из Kenga-кода звать C-функции по сигнатуре. Например:

text

extern "C" fn printf(fmt: *u8, ...) -> i32;
Это компилируется в extern int printf(const char* fmt, ...); — тривиально.

Phase 5 — Экосистема
✅ Self-Healing через Birth — уникальная фишка, которой нет ни в одной ОС.

⚠️ Chicken-and-egg: если падает агент-компилятор, кто пересоберёт его?
Решение: frozen recovery kernel — статически слинкованный минимальный kenga-lite + набор .kenga исходников в read-only разделе. Он никогда не обновляется в рантайме. Если активный компилятор падает — recovery kernel загружается и пересобирает.

Почему важно
