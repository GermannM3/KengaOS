ОСОБЕННОСТИ РЕАЛИЗАЦИИ (важно не сломать)
==========================================
  1) UART 16550 — ПОРТЫ I/O (asm_outb/asm_inb), НЕ mmio! mmio_write8(0x3F8) → page fault.
  2) kf_alloc — СИЛЬНЫЙ символ в ядре (kf_alloc.c, bump-аллокатор); weak-хук в рантайме
     emit-c подхватывает его. Если сильный символ пропадёт — k_die("oom").
  3) Limine 12.6.0: .limine_requests ПЕРВЫМ PT_LOAD, секция "aw", все секции по 4K.
     Запросы: bootloader_info, framebuffer, hhdm. ID запросов начинаются с
     LIMINE_COMMON_MAGIC (0xc7b1dd30df4c8b88, 0x0a82e883a194f07b)! Ошибочные 4 qword
     → Limine не регистрирует запрос ("Requests count" < ожидаемого).
  4) ld.lld -flavor gnu -m elf_x86_64; clang --target=x86_64-elf -nostdinc -include kf_rt.h;
     clang требует export TEMP/TMP/TMPDIR.
  5) boot_info: kf_get_boot_info() (FFI через kf_rt.h), framebuffer — kf_get_framebuffer().
  6) ФРЕЙМБУФЕР: Limine даёт ФИЗИЧЕСКИЙ адрес (0xfd000000), identity-mapped на раннем
     загрузке → пишем напрямую (как эталон kenga-os), БЕЗ прибавления HHDM.
  7) ФФИ emit-c: `@intrinsic fn fb_x(...)` → C-символ `k_fb_x`; `str` → `const char*`.
  8) СКРИНШОТ ЯДРА: QEMU `-display none`/`vnc`/egl-headless НЕ композитит VBE
     linear-framebuffer (всё чёрное). Надёжно: limine.cfg `timeout: 0` (иначе таймер
     меню в headless флейков и гость виснет на меню) + QMP `pmemsave` физ. адреса
     0xfd000000 (4096000 байт = 1280×800×4) → конвертация BGRA→RGB.
     Скрипт: qmp_pmemsave.py в temp/opencode. Курсор в центре = px(640,400)=(245,241,235)
     (XOR-инверсия фона 0x0a0e14).
  9) Kenga: нет ключевого слова `const` на верхнем уровне (ошибка "expected 'fn'").
     Используй локальные `let` внутри функции. `itoa` есть только в compiler-исходниках,
     в freestanding-программе недоступен — избегай форматирования чисел в UART.

ROADMAP
=======
  M1 (ГОТОВО): загрузка через Limine, UART hello, kf_alloc, oops/panic, CI+smoke, скрин меню.
  M2 (ДАЛЬШЕ): GDT/IDT/PIT, прерывания/исключения, планировщик+IPC, framebuffer-консоль
               + PS/2, buddy/paging/syscalls, shell + агент-демон.

ПРОБЕЛЫ / СЛЕДУЮЩИЕ ЗАДАЧИ (к живому UI, по шагам с commit+push)
=================================================
  ШАГ 1 ✓ (сделан): framebuffer + 8x8 шрифт + экран загрузки ядра.
  ШАГ 2 ✓ (сделан): PS/2 мышь (polling 0x60/0x64, init ACK=0xFA) + XOR-курсор.
     Живое движение проверяется ИНТЕРАКТИВНО: qemu ... -display gtk (input-send-event
     в headless не доходит до PS/2). Курсор рендерится в центре — подтверждено pmemsave.
  ШАГ 3 ✓ (сделан, M2.1): GDT + IDT + исключения + panic.
     ВАЖНО: Limine даёт ядру CS=0x28 (НЕ 0x08)! IDT-гейты должны использовать
     текущий CS (kernel cs=0x28), иначе прерывание → #GP → тройной фолт.
     64-битная IDT-запись = 16 байт (lo/sel/ist/flags/mid/hi/zero), а не 8!
     IDT-самотест: int3 → "INT3 CAUGHT" (iretq, не паникует) — CI-гейт.
  ШАГ 4 ✓ (сделан, M2.2): round-robin планировщик (multitasking) — КООПЕРАТИВНЫЙ
     через k_task_yield (asm, ret-переход, без iretq-фрейма). SSE включён в
     k_intr_init (enable_sse: CR4.OSFXSR), иначе xorps -> #UD.
     ВАЖНО: прерывная (timer-driven) версия с ручным iretq-фреймом НЕ заработала;
     оставлен кооперативный, прерывный — отдельная задача.
  ШАГ 5 ✓ (сделан, M2.3): PS/2 клавиатура (IRQ1→вектор 33, kf_kbd.c ring buffer)
     + framebuffer-консоль (kf_fb.c: k_fb_con_*, скроллинг) + shell (kf_shell.c,
     C — в Kenga нет chr() для построения строк). Команды: help/info/clear/echo/tasks.
     IRQ-обработка в intr.c: векторы 32-47 → EOI + dispatch (не panic).
     ТЕСТ ВВОДА: QMP `human-monitor-command sendkey info ret` (HMP sendkey надёжнее,
     чем input-send-event для Enter). Проверка консоли — pmemsave 0xfd000000.
  ШАГ 6 ✓ (сделан, M2.4): физическая память + kernel heap.
     kf_mem.c: Limine memmap -> самый большой usable-регион (base>=1MB, ядро Limine
     помечает reserved отдельно — скипать НЕ надо!) -> HHDM-адрес = heap (~62MB).
     kf_alloc (сильный символ) теперь аллоцирует из heap; ДО mem_init — fallback-арена
     (8KB), иначе ранний emit-c рантайм падает (kf_alloc=0). Команда shell 'mem'.
     ВАЖНО: memmap response.entries — массив УКАЗАТЕЛЕЙ на записи (entries[i]->base/length/type),
     не массив записей (это была причина mem_init=FAIL).
  ШАГ 7 ✓ (M2.5): процессы + IPC (kf_proc.c). k_ipc_send/k_ipc_recv, per-proc queues.
     IPC подтверждён (LOGGER: hello). ФИКС: lg_uart объявлен ПОСЛЕ k_ipc_send/recv ->
     сборка падала, бинарник ломался -> казалось, что IPC/консоль сломаны.
  ШАГ 8 ✓ (M2.6): init + kenga-agent через IPC (двусторонний round-trip).
     k_proc_init = "init": спавнит logger + agent. agent получает msg и отвечает
     отправителю (k_ipc_send(m.from,...)). Shell: 'ask <text>' -> агент -> reply.
     ВАЖНО: shell теперь спавнится через k_proc_spawn (не k_task_create), иначе его
     нет в procs[] и k_ipc_recv не находит себя (round-trip зависал).
     КРИТИЧНЫЙ ФИКС (#GP при старте): задачи входят через `ret`, rsp%16==0, а обычный
     вызов функции даёт rsp%16==8. Из-за этого rbp смещён на 8, и SSE `movaps` (из -O2)
     даёт #GP. ФИКС: в sched.c k_task_create фрейм строится на (top - 8*8) вместо
     (top - 8*7), чтобы стартовый rsp%16==8 (как после call).
  ИЗВЕСТНАЯ ПРОБЛЕМА: framebuffer-консоль — динамический вывод (эхо/команды) нестабилен
     в headless-capture, con_buf верен. Ввод QEMU sendkey капризный. Интерактивная
     проверка: qemu -display gtk -serial stdio. ЛОГОТИП: docs/logo.png (юзерский).
     README: БЕЗ смайликов и ИИ-стиля (## **).
